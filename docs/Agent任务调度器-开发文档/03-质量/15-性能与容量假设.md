# 性能与容量假设

**先说清楚这些数从哪来。** 本项目单人自用、无生产环境、无历史数据，
所以下面的数字分三类：**已实测**（本机跑出来的）、**有推导依据**（从已知约束算出来的）、
**未评估**（没依据就写「未评估」，不编）。

## 规模假设

| 维度 | 假设值 | 依据 |
|---|---|---|
| 用户数 | **1** | 决策 20，原话通篇第一人称「我需要」 |
| 客户端连接数 | **1–3**（桌面 + 手机 + 偶尔第二台设备） | 决策 20 允许多设备配对（E-125） |
| 同时在跑的 agent | **1–5**，上限由 min(并行窗口, 每 agent 上限, 用户设定) 决定 | 交接台的并行窗口数通常落在 2–4（技能文档原文）；桌面端界面按 **5 条以上并置**设计（E-106） |
| 一份文档的任务数 | **30–80** | 本文档自身就是 M1–M10、约 70 个任务，属同一量级 |
| 同时接入的文档数 | **1–5** | E-87 要求按文档分组隔离，未设硬上限 |
| 单次运行的事件条数 | **数千到数十万** | 「单任务日志可达 10 万行以上」是 E-143 的前提 |
| 单次运行的日志体积 | **几 MB 到几十 MB**；200MB 触发切片 | E-149 定的切片阈值；E-98 的分段加载阈值是 20MB / 50 万字 |
| 库体积 | **未评估** | 正文不进库（决策 26），库只存索引；但一次运行灌多少条**里程碑**事件没有实测样本 |
| 长跑时长 | daemon **连续数天** | E-142 的环形缓冲就是为这个场景设的 |

## 目标指标

前端的感知性能目标见 12 节。这里是服务端侧：

| 指标 | 目标 | 依据 |
|---|---|---|
| 事件从 agent 输出到推达客户端 | **< 200ms**（局域网） | 无网络跳数，瓶颈只在行解析与 SSE 写 |
| 按字节偏移取一段日志（2000 行） | **< 100ms** | 偏移索引直接 seek，不扫全文 |
| `GET /snapshot` 全量快照 | **< 500ms** | 只查索引与元数据，不含正文 |
| daemon 常驻内存 | **< 300MB** | 环形缓冲 5000 条 + 每条 payload ≤32KiB 截断（E-142）；正文不驻留 |
| daemon 启动到可服务 | **< 3s** | 自检 + 单实例锁 + 打开库 + 迁移 + 装配 |
| 单实例锁与迁移 | 启动期一次性 | 见 08 节 boot 序列 |

## 已知瓶颈

按「最可能先撞上」排序：

1. **前端渲染，不是后端。** 5 条流 × 每秒数十条事件是这个产品的常态负载。
   对策已写死：事件不进 React state、按帧合并 flush（80ms）、
   `getSnapshot` 只返回整数、虚拟列表只挂可视窗口（E-143、E-144）。
   **这是第一个会被撞到的地方，也是最容易写错的地方。**
2. **行解析的背压。** agent 可能爆发式输出。
   对策：每 run 一个 AppendQueue，待写超 8 MiB 暂停 stdout、回落 4 MiB 恢复；
   **禁止把 stdout 读进内存字符串**（08 节）。
3. **better-sqlite3 是同步 API。** 一次长事务会阻塞整个事件循环。
   对策：**事务回调内禁止 `await` 与任何异步/阻塞副作用**，
   硬顺序是「先在事务里改库、事务返回后再做副作用」（08 节 tx）。
4. **全文搜索是线性扫文件**（决策 43 不建索引）。
   对策：分段流式读并周期让出事件循环，单次硬超时 10s、结果上限 500 条（E-219）。
   **若实际出现单会话上百 MB，需回头重裁决策 43。**
5. **磁盘增长**。默认不自动删除，达阈值只告警（决策 16）。
   `disk-watch` 每 5 分钟检查，超阈值置「停止新派发」标志（E-103、E-104）。

## 未评估

诚实标注，不编数字：

- **每次运行会产生多少条里程碑事件**（决定库体积增速）——没有实测样本
- **四家 agent 各自的事件密度差异**——只有 grok 的 ACP 流做过粗略观察，其余未测
- **Android 上虚拟列表滚动十万行的实际帧率**——没有真机测过；
  E-232 已把「真机各看一次」写进验收
- **worktree 数量增长后 git 操作的耗时**——单人项目下预计不会成为问题，但没测
- **SQLite WAL 在多客户端并发读 + 单写下的表现**——规模太小，未做压测

**这些不是遗漏，是明写的空白。** 真撞上了再补测，不预先优化。
