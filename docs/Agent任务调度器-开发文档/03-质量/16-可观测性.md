# 可观测性

这个产品有一个别处少见的特点：**它的业务数据本身就是可观测性数据**。
事件流既是给用户看的运行流，也是审计记录，还是排障时的第一现场。
所以本节不新建一套监控体系，而是说清**哪些走事件流、哪些走进程日志、两者边界在哪**。

## 两条记录通道

| 通道 | 内容 | 谁看 | 保留 |
|---|---|---|---|
| **事件流**（`events.ndjson` + SQLite 索引） | 业务事件：运行状态、工具调用、闸门、审批、权限受阻、配对 | 用户（界面）+ 排障 | 默认不自动删，达阈值告警（决策 16） |
| **进程日志**（Fastify logger → stdout / 文件） | daemon 自身：启动自检、HTTP 请求、未捕获异常、配置热加载、job tick 异常 | 只有排障时看 | 按大小轮转 |

**边界**：凡是用户在界面上应该看得见的，进事件流；
凡是只有出问题时才需要的，进进程日志。
**禁止把令牌、配对码、`Authorization` 头写进任何一条**（logger 的 `redact` 与事件构造处各挡一道）。

## 日志级别与关键埋点

| 级别 | 用在哪 | 例子 |
|---|---|---|
| `error` | daemon 自身出问题，需要人介入 | 单实例锁抢占失败、迁移失败、`unhandledRejection`、SQLite 损坏 |
| `warn` | 降级但仍能干活 | agent 注册表校验失败保留上一版（E-94）、模型清单解析失败降级（E-90）、探测输出无法识别（E-195）、日志索引修复补齐了 N 条 |
| `info` | 生命周期里程碑 | 启动自检通过（含 node 版本、数据目录、端口）、迁移执行了哪几个、jobs 启动、优雅退出 |
| `debug` | 只在 `AGSCHED_LOG_LEVEL=debug` 打开 | 每条 spawn 的 `LaunchSpec`（**参数数组原样，不拼串**）、每次探测的原始 stdout、SSE 订阅与注销 |

**必须埋的点**（不是「建议」，是排障时没有它就抓瞎的那些）：

1. **每次 spawn**：`runId` / agent / 解析出的绝对路径 / 参数数组 / 权限档 / 三个超时值。
   `.cmd` 走 `comSpec` 时**要记录改写后的完整参数数组**——E-130 的问题只有这里看得出来
2. **每次进程终止**：记录平台、目标 pid/进程组、使用 `taskkill /T`、`/T /F`、
   `SIGTERM` 或 `SIGKILL` 中的哪一步、两次之间等了多久，以及最终是否仍有存活子进程
   （E-119 的孤儿问题只有这里能发现）
3. **每次行解析失败**：原始行的前 200 字节 + 字节长度。
   E-140 要求「归入 raw.log 并继续」，但**必须留下计数**，否则格式漂移会静默发生
4. **未知厂商事件**：`runs.unmapped_event_count` 递增（E-202）。
   这个计数突然上涨 = 某家改版了
5. **每次配置热加载**：内容指纹、校验结果、被忽略的未知字段（E-93、E-94）
6. **每次 job tick 跳过**：上一次未完成而跳过本次的计数——
   `scheduler-tick` 的重入保护若频繁触发，说明调度算得太慢
7. **写序违例的自检**：`log-index-repair` 补齐了多少字节。
   「文件比索引多」是正常态，**「索引比文件多」是数据损坏，必须 `error`**（08 节）
8. **每次进 HEAD 判定**：runId、分支或 SHA、method（ancestor / no_diff / branch_gone / branch_gone_unmerged / dirty_worktree / error）、
   耗时、stderr 尾 200 字节——`debug`；method 为 error 记 `warn`（E-289、E-301）
9. **每次收口触发**：批次号、轮次、trigger（auto / manual）、promptSource、匹配到的 `dispatchBatches` 键、worktree 路径——`info`；
   `promptSource='builtin'` 记 `warn`（文档没给收口提示词，E-296）
10. **收口报告解析结果**：ok 或缺段清单、findings 数、unassigned 数、自报裁定与有效裁定是否一致——
    缺段、不一致、unassigned>0 都记 `warn` 并附原文前 200 字节（E-274、E-286、E-290）
11. **返工分支选择**：reviewRunId、targetRunId、adapterKind、三个能力位、选中的 mode、rework_count——`info`；
    返工块未结构化记 `warn`（E-278、E-279）
12. **修复运行派发**：每条的 taskKey、crossBatch、queued_reason——`info`；因 agent 不可用没派出的组记 `warn`（E-275、E-280）
13. **tick 因本轮已触发收口而跳过派发**的计数——`debug`（08 节 scheduler-tick 第 2 步）

**日志里禁止打印提示词全文与收口报告全文**——只打长度与前 200 字节；正文在 `raw.log` 与 `batch_wrapups.report_text`。

## 要盯的指标

没有 Prometheus，没有外部监控——**单人自用，指标直接进界面或进日志**：

| 指标 | 在哪看 | 为什么盯它 |
|---|---|---|
| 每 agent 在跑数 / 上限 | 界面批次汇总条 | 并发瓶颈来源（E-52 要求显示是三者中哪一个卡住） |
| 最后事件距今时长 | 每条运行流头部 | 停滞检测的输入（E-22、E-120） |
| `unmapped_event_count` | 运行详情 | 厂商改版的早期信号 |
| 行解析失败计数 | 进程日志 | 同上 |
| 数据目录占用 | 设置页 + `disk-watch` | E-103 的阈值告警 |
| 环形缓冲的最小/最大 event id | `GET /health` | 判断客户端断线多久会掉出重放窗口（E-153） |
| daemon 常驻内存与运行时长 | `GET /health` | 长跑内存增长（E-142 的验证点） |
| 每 agent 的探测缓存命中率 | `debug` 日志 | 探测开销是否失控（E-197） |
| 每批收口轮次 / 上限 | 批次树标题 | 一批是不是在反复收口（E-276） |
| 收口报告的 unassigned 开放项数 | 收口报告面板 | 收口 agent 有没有按格式写「涉及 〈任务ID〉」（E-290） |
| `branch_gone` 判定次数 | 进程日志 | 突然上涨 = 人在手删分支，或 daemon 停机太久没记到 SHA（E-289） |

`GET /health` 返回的不只是 `ok`——它是**唯一不需要令牌就能拿到的诊断入口**，
所以只放不含用户数据的运行时指标：`uptimeSec`、`rss`、
`eventIdRange`、`activeRuns`、`sseClients`、`dbSizeBytes`。

## 告警条件

没有告警系统，**告警就是界面上的横幅 + 系统通知**：

| 条件 | 呈现 | 依据 |
|---|---|---|
| 磁盘占用超阈值 | 顶栏横幅列出占用最大的几个任务 + 手动归档入口 | E-103 |
| 存储盘写满 | **立即停止新派发**并明确报错 | E-104 |
| agent 变为不可用（路径失效 / 探测失败） | 该 agent 卡片置灰 + 写明缺什么 | E-29、E-88、E-195 |
| 运行完全无流事件超阈值 | 醒目告警（仍在输出时只标弱提示） | E-120 |
| 任务停在闸门等人超阈值 | 归类「等人」不重复告警，超阈值提示「中止以释放并发窗口」 | E-122 |
| daemon 重启后发现「运行中」的孤儿记录 | 标「异常终止」或「失联」并给处置入口 | E-123、E-02 |
| 文档指纹变化且有在途运行 | 顶栏横幅「本文档已更新，N 个任务的依据已变」 | E-50、E-78 |
| 某 agent 被手动调到最高权限档 | **持续**显示醒目标记（非一次性 toast） | E-136 |
| agent 自行 push 到远端 | 任务详情里高亮标注 | E-75 |
| 批次进入 `needs_attention` | 顶栏横幅 + 系统通知，写明是哪一种原因（收口运行失败／报告不合八段／超 2 轮仍 open／无可派修复项／agent 不可用）+ 批次级收口闸门 | E-274、E-276、E-287、E-288、E-295 |
| 批次停在 `awaiting_landing` 超 30 分钟 | 归「等人」类不重复告警，标题保持「等你落地 N 个」暖色 | E-272、E-122 同法 |
| 返工块「未结构化」 | 审批卡带「投递原文到实施会话」按钮，不自动投递 | E-278 |
| 进 HEAD 判定连续 error ≥3 次 | 横幅「无法判定分支是否已合入」，不推断为已合入 | E-301 |
| 收口自报 clean 但有效裁定 open | 收口报告面板同时显示两者 | E-286 |

**「无人应答不会自动批准」必须写在审批卡上**——
可以超时自动取消（写明即可），**绝不自动批准**（11 节 avoid#23）。

## 排障时的第一现场

出问题时按这个顺序看，写在这里是为了三个月后自己还记得：

1. `GET /health` —— daemon 活着吗？内存多少？event id 到哪了？
2. 该运行的**运行流** —— 界面上直接看，最后一步是什么、卡在哪个状态
3. `raw.log` —— 归一化之前的原始输出，格式漂移只有这里看得见
4. `events.ndjson` —— 归一化之后的全量事件（**永不截断**，与索引表不同）
5. 进程日志 —— spawn 参数、终止方式、解析失败计数
6. `agents.json` 与派发快照 `launch_spec_json` 的差异 ——
   在途运行用的是**快照**，与当前注册表不一致是正常的（E-93）
