# 里程碑与交付顺序

**总量 77 个任务、121.5 人天。** 按单人推算约 6 个月（含缓冲）。
这个数字不是估出来的乐观值——它是 10 个模块逐任务加总的结果，
其中最大的两块是 M9 界面（29 人天）与 M4 适配（21 人天）。

批次按依赖排序。**每一批结束时都必须有能演示的东西**，
否则前四个月拿不出任何可见成果，这对单人项目是致命的。

## 顺序上的硬约束

- **M1 必须最先做完。** 其余九个模块全部依赖它，且它内部的三平台 platform 适配器
  与 `spawn` 基座（M1-T7）是 M4 全部适配器的地基。
- **M2 与 M3 可以并行**（互不依赖，都只依赖 M1），但单人做就按上表顺序。
- **M4 是最大的单一风险块**（21 人天、12 个任务、47 条边界）。
  它的前三个任务（注册表、参数模板、指纹探测）是后面九个的公共前提，
  **建议先把 codex 与 claude 两家打通再做 pi 与 grok**——
  这两家形态差异最大（daemon/thread 模型 vs stdin/stdout 双向流），
  接口被它们定型后，剩下两家是填空（决策 6 的假设）。
- **M9 理论上可以很早开工**（只依赖 M2 的契约），
  这是「客户端界面」与「壳」拆成两个模块的收益之一。
  单人做的话不并行，但**如果哪天有第二个人，这里是唯一自然的切口**。
- **M10 必须最后**——它依赖 M9 的界面已经能跑。
  R-01（Windows Rust 工具链）与 R-02（Android 环境）原本都在这一批爆发，
  **两条已于 2026-09-01 关闭**：Tauri v2 空壳构建已跑通，JDK 17 与 Android SDK/NDK 已就位。
  macOS/Linux 仍需各自 runner 与运行依赖证据（R-17）。把它放在最后仍然是有意的：
  前五批成果可通过浏览器直连，但没有 M10-T5 通过就不能发布“三平台桌面版”（E-257、E-265）。

## 每批的验收前置

- **第三批结束时**必须真派五个 agent，不能用假子进程蒙混——
  假进程测不出参数拼错、模型名无效、登录态过期（17 节）
- ~~**第六批的第一个前端任务**必须出一屏真页给用户目视确认~~
  **已于 2026-09-01 提前完成并确认**——真页在第六批开工前就出了，R-03 随之关闭（决策 28、E-160）。
  第六批不再背这个前置动作；M9-T1 直接照 11 节已确认的 token 表实现
- **第六批结束时**必须在 Android 真机与 Windows 125%/150% 缩放下各看一次 12 个形状，
  并在 Windows、macOS、Linux 各做一次桌面壳启动、通知点击和 Unicode 路径运行验收
  （E-232、E-266）。

## 如果要砍

单人 5–6 个月是很长的周期。若中途要收缩，按这个顺序砍——
**从后往前砍，且绝不砍第一批到第四批**：

1. **先砍 M10 手机壳**：降级为浏览器直连，只损失原生通知与安全令牌存储（E-200）。省 3.5 人天
2. **再砍 M9 的手机端适配**（M9-T12、M9-T13）：只做桌面端。省 3 人天
3. **再砍 M7 的审查 agent**（M7-T2、M7-T3、M7-T4）：只留机械检查，审查全人工。
   省 3.5 人天——但这等于放弃补充需求里的「审查可自动」，**需要重新裁决**
4. **绝不砍**：M1 的进程树终止（E-119，砍了会留孤儿占文件锁）、
   M4-T3 的指纹探测（E-195，砍了会静默派错 agent）、
   M8-T2 的路径冲突排队（E-46，砍了并行必然互相污染）、
   M6-T1 的状态机（E-23，砍了「已退出」就等于「已落地」，整个产品的判断基础没了）
