# 概述与目标

## 这个东西是什么

一个**跑在本机的 AI coding agent 任务调度器**。

它读一份由 `unattended-run` 技能产出的开发文档，从中取出已经拆好、带依赖关系的任务清单，
把任务**按批次派发**给装在这台电脑上的多个不同厂商的 AI coding agent 去写代码，
然后盯着它们干活、自动跑审查、把需要人拍板的地方摆到人面前。

它由三部分组成：一个**常驻服务（daemon）**、一个**桌面端**、一个**手机端**。
daemon 是真正干活的那个；两个端只是它的两副面孔，共用同一套界面代码。

## 解决的是什么问题

这份开发文档的阅读器里本来就有一个「任务交接台」。它的现状是：

- 人点一下「复制实现提示词」，把提示词粘到 codex 之类的 agent 里
- agent 干完，人再点「复制审查提示词」，拿回来给审查者
- 通过了，人手工走 `gh stack` 落地
- 任务状态靠**人手工点击**在「待派 / 进行中 / 已落地」三态之间切换，存在浏览器 localStorage 里

也就是说，**交接台知道该干什么，但对 agent 实际在干什么一无所知**。
中间「复制 → 粘贴 → 等 → 回来看一眼 → 再复制」的全过程都是人肉的，
人必须守在电脑前，而且一次只顾得上一两个。

这个调度器接管的正是这一段：把人肉的复制粘贴变成自动派发，
把手工点击的三态变成**从 agent 真实输出观测到的状态**，
并且让人在离开电脑之后仍然能看见进度、能回话、能叫停。

## 谁用它

**一个人**——写这份开发文档的那个开发者本人。单人单机，不是团队产品，没有账号体系。

他的典型一天：

1. 选一份开发文档，选这一批要干的任务
2. 给每个 agent 选好默认模型
3. 点派发，然后**长时间盯着几个运行流**
4. agent 中途问「要不要装这个依赖」，他回一句
5. 某个 agent 跑偏了，他把它中止，换一个 agent 重派
6. 审查自动跑完，他看结论、点放行
7. 夜里派一批活，第二天早上看结果；白天出门时用手机看进度

## 已确认要做的能力

下面每一条都经过裁决（编号对应 `05-附录/22-决策记录.md`）。
带 ★ 的是用户原话没提、但判定为「不做主流程就不完整」而补进来的。

| 能力 | 来源 | 决策 |
|---|---|---|
| 从 `docs-data.js` 读入任务、依赖、验收标准与边界编号（**批次不在 payload 里，本产品按 `deps` 自己拓扑分层，规则与交接台逐字一致，保证「第 3 批」两边指同一批任务**） | 原话「根据文档产出的 任务交接台中的任务」 | 4, 48 |
| 把任务派给 codex / claude / pi / grok 四个 agent（插件式，可加第五个） | 原话点名了五个 agent | 6 |
| 按批次派活，按**本产品自己的并行窗口设置**限流（默认 2，可调 1–6，**不移植阅读器的 `bestLanes()`**——它要读阅读器的进度 localStorage），路径冲突的任务自动排队 | 补充需求「按批次派活」 | 9, 48, 49 |
| 给每个 agent 指定默认模型，模型清单从各家配置文件读出；单任务可临时覆盖 | 补充需求「选择指定默认模型（可获取agents配置文件中的模型）」 | 7, 8 |
| 看到每个任务的状态与通用进度信号（最后一条消息、改动文件数、耗时、token） | 原话第 1 点 | 5 |
| 进入任务详情查看该 agent 的完整会话内容，分段加载 | 原话第 2 点 | 16 |
| 三个闸门（派发前 / 审查后 / 落地前）各自可设「自动」或「等我确认」 | 补充需求「自动/半自动」 | 10 |
| 自动审查：先跑本地机械检查，过了再派一个 agent 跑交接台生成的审查提示词 | 补充需求「先实施，审查可自动」 | 11 |
| ★ 任务状态机，把「已退出」与「已落地」严格分开 | 退出码为 0 不等于活干完了 | 5 |
| ★ 中止运行中的任务、换一个 agent 重派、长时间无输出时标记停滞 | 检测得出问题却没有处置手段等于没检测 | 19 |
| ★ 在会话里回话与授权（两端都能回） | 中档权限必然会在装依赖处停下，没有回话通路「自动派活」就在第一个提问处停摆 | 18 |
| ★ 每任务独立 git worktree 隔离，读 diff 算改动 | 多个 agent 同时改一个工作区必然互相污染 | 6, 12 |
| ★ agent 接入注册表（路径、参数模板、并发上限、默认模型可配） | 四家形态各异且在高频改版 | 15 |
| ★ 文档重新生成后，拿派发时的快照与当前文档比对并打标 | 文档是可反复重新生成的产物，验收标准会变 | 13 |
| ★ 手机与桌面的设备配对（一次性配对码 + 可单独吊销的长期令牌） | 原话要「手机 app 端」，而 agent 都在电脑上 | 2, 20 |
| ★ 落地清单：worktree 路径、分支名、diff 摘要、可一键复制的 `gh stack` 命令 | 派完到落地之间不能断在产品外面 | 12 |

## 什么算做完

第一版满足下面全部七条，才算交付：

1. 选一份真实的开发文档，任务、依赖、批次、验收标准、边界编号全部正确读入。
2. 给 codex / claude / pi / grok 四个 agent 各派出一个真实任务，四个都能跑起来并正常结束。
3. 任务状态能从 agent 的真实输出观测得出，且「已退出」与「已落地」不会被混为一谈。
4. 能在任务详情里翻完一个几十万字的会话，桌面端与手机端都打得开、不卡死。
5. 一整批任务能在半自动模式下跑完：自动派发 → 自动机械检查 → 自动 agent 审查 → 停在人面前等放行。
6. 手机与电脑完成配对后，能在手机上看到进度、收到完成通知、回一句话、中止一个任务。
7. 派发过的任务都能给出落地清单，人照着它用 `gh stack` 就能落地。

## 明确的边界

- **不替用户提交、push、建 PR 或合并**——见 `02-非目标.md`。
- **不自建任何服务器**，会话内容与源码不出本机。
- **不改动开发文档目录里的任何文件**，包括不回写交接台的状态。
