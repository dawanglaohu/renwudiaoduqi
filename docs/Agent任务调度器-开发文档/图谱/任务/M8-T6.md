# M8-T6　批次收口触发、轮次与批次级闸门

- 所属模块：[[M8]]　**派发调度**——决定什么时候把哪个任务、用哪个 agent 与哪个模型、以什么权限派出去，并按批次、并行窗口、每 agent 并发与路径冲突限流，在三个闸门处停或放行、失败或重派时重新入队；判定本批分支是否都进了 HEAD、触发收口运行、按收口报告派修复运行与管理收口轮次也归它；泳道（窗口槽位）分配、任务终态后的补位、查 bug 与收口模式两个开关的持久化同样归它——泳道分配是它算出的派生数据。凡涉及顺序、名额、放行、重派的都归它；任务指派写进派发快照、阶段取值链（任务指派 → 阶段覆盖 → agent 默认）与收口指派设置也归它——它是唯一决定「这一阶段用谁跑」的地方，M7 只消费结果
- 前置依赖：[[M8-T3]]、[[M8-T4]]、[[M3-T6]]、[[M7-T6]]、[[M5-T5]]
- 完成后解锁：[[M7-T8]]、[[M8-T7]]、[[M8-T8]]、[[M9-T19]]

## 输入 / 产出

- **输入**：M8-T3 的 tick 与批次路由；M3-T6 的收口材料；M7-T6 的解析器；M5-T5 的进 HEAD 判定；M8-T4 的闸门模型
- **产出**：`domain/batch-state-machine.ts`、`domain/wrapup-prompt.ts`、`domain/wrapup-policy.ts`、`service/wrapup.ts`（`triggerWrapup` / `recordWrapupResult` / `listWrapups`）、`service/batch.ts` 的 `transitionBatch()`、`http/routes/batches.ts` 新增 `wrapup` 与 `wrapups` 两端点、`repo/batch-wrapups.ts`、四表重建迁移（batches 七值、runs 新列与 `kind` 四值含 `bughunt`、dispatch_snapshots / gates 的 task_id 可空、`batch_wrapups` 表）、`db/migrate.ts` 的 `foreign_keys=off` 例外、shared 的 routes / codes / events / batches DTO 增量

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 批次状态七值白名单只在 `transitionBatch()` 里改，每次迁移发 `batch.advanced{from,to,reason}`
tick 第 1 步按节流刷新 `is_in_head` 与 `branch_tip_sha`，第 2 步全部 landed 但有未进 HEAD → `awaiting_landing`（[[E-272]]），全部进 HEAD 且无在途收口且轮次 < 2 → 派收口运行且本 tick 不再派发
读接口不跑 git（[[E-283]]、[[E-301]]）
2) 收口运行 `kind='wrapup'`、`task_id` 为空、`workspaceWrite`、占 1 名额、同批同时只一条（唯一部分索引）
agent/model/effort **默认跟随本批 `ended_at` 最晚的 landed 实施运行的任务指派**（即决策 116 的 `follow` 模式，并列取 run id 字典序最大），第 2 轮沿用上一轮，agent 不可用转 `needs_attention` 不静默换家，手动触发可在 body 覆盖（[[E-287]]、[[E-344]]）
三值的取值收成 `triggerWrapup()` 内单一函数入口，pipeline 设置 `wrapupAssignment` 的 `fixed` 模式由 M8-T9 接进该入口，本任务不读 `settings.pipeline`
3) 提示词按 08 节四段顺序组装，材料逐字，材料缺失走 builtin（[[E-296]]）
工作区指针段只给本批 diff stat 与任务清单、不内联 diff 正文，收口 agent 自己在工作区读文件
报告里「基于部分 diff」的标注由解析器原样保留进 `summary_text`，不因此改裁定（[[E-285]]）
4) 收口运行退出后走八段解析不派审查 agent，空 diff 不判失败（[[E-294]]）
解析成功 INSERT `batch_wrapups` 并按有效裁定迁移：clean/fixed → `done`，open → 交 M8-T7 派修复
解析失败或运行失败/中止 → 收口运行 `awaiting_human` + `task_id` 为空的收口闸门 + 批次 `needs_attention`，不回滚工作区（[[E-274]]、[[E-295]]）
5) 批次级闸门 pass 必带 comment → 写 `is_human_verdict=1` 的人工裁定行 → `done`
reject 只关闸门
手动 `POST /batches/:id/wrapup` 从 `needs_attention` 不受自动上限、受硬顶 6 轮，超限 `E_WRAPUP_ROUND_LIMIT`
条件不满足 `E_BATCH_NOT_WRAPPABLE` 带 `details.reason`
幂等键重复 409 返回既有 run（[[E-288]]）
6) 迁移首行标记走 `foreign_keys=off` 例外，`foreign_key_check` 零行，含 0001 数据的库 fixture 逐行无丢失、新旧库 `sqlite_master` 一致（[[E-291]]）
7) 17 节的 `batch-wrapup` 集成剧本跑到 `done`
事务内不 await/spawn/publish（08 节）

## 必须处理的边界

- [[E-272]]　全部已验收但分支未进 HEAD
    - 触发：本批任务全部 landed，至少一条 landed 运行的分支尚未进入当前 HEAD
    - 期望：批次转 `awaiting_landing`，标题显示「等你落地 N 个」暖色（N 来自 daemon 字段 notInHeadCount）；不派收口、不解锁下一批；进 HEAD 判定只在 `scheduler-tick` 内按节流做（每运行 ≥30s 一次、每 tick ≤20 条），不在任何读接口现跑 git，不做比 tick 更密的轮询
- [[E-274]]　收口输出不合八段
    - 触发：收口运行的最终文本缺任一段、段头顺序找不齐、或条目格式不合
    - 期望：按「收口未完成」处理：保留原文可读、不做部分解析、不猜；收口运行转 `awaiting_human` 并开批次级收口闸门，批次 `needs_attention`，不计入自动轮次
- [[E-283]]　收口运行的名额与权限
    - 触发：收口运行被派出
    - 期望：计入并行窗口与该 agent 并发上限（占 1 个名额）；权限档恒 `workspaceWrite`，不给 `unrestricted`；同一批次同时只有一条收口运行
- [[E-285]]　收口 agent 上下文超限
    - 触发：本批 diff 或测试输出超出收口模型上下文
    - 期望：与 E-65 同法：给 diff stat 全量 + 验收标准命中文件全文，其余折叠，报告标注「基于部分 diff」；产品不因此判失败
- [[E-287]]　自动收口的 agent 取值
    - 触发：tick 自动触发收口，无人在场选 agent
    - 期望：第 1 轮取本批 `ended_at` 最晚的 landed 实施运行**运行行的 `agent_id` / `model_name` / `effort_tier`**（M8-T9 后为快照 `assignment_json`，即任务指派；并列取 run id 字典序最大）；第 2 轮起沿用上一轮收口运行的取值；推导出的 agent 不可用则不派、批次 `needs_attention`（原因 `agent_unavailable`），人用手动触发带 `agentId` 覆盖；禁止静默换家
- [[E-288]]　批次进入 needs_attention 后人的出口
    - 触发：收口运行失败/中止/中断、八段解析失败、open 达上限、open 但可派条目为零、agent 不可用
    - 期望：每次进入都在最近一条收口运行上开一张 `task_id` 为空的批次级收口闸门：pass 必须带 comment → 写一条 `is_human_verdict=1`、`verdict=clean` 的收口记录 → 批次 `done`；reject 只关闭闸门，批次留在 `needs_attention`；手动再收口不受自动上限约束、受硬顶 6 轮约束，到顶返回 `E_WRAPUP_ROUND_LIMIT`；批次因重派离开 needs_attention 时未决闸门标 superseded
- [[E-291]]　迁移需要整表重建
    - 触发：扩枚举 CHECK 或放宽 NOT NULL，SQLite 只能 12 步法重建，且外键开着时 DROP 会失败
    - 期望：首行标 `-- requires: foreign_keys=off` 的迁移在事务外先关外键、事务内重建、执行后 `PRAGMA foreign_key_check` 必须零行否则回滚并以非 0 退出、finally 开回；标记不在首行按普通迁移执行；重建不算改已应用文件
- [[E-294]]　收口运行退出但没改代码
    - 触发：`kind=wrapup` 的运行退出码 0 且 diff 为空
    - 期望：不按 E-61 判失败；其 exited 后走八段解析而不是派审查 agent；解析成功且裁定 clean 即批次 `done`
- [[E-295]]　收口运行中途失败或被中止
    - 触发：收口运行 failed/aborted/interrupted 时工作区已有半成品改动
    - 期望：不回滚工作区、不派修复运行；批次 `needs_attention` 并开收口闸门；落地清单照常列出该分支并标「未完成的收口改动」，由人决定丢弃或合入
- [[E-296]]　收口提示词匹配不到
    - 触发：文档 `dispatchBatches` 里没有 tasks 集合与本批当前任务集合相等的条目，或文档未导出该键
    - 期望：用内置通用收口提示词并标「文档未提供」（`prompt_source=builtin`，记 warn）；匹配只按派发快照那一刻的文档，不按当前文档；材料逐字引用不改写，外层包装说明覆盖其中的提交/推送/PR/合并/记录文件步骤
- [[E-301]]　进 HEAD 标记的单调性
    - 触发：分支合入后本地分支被删、worktree 被清理、或后续 git 判定报错
    - 期望：`is_in_head` 一旦为 1 不回 0；tick 在分支存在时记录 `branch_tip_sha`；判定连续 error ≥3 次横幅「无法判定分支是否已合入」，不推断为已合入
- [[E-344]]　收口指派缺省与取不到
    - 触发：tick 自动触发收口；`wrapupAssignment` 为 `{mode:'follow'}`（默认）或 `fixed`
    - 期望：`follow`：取本批 `ended_at` 最晚的 `landed` 实施运行的任务指派（并列取 run id 字典序最大），第 2 轮沿用上一轮收口快照；本批没有任何成功实施运行快照（全部人工裁定 landed）→ `follow_source_missing`，不派、批次 `needs_attention`（原因 `agent_unavailable` 同一出口），卡片提示改固定指派或手动 body 覆盖。`fixed`：只填 agentId 时 model／effort 回落 follow 取到的值（同家沿用、跨家按 E-342 重映射）；agentId 已从注册表删除 → 设置页标红「agent 不存在」，触发时同上转 `needs_attention`。手动 `POST /batches/:id/wrapup` 的 body 覆盖优先级最高、只作用该轮；收口快照 `assignment_json.source='wrapup_settings'`、`followedTaskId` 在 follow 模式为被跟随任务；收口修复运行沿用被修任务的指派快照，不读本项
