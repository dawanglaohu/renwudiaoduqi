# M1-T8　三档超时计时器与背压

- 所属模块：[[M1]]　**运行底座**——让 daemon 在这台机器上稳定跑起来并把字节落到磁盘上：进程单实例与端口、启动自检、开机自启注册、数据目录、结构化存储的连接与迁移、日志正文的追加写与字节偏移索引、以及全部平台差异（进程树终止、路径规范化与长路径、配置目录、子进程编码）的唯一收口。凡与操作系统、磁盘、进程存活打交道而不带任何业务概念的都归它
- 前置依赖：[[M1-T7]]
- 完成后解锁：[[M4-T8]]、[[M4-T9]]、[[M4-T10]]、[[M4-T11]]、[[M6-T2]]

## 输入 / 产出

- **输入**：M1-T7 的 spawn 基座
- **产出**：`proc/timers.ts`、`AppendQueue` 背压接线

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 启动超时与思考超时**分开计时**，native 默认 60s、generic-acp 默认 180s（[[E-190]]）
2) `idleTimeoutMs` 只喂给停滞检测打弱标记，**proc 层绝不因它杀进程**（[[E-120]]）
3) 待写字节超 8 MiB 时 `pause()`、回落 4 MiB 再 `resume()`
代码中不存在把 stdout 读进内存字符串的路径
4) 内存只保留最近 **5000** 条事件的环形缓冲（与 M2-T4 的重放窗口是同一个缓冲，**不另开第二个**），单条 payload 超 32 KiB 入缓冲前替换为引用（[[E-142]]）

## 必须处理的边界

- [[E-120]]　长思考被误判停滞
    - 触发：超过阈值但 NDJSON 仍在输出
    - 期望：只标「疑似停滞」的弱提示，不改运行状态；只有完全无流事件超阈值才升级为醒目告警
- [[E-142]]　daemon 长跑内存增长
    - 触发：连续运行数天
    - 期望：内存只保留最近 N 条事件的环形缓冲，历史事件全部落盘按需回读
- [[E-190]]　ACP 适配器冷启动慢
    - 触发：经 `npx` 拉起或离线导致启动缓慢
    - 期望：**启动超时与 agent 思考超时分开计时**，否则冷启动会被停滞检测误判为卡死

## 实施沉淀

<!-- notes:begin -->
- 启动超时与思考超时的生命周期分离：ACP 经 npx 首次下载或弱网拉起时冷启动可耗时上百秒。若冷启动期沿用空闲计时，stall-detector 会将正常拉起误判为停滞。实现确保在首条有效 JSON 事件到达前，isIdleSuspected 恒返回 false；首条事件到达解除启动超时后，空闲与思考计时方以该时刻为基准起算。
- 停滞检测的弱判定边界：proc 层仅负责向 stall-detector 提供 isIdleSuspected 与 idleDurationMs 查询能力，全生命周期绝不注册因 idle 超时而执行的 kill 逻辑；唯二强杀分支仅为 startupTimeout（标派发失败）与 checkTimeout（机械检查硬超时）。
- 水位滞回（Hysteresis）设计：8 MiB 触发 pause 与 4 MiB 触发 resume 之间必须维持状态锁，未回落至 4 MiB 前维持暂停，防止字节在 8 MiB 临界点高频抖动导致 child.stdout 反复 pause/resume 造成系统调用颠簸。
- 管道流控与内存防御：Node.js Readable 挂载 data 事件时会自动将流转为 flowing 模式。背压通过直接接管 child.stdout.pause() 使内核管道满载从而阻塞子进程写端；stdout 读取端由 line-reader 基于 1 MiB 软上限的 Buffer 切割逐行产出，代码路径无全量累计字符串。
<!-- notes:end -->
