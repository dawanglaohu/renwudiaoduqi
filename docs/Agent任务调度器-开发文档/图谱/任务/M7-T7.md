# M7-T7　审查续接与轮次上下文

- 所属模块：[[M7]]　**审查流水线**——对已结束的运行做「合不合格」的判定：先跑本地机械检查，通过后以只读档派一个 agent 跑文档给出的审查提示词，产出 pass / rework / doc-issue 并回灌 rework 意见；从审查输出提取返工文本、按能力位选回灌／恢复／新开返工运行，以及解析收口运行的八段报告，也归它；第 N+1 轮审查续接同一审查会话、查 bug 阶段的运行与五段报告解析同样归它。凡「判定一次运行的结果」的都归它；审查、查 bug 阶段的运行用哪个 agent、模型与思考强度，一律读派发快照里的任务指派（审查可被 pipeline 设置的「审查覆盖」替换），不自己取 agent 默认
- 前置依赖：[[M7-T2]]、[[M7-T4]]、[[M6-T6]]
- 完成后解锁：[[M7-T8]]

## 输入 / 产出

- **输入**：M7-T2 的第 1 轮审查派发；M7-T4 的返工回灌与 `{reviewRunId, targetRunId, reworkText}`；M6-T6 的类型化投递结果；派发快照里的 `adapterKind` 与能力位
- **产出**：`service/review.ts` 的 `startReviewRound({taskId, implRunId, round, reworkItems})`、`proc/registry.ts` 的 `reassign(prevRunId, newRunId)`、`domain/rework-prompt.ts` 的续审头部常量、`repo/runs.ts` 的 `findLatestReview`、新增一个普通迁移（`runs.review_round`、`runs.continued_from_run_id REFERENCES runs(id)`、`ux_runs_continued` 唯一部分索引、`(task_id, kind, review_round)` 索引）、`test/unit/review-round.test.ts`

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 第 N+1 轮 = 新 `kind='review'` 行（`review_round=N+1`、`continued_from_run_id` 指向第 N 轮审查行、`parent_run_id` 仍指被审实施运行、`permission_tier='readOnly'`）
代码中不存在复用第 N 轮行当第 N+1 轮的路径
`continued_from_run_id` 跨任务或指向非 review 行由 service 拒绝（决策 89）
2) 通路按能力位选、不试了再降级：注册表仍持有第 N 轮进程且 `canReply` → `reply`（`proc.registry.reassign` 后经 M6-T6 向 stdin 注入「第 N+1 轮，只核上一轮的 R 条目：…」）
已结束且 `canResume` 且 `vendor_session_ref` 非空 → `resume`（新 spawn 带 `resumeSessionRef`，`vendor_session_ref` 与第 N 轮相等）
都不 → `new_session`，`vendor_session_ref` 为空、提示词头部为自包含块 `{round, previousReviewRunId, reworkItems[]}`，上一轮 REWORK 条目原文逐字（[[E-304]]）
3) 撑爆按事件流结构判定：投递后、该轮首条内容事件前出现未送达／启动超时／退出／错误事件 → 同一函数降级为 `new_session` 恰一次（恢复分支失败行标 `failed`、reason `continuation_exhausted`）
内容事件之后才失败按 [[E-62]] 转人不新开
新开后再次内容前失败 → 转人并 comment `review_continuation_failed`
判定函数只读事件种类，厂商错误串只进日志
返工反喂实施会话时用同一判定函数，触发即按决策 60 第三分支新开 `origin='rework'` 运行且 `rework_count` 不重复加（[[E-330]]、[[E-304]]、[[E-305]]、[[E-113]]）
4) 续接目标 `session_archived_at` 非空先抛 `E_SESSION_ARCHIVED`（[[E-302]]）
5) 第 N+1 轮机械检查照常跑、verdict 写在新行
轮次与返工计数写死为 `review_round = rework_count + 1`
查 bug 触发的再审（`reworkItems` 来自 FIXED 条目）走同一入口（[[E-307]]）
6) 旧审查行 `review_round` 为 NULL 时读侧按 1 处理、不回填
事务内不投递、不 spawn、不 reassign（08 节）

## 必须处理的边界

- [[E-113]]　消息投递失败
    - 触发：进程已死或管道已断
    - 期望：消息落地为「未送达」并保留原文可复制，绝不静默丢弃或假装已发出
- [[E-302]]　任务终态时会话进程还在
    - 触发：任务进入 landed／failed／aborted／interrupted，而该任务的实施／审查／查 bug 会话进程仍存活
    - 期望：结束并归档该任务全部会话：进程走 `platform.killTree` 两阶段（E-119），每条运行写 `session_archived_at`，`vendor_session_ref` 从此只作只读引用；同一泳道的下一个任务一律新建会话，**绝不把已归档会话拿来跑新任务**
- [[E-304]]　审查会话不能续接或已撑爆
    - 触发：第 N+1 轮审查时审查 agent 的 `canReply` 与 `canResume` 都为假，或续接投递返回上下文超限／未送达
    - 期望：新开审查运行（`review_round=N+1`、`continued_from_run_id` 指向上一轮审查运行），提示词头部带轮次与上一轮 REWORK 条目原文、只核这些条目；分支按能力位决定而不是试了再降级；不静默丢失轮次
- [[E-305]]　实施会话上下文撑爆
    - 触发：反喂返工文本时实施 agent 报上下文超限，或续接投递未送达
    - 期望：按决策 60 第三分支新开实施运行（`origin='rework'`、同 worktree 与分支、attempt_no+1），提示词自包含（返工块原文 + 快照实施提示词「收到返工指令时」段 + 工作区指针 + 只改列出条目）；`rework_count` 照加；不静默丢弃返工文本
- [[E-307]]　查 bug 修了东西
    - 触发：查 bug 报告 FIXED 段非空且自审查 pass 以来工作区 diff 非空
    - 期望：`rework_count<2`：先 `+1`，再通知**该任务的同一审查会话**再审一轮（续接规则同 E-304），提示词头部「第 N 轮，只核查 bug 阶段的修改：〈FIXED 条目原文〉」；`rework_count` 已达 2：不派再审、不 +1，任务转 `awaiting_human`，闸门 comment 写 `bughunt_fixed_over_limit`，审批卡列 FIXED 条目与 diff 摘要；FIXED 非空且 NOT_FIXED 含 S1/S2：直接转人、不先再审；运行轨上画成查 bug 节点回到审查节点的回环，轮次沿用同一 `rework_count`；不派第二个审查会话、不跳过再审直接落地
- [[E-330]]　续接撑爆的判定
    - 触发：第 N+1 轮审查续接投递（回灌或恢复）之后，或返工反喂实施会话之后
    - 期望：按归一化事件流结构判定、不看厂商字符串：该轮首条内容事件（`agent_message_chunk`／`agent_thought_chunk`／`tool_call` 任一）之前出现未送达（E-113）、启动超时（E-190）、进程退出或错误类事件 → 判「会话不可续」，只新开一次（审查按 E-304、实施按 E-305），恢复分支产生的失败行标 `failed`（reason `continuation_exhausted`）不计入 `review_round`；内容事件之后才失败按 E-62 转人、不新开；新开的会话再次在内容前失败 → 不再新开，转人并 comment `review_continuation_failed`；投递成功但既无事件也不退出 → 走停滞检测（E-120），不算撑爆；`canReply` 与 `canResume` 皆假的 agent 不进入本判定，按能力位直接新开
- [[E-62]]　审查 agent 崩溃或超时
    - 触发：审查这一步自身失败
    - 期望：既不算 pass 也不算 fail，标「审查未完成」转人工；任何情况下不默认放行
