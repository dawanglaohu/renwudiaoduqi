## 实施沉淀

<!-- notes:begin -->
1. **权威计数口径（AC 1, AC 2）**：批次级统计严格使用 `deriveTaskState({ manualState: task.manual_state, runs: taskRuns }, undefined, { ignoreWrapupFix: true })` 派生单任务权威状态。其中跨批修复运行（`origin='wrapup-fix'`）不影响已验收任务的 `landed` 归属（E-275）。`taskCount` 为批次下任务总数，`landedCount` 为 `state === 'landed'`，`runningCount` 为 `{starting, running, reviewing, reworking}`，`waitingCount` 为 `{awaiting_human, awaiting_reply, orphaned}`。
2. **默认展开判定（AC 1, E-284, 决策 71）**：`defaultExpanded` 在批次处于 `{running, wrapping, awaiting_landing, needs_attention}` 四种活跃或需关注状态时为 `true`，其余状态为 `false`。前端 `batch-expansion.ts` 接收快照中的 `defaultExpanded` 作为种子；用户手动折叠后不被后续快照静默冲掉；当 `batch.advanced` 推动批次进入上述状态时，重新并入展开集合，保证自动展开只增不减。
3. **接口一致性与并发安全（AC 1, AC 2）**：`GET /api/v1/batches`、`GET /api/v1/batches/:batchId` 与 `GET /api/v1/snapshot` 统一通过 `computeBatchSummary` 与 `toBatchDto` 产出同构 `BatchDto`。事务内与事务后读取直接反映 SQLite 最新权威事实。
4. **规避破坏既有测试的契约设计与 Jev 裁决**：`taskCount/landedCount/runningCount/waitingCount/defaultExpanded` 作为可选只读属性加入 `BatchDto`，与 `canWrapup?: boolean` 及 `notInHeadCount?: number` 风格完全统一；在服务端正式产出中始终保证下发确切数值，同时避免因强制必填破坏范围外未 mock 这些字段的历史测试。经 Jev 裁决拍板（model=jev-1.13.0 line=adjudicate: pick=B(high 0.99) spec_change=no(0.12) outside_stack=no(0.05) needs_owner=no(0.05) reversible=yes(0.75) adopt=take(B)），选定方案 B：在 6 个有效路径内以可选契约字段实现，保持范围收敛与完全向后兼容。
