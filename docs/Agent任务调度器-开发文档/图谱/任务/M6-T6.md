# M6-T6　回话投递与能力位约束

- 所属模块：[[M6]]　**运行监管**——管一次运行从启动到结束的全过程：状态机（「已退出」与「已落地」分开）、收流与落盘编排、按游标分段回读与厂商会话文件的只读引用、进度信号、停滞检测、中止与 daemon 重启后的对账、回话投递；任务到达终态后结束并归档该任务全部会话（进程还在走 `killTree` 两阶段），归档后会话引用只读、不得复用，也归它。凡「这一次运行现在怎么样、它说过什么」的都归它
- 前置依赖：[[M6-T1]]、[[M4-T8]]
- 完成后解锁：[[M6-T7]]、[[M6-T10]]、[[M7-T4]]、[[M7-T7]]

## 输入 / 产出

- **输入**：各适配器的注入通道与能力位
- **产出**：`POST /runs/:id/messages`、投递路径

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 「可回话」做成能力位，**UI 按能力位灰掉按钮而不是点了才报错**
不具备时返回 `E_CAPABILITY_UNSUPPORTED`（[[E-117]]）
2) 进程已死或管道已断时消息落地为「未送达」并保留原文可复制，**绝不静默丢弃或假装已发出**（[[E-113]]）
3) 会话已结束但支持 resume 的走「恢复会话后投递」并明示这是一次新运行
不支持恢复的禁用发送并提示改用重派（[[E-112]]）
4) 两端同时回话时按到达先后串行投递，每条记录来源设备与时间戳，**不做去重合并**（[[E-114]]）
5) 空消息拒绝提交
超长在发送前提示并让人确认截断点，**不静默截断**（[[E-116]]）
6) 写 stdin 时检查 `write()` 返回值并在 `drain` 后续写

## 必须处理的边界

- [[E-112]]　会话已结束后才回话
    - 触发：用户在 agent 回合结束后点发送
    - 期望：支持 resume/fork 的 agent 走「恢复会话后投递」并在 UI 明示这是一次新运行（新运行记录、新退出码）；不支持恢复的禁用发送并提示改用重派
- [[E-113]]　消息投递失败
    - 触发：进程已死或管道已断
    - 期望：消息落地为「未送达」并保留原文可复制，绝不静默丢弃或假装已发出
- [[E-114]]　两端同时回话
    - 触发：手机与桌面同时发消息给同一会话
    - 期望：按到达 daemon 的先后串行投递，每条消息记录来源设备与时间戳，不做去重合并
- [[E-116]]　空消息或超长消息
    - 触发：用户提交空内容，或超过 agent 输入上限
    - 期望：空消息拒绝提交；超长在发送前提示并让人确认截断点，不静默截断
- [[E-117]]　agent 不具备注入能力
    - 触发：后续接入的 agent 没有消息注入通道
    - 期望：「可回话」做成能力位，UI 按能力位灰掉按钮，而不是点了才报错

## 实施沉淀

<!-- notes:begin -->
- **并发回话串行化与非合并原则（E-114）**：手机与桌面端同时向同一会话发送回话时，网络到达顺序存在微小时间差。通过 `enqueueForRun` 为每个 `runId` 维护独立的内存 Promise 链，按到达先后执行写入与落库。禁止任何基于内容相似度的去重合并，每条消息独立落库并分别绑定来源设备的 `actorDeviceId` 与精确时钟戳，保证两端操作的完整因果序。
- **管道背压与 drain 等待（AC 6）**：Node.js 子进程的 `child.stdin.write` 在写入缓冲区满时返回 `false`。若不检查返回值而直接连续写入或立即返回成功，会导致数据积压在内存或在进程异常退出时丢失尾部。通过 `writeStdin` 返回值判断背压并在返回 `false` 时显式 `await waitForStdinDrain()`，确保写入完全冲刷至操作系统管道后再完成投递。
- **未送达保留原文可复制（E-113）**：当进程意外崩溃或 stdin 管道已被破坏（如 EPIPE / destroyed）时，绝不吞掉错误或假装已送达，而是生成独立 `messageId` 并将 `delivery_state` 记为 `undelivered` 落入 `run_messages` 表，完整保留用户原始输入文本，同时发布 `run.message_undelivered` 事件并抛出 `E_MESSAGE_UNDELIVERED`，确保前端既可给出精准提示，用户又可一键复制未送达内容重新发送。
- **已结束会话的 resume 判定与新运行边界（E-112）**：对于已处于终态或已退出的会话，必须先依据 Agent 适配器的 `canResume` 能力位判定：不具备 resume 能力的 Agent（如 Claude 或 Pi）直接阻断并提示用户使用重派；具备 resume 能力的 Agent（如原生 Codex）走会话恢复路径，投递结果显式标记 `isNewRun: true` 并返回新运行 ID，避免在已终态的历史记录上覆写退出码和生命周期。会话恢复本身由 M7-T5 通过 `resumeSession` 依赖注入——**未注入时这条通路并不存在，此时必须落为未送达（`resume_unavailable`）而不是回一个「已送达」加一个凭空生成的新运行 id**：没有新运行行却声称这是一次新运行，等于在数据里假装消息已发出，正踩 E-113 的红线。
- **「先写 stdin 再落库」的顺序是被逼出来的（AC 6 与 08 节事务边界）**：投递状态只有真正写过 stdin 才知道，所以顺序是「探测进程与管道 → 写 stdin → 单事务落库 → 事务返回后发事件」，而不是 08 节的「先落库再做副作用」。代价是写成功而落库失败时消息进了 agent 却没留痕；可接受的前提是写失败与非存活进程一律走未送达分支，绝不因为落库失败就回头改口说没发过。
