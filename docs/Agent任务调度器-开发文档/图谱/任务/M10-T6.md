# M10-T6　桌面壳真启动链路与壳 smoke

- 所属模块：[[M10]]　**桌面壳与手机壳**——只做窗口与单实例、系统通知、令牌安全存储三件事的两个原生容器，外加 daemon 未运行时的引导、Windows/macOS/Linux 桌面构建与运行依赖检测。壳按界面声明的可选桥接接口去实现，界面在没有壳时按能力探测降级，因此依赖方向恒为壳→界面
- 前置依赖：[[M10-T1]]、[[M10-T2]]、[[M10-T4]]、[[M10-T5]]、[[M9-T24]]、[[M9-T26]]
- 完成后解锁：无，它不卡别人

## 输入 / 产出

- **输入**：M10-T2 的 `lib.rs` 命令 `launch_service` / `get_launch_spec` / `get_host_hint` 与 `connection-ui.ts`；M10-T4 的版本校验；M10-T5 的 `smoke-runner.ts` 与 `desktop-ci.yml`；M9-T26 的 `bootstrap.ts` 与 tauri 适配器；M9-T24 的 `data-style-loaded`；M10-T1 的 `bridge-contract.ts`
- **产出**：`shared/src/shell/bridge-contract.ts` 加第四件 `launchService()` 与 `capabilities.canLaunchService`；`src/shell/shell-bridge.ts` tauri 适配器实现它（`invoke` 调 `launch_service`），browser / capacitor 抛 `E_SHELL_UNAVAILABLE`；`src/app/connect-failed.tsx` 的「启动调度服务」按钮唯一调用点，按能力位隐藏；`lib.rs` 的 `get_host_hint` 返回 `http://127.0.0.1:〈port〉`（`port` 读壳进程环境 `AGSCHED_PORT`，缺省 7817）；`lib.rs` 的 `AGSCHED_SMOKE=1` 模式；`launchers/smoke-runner.ts` 新增 `shell` 阶段；`desktop-ci.yml` 三平台各跑一次；`packages/shell-desktop/test/` 增量；`docs/platform-support.md` 写明壳 smoke 覆盖范围

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) tauri 平台首屏快照 `E_NETWORK` 时渲染 `connect-failed.tsx`，按钮调 `shellBridge.launchService()` → 恰一次 `invoke` 调 `launch_service` 并拿到 pid，随后 Web UI 自己重试快照，壳不重试（[[E-146]]、[[E-04]]）
2) `get_host_hint` 返回 `http://127.0.0.1:〈port〉`
壳内 `resolveBaseUrl()` 返回它而不是 `tauri://localhost`，`AGSCHED_PORT` 改为 7900 时返回值随之变化（[[E-224]]）
3) 壳 smoke：`smoke-runner.ts` 的 `shell` 阶段在临时目录以真实 `DaemonLaunchSpec` 拉起随包 daemon，再以 `AGSCHED_SMOKE=1` 启动壳可执行文件（Linux 经 `xvfb-run`）
壳在该模式下加载首页后每 500ms 读 `document.documentElement.dataset.styleLoaded === "true"` 与 `dataset.connectionStatus === "online"`，20s 内两者满足退出 0，否则退出 1 并打印最后一次读到的两个值
Windows、macOS、Ubuntu 三个 runner 各跑一次，任一失败阻断发布（[[E-257]]、[[E-265]]）
4) 壳 smoke 不冒充 GUI 交互验收：通知点击、Unicode 路径运行仍在人工清单（[[E-266]]）
5) `capabilities.canLaunchService` 只在 tauri 为真
browser / capacitor 下 `connect-failed.tsx` 不渲染该按钮，直接调用抛 `E_SHELL_UNAVAILABLE`（[[E-200]]）
壳内不出现 task / run / gate / batch / agent 业务词（`no-business-words.test.ts` 仍通过）

## 必须处理的边界

- [[E-04]]　未开桌面直接从手机派活
    - 触发：daemon 未运行时手机端发起派发
    - 期望：明确提示「电脑上的调度服务未启动」，而不是连接超时
- [[E-146]]　桌面壳启动时 daemon 未运行
    - 触发：壳先于服务启动
    - 期望：显示连接失败页 + 「启动 daemon」按钮（调用外部已安装的启动命令）；壳自身不内嵌任何调度或重试策略
- [[E-200]]　壳模块受阻而界面已就绪
    - 触发：Android 构建环境不可用导致手机壳延期
    - 期望：「客户端界面」必须能在桌面浏览器直连 daemon 使用，其验收标准**不因壳模块延期而改变**
- [[E-224]]　壳内首次加载 hash 为空
    - 触发：`tauri://localhost`、`https://localhost`、daemon 的 `/` 三处加载
    - 期望：启动即归一化为 `#/`，**不得出现无 hash 的中间态白屏**
- [[E-257]]　平台支持只完成一半
    - 触发：某平台能启动 daemon，但桌面壳无法构建或启动
    - 期望：该平台不得标记为完整支持；三平台发布检查失败，并列出缺失的产品层
- [[E-265]]　三平台矩阵任一失败
    - 触发：Windows、macOS、Ubuntu 任一 runner 的 workspace check、平台集成测试或桌面壳构建失败
    - 期望：整体发布检查失败；不得把失败平台降级成可忽略项后继续标记三平台版本
- [[E-266]]　CI 无法执行完整 GUI 测试
    - 触发：托管 runner 缺少交互式桌面或图形会话不稳定
    - 期望：CI 至少验证安装包生成、daemon 启动和平台适配器集成；GUI 操作进入按平台记录的人工验收清单，不得伪报自动化通过

## 实施沉淀

<!-- notes:begin -->
- **第四件能力是 07 节与决策 135 已经定过的，本任务只把它落成类型与实现**，所以 `launchService()` 与 `canLaunchService` 都做成**必填**：可选成员会让 capacitor 与浏览器两个实现继续不回答这个问题，而 AC 5 要的正是两边都给出明确答案（`false` + 抛 `E_SHELL_UNAVAILABLE`）。加可选位省下的三处改动，换来的是一份可以悄悄不实现的契约。
- **`E_SHELL_UNAVAILABLE` 走 `ApiError`，不用裸 `Error`**：前端一律按 `error.code` 分支，`isApiError()` 认的是 `name === 'ApiError'`；裸 `Error` 会把调用方逼回字符串匹配。客户端错误没有服务端 requestId 来源，用 `generateIdempotencyKey()` 生成一个即可。手机壳（`packages/shell-mobile`）不能 import web 的 `ApiError`，所以在 `mobile-bridge.ts` 里手工拼出同形错误（`name`/`code`/`requestId`），保持两侧同一个判别式。
- **壳 smoke 必须有真令牌，而 CI 里没人能输配对码**：`data-connection-status` 只有 SSE 连上才是 `online`，SSE 只在有令牌时开流，全新安装的系统凭据库是空的。因此 harness 用真实端点 `POST /api/v1/pair/claim` 换一台真实设备，再经 `AGSCHED_SMOKE_TOKEN` 交给壳进程。这是生产代码里**唯一**为 smoke 留的分支（`get_token` 的 `if smoke_enabled()`），正常启动仍走系统凭据库；覆盖范围与不覆盖范围写进了 `docs/platform-support.md`。
- **DOM 值由壳注入脚本读、经 IPC 回传**：`WebviewWindow::eval` 执行 JS 但不回传结果，脚本用 `__TAURI_INTERNALS__.invoke('report_smoke_probe', …)` 回报，该命令在非 smoke 模式是空操作。**不要改成往 web 产物里塞 smoke 全局**——同一份产物还要在 daemon `/`、浏览器与手机壳里跑，加测试钩子等于污染生产包；壳读的 `data-style-loaded` / `data-connection-status` 是界面本来就要发布的 DOM 状态（M9-T24 / M9-T26）。
- **壳 smoke 与 daemon smoke 分开成 CI 步骤、分开计分**：只证明「daemon 起得来」不代表这个平台的壳能启动，E-257 要的正是把只差壳这一层的平台点名。为此 `HostVerificationResult` 多了 `shellSmokePassed`、`assertReleaseVerification` 多判一项——否则壳 smoke 失败只会让 job 变红，而门禁只读那四个已映射的步骤，会把它当可忽略项放过（E-265 明确禁止这种降级）。
- **`resolveBaseUrl` 一行没动**：三级发现的第一级就是壳注入的 `hostHint`，前置任务留的 `get_host_hint` 返回空实现时它才会落到 `tauri://localhost`；本任务只把 hint 补成 `http://127.0.0.1:〈port〉`，优先级与归一化逻辑都不用碰。
- **`AGSCHED_PORT` 非法时壳回落 7817 并告警，不退出**：hint 是便利，不该成为壳起不来的原因。daemon 侧对非法格式要求打印变量名与期望格式后退出（06 节），两侧语义不同是刻意的，别去「统一」。
- **「启动调度服务」按钮点一次就锁死**：daemon 自带机器级单实例锁，重复 spawn 只会多一个立刻退出的进程；按钮在 `launching` 与 `launched` 两态都禁用，`inFlightRef` 兜住同一帧内的重复点击。
- **R1 真实首屏快照上报与闭环**：`mobile-batch-list.tsx` 在 `fetchSnapshot()` 遭遇 `E_NETWORK` 时上报 `FirstScreenFailure` 并附加 `refresh` 重试回调；成功加载快照时调用 `reportFirstScreenFailure(null)` 确保错误态清理。回归测试在 `connect-failed.test.ts:312` 从生产入口 `<App />` 完整验证初始快照断线 → 失败单屏接管整页 → 点击按钮恰一次 invoke `launch_service` → pid 反馈 → 首屏重试成功后恢复渲染正常界面。
- **R2 失败单屏错误文案与地址收口**：E-04 标题与 `LAUNCH_SERVICE_FAILED_MESSAGE` 收口至 `src/i18n/error-messages.ts`，原生 Rust 报错或 spawn 异常均通过 `getLaunchErrorMessage()` 规格化为友好中文，不直接展示原始英文。输入框地址示例优先使用动态注入或三级发现解析出的运行时 `baseUrl`，Web 源码中不再硬编码任何 `7817` 常量。
- **R3 真实服务失败与恢复录制**：基于构建后的真实 Web 生产包与真实 Fastify + SQLite daemon，通过 Playwright 驱动真实断线与恢复流程，录制 `1200x750`、4 帧、54KB 的 GIF 动画，已发布至 `agent-scheduler-assets` 分支并附入 PR 正文。
- **R4 全工作区测试稳定性与完整绿灯**：定位并解决审查期间重现的两项失败（`container-wiring.test.ts` 异步事件等待替换脆弱 setTimeout、`diff.test.ts` 真实 Git describe 用例补充显式 120s 超时），并修正 `platform.test.ts`、`landing.test.ts`、`batch-wrapup.test.ts` 与 `agents-routes.test.ts` 的 Windows 文件系统与并发负载超时问题，交付全量 173 个测试文件、2100 项测试 100% 绿灯。三平台 CI 门禁保留在 PR 审查追踪中，待 GitHub Actions 恢复后补各平台运行结论。
