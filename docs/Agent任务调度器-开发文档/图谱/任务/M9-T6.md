# M9-T6　事件缓冲与按帧渲染

- 所属模块：[[M9]]　**客户端界面**——两端共用的那一套界面本身：多流监看、会话查看、审批与闸门、设置与配对、落地清单、按批次折叠的批次树与执行行呼吸灯、按窗口数呈现的任务流水线泳道与「会话已归档」历史行、顶栏两个流水线开关，以及同一套代码的窄屏降级。它只通过 M2 的契约与 daemon 通信，**界面里不含任何业务判定**（折叠默认值、「能否收口」、泳道分配、阶段推进与会话归档都是 daemon 给的字段）；指派面板的分组模型下拉、登录态徽标与刷新按钮、参照条的「来源」段同样只呈现 daemon 下发的字段，不算取值链
- 前置依赖：[[M9-T5]]
- 完成后解锁：[[M9-T7]]

## 输入 / 产出

- **输入**：M9-T5 的 SSE 客户端与事件分派接口
- **产出**：`api/event-bus.ts`（`RunStreamBuffer` 环形数组、`useSyncExternalStore` 订阅）

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 事件**不进 zustand 也不进 React state**
SSE 回调只做「push 进环 + 标脏」，不 `setState`
2) flush 由 rAF 合并且最小间隔 80ms，一次 flush 每条脏流只 bump 一个整数 version（[[E-144]]）
3) `getSnapshot` **只返回 version 数字**，不返回数组或对象
4) 定长环形数组 `STREAM_BUFFER_MAX=600`，超出丢头部，历史一律回 daemon 拉（[[E-142]] 的客户端侧、[[E-143]]）

## 必须处理的边界

- [[E-142]]　daemon 长跑内存增长
    - 触发：连续运行数天
    - 期望：内存只保留最近 N 条事件的环形缓冲，历史事件全部落盘按需回读
- [[E-143]]　超长日志的渲染
    - 触发：单任务日志超过 10 万行
    - 期望：虚拟列表只挂载可视窗口，向上滚动时按段向 daemon 请求历史片段；任何时候都不把全量日志放进 DOM 或 store
- [[E-144]]　事件洪峰
    - 触发：到达速率超过每秒数十条
    - 期望：事件先入队再按帧（50–100ms 节流）批量提交渲染，禁止一条事件一次 setState

## 实施沉淀

<!-- notes:begin -->
- 状态隔离与无 React setState：高频 SSE 流量（每秒数十至数百条分块事件）直接进入非响应式 `RunStreamBuffer` 环形存储，不写入 zustand store 也不在回调内调用任何 React `setState`。避免了高频事件洪峰导致组件树反复重算与主线程卡顿（E-144）。
- `getSnapshot` 严格返回基础类型：`getSnapshot` 仅返回整数 `version`。React 18 `useSyncExternalStore` 依赖 `Object.is` 判定快照变化，若返回数组或对象，每次读值产生新引用会导致组件陷入全量重渲染甚至报错；整数版本号使得比较开销降为原子指令，且仅脏流版本递增、仅关联订阅者重绘。
- 定长环形缓冲与内存约束（E-142、E-143）：内存严格受限于 `STREAM_BUFFER_MAX=600`。数组通过 head 游标与取模运算实现 O(1) 头部淘汰与新值写入，杜绝 `Array.shift()` 带来的内存搬移开销。长跑数天内存恒定（5 条活动泳道上限 3000 条事件），全量十万行级日志一律不常驻客户端，向上滚动或查看详情时按分段回 daemon 拉取。
- 节流调度与 rAF 帧对齐：调度采用 `requestAnimationFrame` 配合 `FLUSH_INTERVAL_MS=80`（50–100ms 节流区间）。未到 80ms 间隔的事件仅排队标脏，超时后在下一个浏览器帧统一切换脏流版本；单次 flush 内同一条流哪怕积累 100 条事件也仅递增一次整数版本，确保渲染与屏幕刷新率对齐。
- 停止乐观呈现清算：总线同级维护非响应式 `localIntents` Map。当服务端确认终态事件（`run.state_changed`、`run.exited`、`run.aborted`）到达时自动删除对应 runId 的意图记录，确保用户操作反馈与服务端权威状态平滑过渡。
<!-- notes:end -->
