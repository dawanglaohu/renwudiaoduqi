# M9-T6　事件缓冲与按帧渲染

- 所属模块：[[M9]]　**客户端界面**——两端共用的那一套界面本身：多流监看、会话查看、审批与闸门、设置与配对、落地清单、按批次折叠的批次树与执行行呼吸灯、按窗口数呈现的任务流水线泳道与「会话已归档」历史行、顶栏两个流水线开关，以及同一套代码的窄屏降级。它只通过 M2 的契约与 daemon 通信，**界面里不含任何业务判定**（折叠默认值、「能否收口」、泳道分配、阶段推进与会话归档都是 daemon 给的字段）
- 前置依赖：[[M9-T5]]
- 完成后解锁：[[M9-T7]]

## 输入 / 产出

- **输入**：M9-T5 的 event-bus
- **产出**：`RunStreamBuffer` 环形数组、`useSyncExternalStore` 订阅

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 事件**不进 zustand 也不进 React state**
SSE 回调只做「push 进环 + 标脏」，不 `setState`
2) flush 由 rAF 合并且最小间隔 80ms，一次 flush 每条脏流只 bump 一个整数 version（[[E-144]]）
3) `getSnapshot` **只返回 version 数字**，不返回数组或对象
4) 定长环形数组 `STREAM_BUFFER_MAX=600`，超出丢头部，历史一律回 daemon 拉（[[E-142]] 的客户端侧、[[E-143]]）

## 必须处理的边界

- [[E-142]]　daemon 长跑内存增长
    - 触发：连续运行数天
    - 期望：内存只保留最近 N 条事件的环形缓冲，历史事件全部落盘按需回读
- [[E-143]]　超长日志的渲染
    - 触发：单任务日志超过 10 万行
    - 期望：虚拟列表只挂载可视窗口，向上滚动时按段向 daemon 请求历史片段；任何时候都不把全量日志放进 DOM 或 store
- [[E-144]]　事件洪峰
    - 触发：到达速率超过每秒数十条
    - 期望：事件先入队再按帧（50–100ms 节流）批量提交渲染，禁止一条事件一次 setState
