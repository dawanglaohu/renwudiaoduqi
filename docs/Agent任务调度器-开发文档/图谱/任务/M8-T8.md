# M8-T8　流水线槽位、补位与阶段设置

- 所属模块：[[M8]]　**派发调度**——决定什么时候把哪个任务、用哪个 agent 与哪个模型、以什么权限派出去，并按批次、并行窗口、每 agent 并发与路径冲突限流，在三个闸门处停或放行、失败或重派时重新入队；判定本批分支是否都进了 HEAD、触发收口运行、按收口报告派修复运行与管理收口轮次也归它；泳道（窗口槽位）分配、任务终态后的补位、查 bug 与收口模式两个开关的持久化同样归它——泳道分配是它算出的派生数据。凡涉及顺序、名额、放行、重派的都归它；任务指派写进派发快照、阶段取值链（任务指派 → 阶段覆盖 → agent 默认）与收口指派设置也归它——它是唯一决定「这一阶段用谁跑」的地方，M7 只消费结果

## 必须处理的边界

- [[E-283]]　收口运行的名额与权限
    - 触发：收口运行被派出
    - 期望：计入并行窗口与该 agent 并发上限（占 1 个名额）；权限档恒 `workspaceWrite`，不给 `unrestricted`；同一批次同时只有一条收口运行
- [[E-302]]　任务终态时会话进程还在
    - 触发：任务进入 landed／failed／aborted／interrupted，而该任务的实施／审查／查 bug 会话进程仍存活
    - 期望：结束并归档该任务全部会话：进程走 `platform.killTree` 两阶段（E-119），每条运行写 `session_archived_at`，`vendor_session_ref` 从此只作只读引用；同一泳道的下一个任务一律新建会话，**绝不把已归档会话拿来跑新任务**
- [[E-303]]　泳道补位时复用了旧会话引用
    - 触发：新建运行的 `vendor_session_ref`（或续接目标会话）等于其他任务任一运行的引用
    - 期望：拒绝派发并返回 `E_SESSION_ARCHIVED`，`details` 带冲突的 taskKey 与 runId；泳道保持空闲、下一次 tick 重试；service 层校验与 arch 测试各挡一道，不靠人 review
- [[E-307]]　查 bug 修了东西
    - 触发：查 bug 报告 FIXED 段非空且自审查 pass 以来工作区 diff 非空
    - 期望：`rework_count<2`：先 `+1`，再通知**该任务的同一审查会话**再审一轮（续接规则同 E-304），提示词头部「第 N 轮，只核查 bug 阶段的修改：〈FIXED 条目原文〉」；`rework_count` 已达 2：不派再审、不 +1，任务转 `awaiting_human`，闸门 comment 写 `bughunt_fixed_over_limit`，审批卡列 FIXED 条目与 diff 摘要；FIXED 非空且 NOT_FIXED 含 S1/S2：直接转人、不先再审；运行轨上画成查 bug 节点回到审查节点的回环，轮次沿用同一 `rework_count`；不派第二个审查会话、不跳过再审直接落地
- [[E-309]]　窗口数调小
    - 触发：用户把并行窗口数从 N 调到 M＜N，而在跑的流水线数 ＞M
    - 期望：不杀任何在跑流水线，只停止补位；`lanes` 仍按实际占用返回并标 `overLimit`，空出的泳道不再补，直到占用 ≤M；调整立即生效、不需重启批次；被移除的空泳道其历史行随之消失、不迁移
- [[E-310]]　窗口数调大
    - 触发：用户把并行窗口数从 N 调到 M＞N 且有可放行任务
    - 期望：下一次 tick 立即补位到 M 条，新泳道 laneNo 为 N+1…M；无可放行任务时新泳道显示空闲与队列下一个（E-319）；新增泳道无历史行
- [[E-311]]　一个任务的多个阶段同时在跑
    - 触发：同一任务的实施运行已退出、审查运行在跑，或查 bug 运行在跑
    - 期望：全部阶段共用**同一个槽位**：槽位按任务计数，不按运行计数；审查与查 bug 运行不额外占窗口，但各占该 agent 并发上限 1 名额（M8-T1 的计数不变）；`lanes[].currentRunId` 指向当前阶段的运行
- [[E-312]]　收口模式为手动
    - 触发：`pipeline.wrapupMode='manual'` 且本批全部 landed 并进 HEAD
    - 期望：tick 第 2 步不调 `triggerWrapup`；批次留在 `running`（分支未全进 HEAD 时是 `awaiting_landing`），`canWrapup=true` 且标题追加「可收口」暖色；只有 `POST /batches/:id/wrapup` 能进 `wrapping`；下一批仍等本批 `done`（E-281）；切回自动后下一次 tick 立即按 E-283 自动派
- [[E-317]]　泳道分配的算法归属
    - 触发：前端拿到快照与事件要画泳道
    - 期望：`lanes[]` 由 daemon 的纯函数算出，随 `GET /snapshot` 与 `lane.assigned`／`lane.released` 事件下发；前端只按 `laneNo` 排列，不算槽位、不算下一个任务、不推断阶段；字段缺失显示「—」
- [[E-318]]　流水线设置存储缺行或损坏
    - 触发：`settings` 表无 key=pipeline 行，或 `value_json` 非法／含未知值
    - 期望：缺行返回内置默认 `{bughunt: 0, wrapupMode: 'auto'}` 不插行；非法回落默认并 warn，不退出、不覆盖坏值直到下一次 PATCH；PATCH 两字段整体写入，缺字段或值非法返回 `E_VALIDATION`；写成功发 `settings.pipeline_changed` 让另一端刷新
- [[E-319]]　空闲泳道
    - 触发：泳道无任务
    - 期望：显示「空闲 · 队列下一个是 〈ID〉（等 〈前置〉 落地）」，〈ID〉与前置来自 daemon 的 `nextTaskId` 与其未落地前置；无任何未派任务时显示「空闲 · 本批已全部派出」；不画假的阶段链；手机档运行条写「泳道 k/N · 空闲」，拇指栏停止键置灰但保持原位
- [[E-326]]　任务停在人工闸门期间的泳道与会话
    - 触发：运行以任何原因进入 `awaiting_human`（pass 等确认、E-55 超限、审查未完成、doc-issue、查 bug 转人等），或 daemon 重启后成为 `orphaned`
    - 期望：同一事务里 `tasks.lane_no` 置 NULL、发 `lane.released{reason:'awaiting_human'}`，下一 tick 补位；该任务全部运行**不写 `session_archived_at`、不 killTree**，进程自然退出只留 `vendor_session_ref` 供恢复；路径锁仍按 E-46 到 landed 才释放；`awaiting_reply` 不释放泳道、继续占额度；人放行→landed 或人判失败→failed 才按 E-302 归档，此时不再发 `lane.released`；等待不过期、不自动放行（E-58），daemon 重启不改其状态；停靠中的任务不在甲板上，入口只有批次树「等你」行、全局未处理徽标与任务／运行详情里的审批卡
- [[E-327]]　人打回后重新入道

    - 期望：当场 decide 闸门、意见落 `rework_text`（source=human）、运行迁 `reworking`，计数照加不受 E-55 拦截；返工进入可放行集合并**排在全部新任务之前**（多个返工按打回时间先后），有空泳道当场入道（泳道号可与原先不同）再按 M7-T5 三分支投递；等泳道期间 `lanes[]` 不含它、批次树该行显示「返工排队 · 等泳道」静态点不呼吸、审批卡已关闭；入道时进程已死或 daemon 重启过则按快照能力位恢复（E-112）或新开 `origin=rework`（E-279），worktree 已清理走 E-277；批次 `paused` 时不入道并显示「批次已暂停 · 返工排队」，恢复后先于新任务入道；返工再次退出后续接同一审查会话第 N+1 轮（未归档）

## 实施沉淀

<!-- notes:begin -->
1. 泳道槽位只按任务与活跃收口计数，不按运行计数：
同一任务下的实施、审查、查 bug 阶段无论多轮如何轮转，始终共享同一个槽位编号 tasks.lane_no。严禁用 runs.state 数在跑运行来推算槽位空闲，否则审查运行与查 bug 运行时会被误判为占用额外槽位导致流水线吞吐骤降；只有人工闸门停靠（awaiting_human）与任务终态时，槽位才在同一事务中置 NULL 释放并向外发布 lane.released。
2. 调度器补位候选队列的阶段优先级与并发分配：
人工打回后处于 reworking 且 tasks.lane_no 为 NULL 的任务必须排在全部新任务之前进入并发分配（按打回时间升序）。不能在进入 allocateConcurrencySlots 之前用 slice(0, free.length) 提前裁断候选数组，否则超出槽位的新任务不会被记入 tasksDeferred，必须将所有排队任务一同传给 allocateConcurrencySlots，由其按 availableSlots 判定，使超出窗口容量的任务正常产出 window_exhausted 延后记录。
3. 泳道纯函数 deriveLanes 的确定性与空闲槽推导：
必须在函数入口对输入的任务与运行集合按 id 排序，避免因数据库查询返回的物理行顺序波动破坏快照输出的字节一致性。空闲槽位在候选可放行任务耗尽后，必须平滑降级至由于前驱依赖阻断的未派任务，并在 nextBlockedBy 中列出其未落地的依赖 taskKey，而不是直接置空，以保持前端甲板对下一步调度的可见性。
4. 流水线设置与收口模式闸门：
pipeline.wrapupMode 的变更只控制后台调度 tick 是否自动触发收口，不修改批次本体状态（批次仍留在 running，待进 HEAD 时为 awaiting_landing）。triggerWrapup 针对 auto 触发显式校验 wrapupMode，当处于 manual 时强抛 E_PIPELINE_STAGE_DISABLED{stage:'wrapup'}，但对人工显式触发（manual）恒放行，确保手动收口入口随时可用。
5. 返工投递失败后保留人工恢复入口：
启动失败或启动即退出时只把返工运行标为失败，目标实施行停到 awaiting_human、释放泳道，并以带类型化原因的 waiting 闸门卡供再次决定。原会话和返工计数保留；再次人工打回才构成新一轮决定。默认 agent 并发为 1 时，补位名额计算排除被返工取代的旧实施行，避免返工永久排队。
