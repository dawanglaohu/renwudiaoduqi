# M6-T9　会话保留策略与全文查找

- 所属模块：[[M6]]　**运行监管**——管一次运行从启动到结束的全过程：状态机（「已退出」与「已落地」分开）、收流与落盘编排、按游标分段回读与厂商会话文件的只读引用、进度信号、停滞检测、中止与 daemon 重启后的对账、回话投递；任务到达终态后结束并归档该任务全部会话（进程还在走 `killTree` 两阶段），归档后会话引用只读、不得复用，也归它。凡「这一次运行现在怎么样、它说过什么」的都归它
- 前置依赖：[[M6-T8]]、[[M1-T5]]
- 完成后解锁：无，它不卡别人

## 输入 / 产出

- **输入**：M1-T5 的删除原语
- **产出**：保留策略、`searchInRun()`、`http/routes/runs.ts` 的 `search` 与 `DELETE logs` 两个端点

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 清理**只清自己捕获的日志正文**
任务记录、三段快照、派发元信息一律保留，历史仍可回溯（[[E-105]]）
2) 全文查找按分段流式读并周期让出事件循环，硬超时 10s、结果上限 500 条
超时返回「已找到的前 N 条 + 未搜完」并允许取消（[[E-219]]）
3) 搜索按发起时刻的偏移索引末尾做快照式扫描，不追新写入，结果标注截止位置（[[E-220]]）
4) 目标正文已被清理或缺失时返回「该会话正文已清理」的明确结果，**不返回 500、不用空列表冒充无匹配**（[[E-221]]、[[E-207]]）
5) 同一任务重试或续跑时进度只展示最近一次运行，历史运行可展开，两次运行的事件不混成一条流（[[E-27]]）

## 必须处理的边界

- [[E-105]]　自动清理被触发
    - 触发：用户开启了自动清理且达到条件
    - 期望：只清理自己捕获的日志正文；任务记录、三段快照、派发元信息（谁派的、何时、结果、模型）一律保留，历史仍可回溯
- [[E-207]]　正文在产品外被删
    - 触发：用户手工删了某次运行的正文
    - 期望：M1 只报「文件缺失」这一磁盘事实，M6 把对应 events 索引标记为 orphan，会话视图显示「正文已不可用」占位，不崩不空白
- [[E-219]]　全文搜索阻塞 daemon
    - 触发：服务端扫文件搜索
    - 期望：按分段流式读并周期让出事件循环；单次搜索硬超时 10s、结果上限 500 条；超时返回「已找到的前 N 条 + 未搜完」并允许取消，**而不是失败或干等**
- [[E-220]]　边搜边写
    - 触发：搜索发起时会话仍在持续写入
    - 期望：按发起时刻的偏移索引末尾做**快照式扫描**，不追新写入，结果里标注截止位置
- [[E-221]]　搜索目标已被清理
    - 触发：该会话正文已被保留策略清掉或文件缺失
    - 期望：返回「该会话正文已清理」的明确结果，**不返回 500、不返回空列表冒充「无匹配」**
- [[E-27]]　同一任务重试或续跑
    - 触发：任务被重派
    - 期望：进度只展示最近一次运行，历史运行可展开；两次运行的事件不混成一条流

## 实施沉淀

<!-- notes:begin -->
清理与缺失必须分成两种结果。产品策略清完后在 run 目录写 `.purged`，搜索命中墓碑才抛 `E_LOG_PURGED`；目录或分段文件不在才抛 `E_LOG_FILE_MISSING`。没有墓碑、也没有文件时不能当「无匹配」返回空 `hits`，否则前端会把「正文已清理」显示成搜不到。

搜索窗口按发起时刻冻结：对每个分段取 `min(索引 byteEnd, 当时 size)`，读完这个上限就停。边搜边写时文件会继续长，但结果只报告快照内的命中，并用 `scannedUntilSeq` 标截止行。超时检查必须放在读块之后、让出事件循环之后再判；300 行以内的日志常被一次 64KiB 读完，时钟若只在块前读一次，10s 硬超时测不出来。

清理只走 run 目录里能被 `parseSegmentFileName` 解析的捕获文件（`raw.log`、`raw-N.log`、`events.ndjson`、`events-N.ndjson`）。目录内的其他文件（附件、元数据等）既不删、也不计入 `purgedBytes`。厂商会话路径在目录外，不能交给 `deleteByPath`；任务行、dispatch_snapshots、派发元信息都在 SQLite，本任务不删那些行。在途状态（starting/running/awaiting_reply/awaiting_human）拒绝 purge，避免把还在写的流截掉。

E-27 的「进度只展示最近一次」落在 `getTaskRunsSummary()`：按 `attemptNo` 降序，第一条当 latest，其余当历史。搜索与清理都带明确 `runId`，不会把两次 attempt 的事件拼成一条流。前端列表仍要按 run 订阅，这个函数只给拆分口径。
