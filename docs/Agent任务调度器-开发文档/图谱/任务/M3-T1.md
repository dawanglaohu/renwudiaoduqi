# M3-T1　docs-data.js 解析与内容指纹

- 所属模块：[[M3]]　**文档接入**——把 `docs-data.js` 变成本产品唯一的任务真相源（任务、依赖、批次、并行窗口、验收标准、边界编号、实施与审查两段提示词），并负责内容指纹、派发时快照与文档重出后的三个标记；收口提示词 `dispatchBatches` 的按任务集合匹配也归它。凡「这条数据来自文档」的都归它
- 前置依赖：[[M1-T2]]
- 完成后解锁：[[M3-T2]]

## 输入 / 产出

- **输入**：一份 unattended-run 1.1.0 实际导出的 `docs-data.js`；09 节输入协议
- **产出**：`service/docs.ts` 的唯一解析适配器、`domain/layer-of.ts`（批次分层纯函数）、`repo/documents.ts`

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 强制按 UTF-8 读取，去头尾 `JSON.parse`，不启用 JS 引擎
中文 Windows 默认编码下不乱码（[[E-16]]）
2) 校验 schemaVersion=1 与任务包的三处哈希一致
按任务 ID 排序的 id/contractHash 列表算指纹，任务行不变而范围、条款或提示词编译器变化时仍判变更，**不得使用 generated 或 mtime**（[[E-17]]）
3) 指纹相同且仅时间戳或 ready/reasons 变化时不设变更标记、不改运行状态，但仍刷新文档复核元数据（[[E-79]]）
4) 解析失败、必需字段缺失、协议或哈希不一致、文件被删时保留全部既有记录与快照，置 `is_source_readable=0` 并冻结新派发，**不清空任何数据**（[[E-82]]）
5) **批次由本产品按 `deps` 拓扑分层算出**（层号 = 最长前驱链长度，无前驱为 0，显示号 = 层号 +
1），规则与阅读器逐字一致且收敛在这一个模块内
上游日后真导出 `batchNo` 时只改这一个函数（[[E-246]]）
6) 阅读器那条窗口数 localStorage 键**不存在也不读**，本产品一律用自己的 `documents.lane_count` 设置（[[E-247]]）

## 必须处理的边界

- [[E-16]]　docs-data.js 编码读错
    - 触发：在中文 Windows 上按系统默认编码读取
    - 期望：强制按 UTF-8 读取（生成时 ensure_ascii=False）；格式为 `window.DOCS = 〈JSON 字面量〉;` 去头去尾 JSON.parse，不需 JS 引擎
- [[E-17]]　漏判或误判文档变更
    - 触发：重建仅改变时间戳，或任务行不变但范围、条款、提示词编译器已变
    - 期望：校验 schemaVersion=1 与任务包哈希一致性；对按任务 ID 排序的 id/contractHash 列表算指纹，识别任务增删和契约变化，generated 与 mtime 不作变更依据
- [[E-246]]　上游日后导出了 batchNo
    - 触发：`build_docs.py` 改了 payload
    - 期望：只改适配器里那一个分层函数，其余不动（分层规则收敛在唯一适配器模块内）
- [[E-247]]　阅读器里那条键根本不存在
    - 触发：用户从没点过窗口数按钮（最常见）
    - 期望：无可沿用，也无需任何特殊分支——本产品一律用自己的设置项
- [[E-79]]　文件变了但任务契约没变
    - 触发：id/contractHash 指纹相同，仅重建时间戳、mtime 或契约复核 ready/reasons 变化
    - 期望：不产生变更标记、不弹横幅、不改任务运行状态；成功读取时仍刷新文档复核元数据，允许已复核的同版任务解除新派发限制
- [[E-82]]　文档源不可读或任务包不可派发
    - 触发：文件被删、解析失败、缺协议字段或版本不一致；或合法任务包的 ready=false
    - 期望：源不可读时保留全部记录与快照、提示原因并冻结新派发；合法但待契约复核时仅阻止该任务派发并说明 reasons，不清空数据、不视为代码验收失败

## 实施沉淀

<!-- notes:begin -->
适配器以 UTF-8 读取 `docs-data.js`，剥离可选 BOM 和固定的 `window.DOCS = JSON;` 外壳后调用 `JSON.parse`，不执行项目 JavaScript。任务 ID 必须非空且唯一；标题、模块、依赖数组和验收标准必须具备协议要求的类型；dispatch、contract 与 readiness 三处非空契约哈希必须相等；`ready` 必须是布尔值，`reasons` 必须是字符串数组。`effectivePaths` 沿用 unattended-run 1.1.0 的规则：只接受无首尾空白的仓库相对路径，拒绝盘符或根绝对路径、反斜杠、空段、`.`/`..` 段以及通配符。协议错误统一产生 `E_DOC_SOURCE_UNREADABLE`。

文档指纹的 domain 函数按任务 ID 的代码单元顺序排序 `[id, contractHash]`，再序列化成固定 JSON；`generated`、mtime 与 `ready/reasons` 不进入该载荷。SHA-256 实现在 service 层，并作为摘要函数传给 domain，因此纯逻辑层不依赖 Node 运行时模块。固定规范串和已知摘要测试共同约束跨平台结果。

documents repo 只收发字段名与数据库列一致的 snake_case `DocumentRow`；service 负责构造 Row 以及映射 camelCase `DocumentRecord`。repo 工厂预编译 SQL，所有 `prepare`、`run`、`get`、`all` 异常都经 `toDatabaseError` 转成带原始 `cause` 的 `AppError`。非法 `lane_count` 在执行 SQL 前返回 `E_VALIDATION`。

既有文档在文件丢失、JSON 损坏或协议校验失败时只把 `is_source_readable` 置为 0 并刷新 `last_seen_at`；任务、派发快照和运行状态不被删除或覆盖。源恢复后成功导入会恢复可读标记。同一 `[id, contractHash]` 指纹下的重建时间或 `ready/reasons` 变化只刷新本次解析结果与文档发现时间，`hasChanged` 保持 false；`lane_count` 始终来自产品自己的 documents 记录。
<!-- notes:end -->
