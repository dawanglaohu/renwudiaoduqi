## 实施沉淀

<!-- notes:begin -->
1. **服务端态共享资源缓存（07 节前端架构 / AC 1）**：
   - 遵照 07 节 267 行规范，以最小开销原生 Map 实现 `read(key, fetcher)`、`invalidate(prefix)` 和 `refetchAll()`，不引入额外三方依赖。
   - 严格禁止暴露 `set/put/patch` 接口，杜绝前端乐观写污染服务端权威；禁止客户端轮询与基于时间戳的 stale 窗口，状态同步完全收拢为由 SSE 事件和连接恢复驱动。
   - 对相同 key 的并发读取复用同一在途 Promise，并将传入的 fetcher 登记/覆盖为该 key 的最新重拉入口。

2. **在途失效与 E-333 自动再拉机制（AC 1, AC 2, E-333）**：
   - 当某个 key 在请求在途期间收到失效事件（如 `lane.released`、`lane.assigned` 或 `settings.pipeline_changed`），标记 `invalidatedWhileInFlight = true`。
   - 旧响应到达时，若检测到在途期间被失效，**必须自动使用最新登记的 fetcher 再次拉取**，等待该次 `read()` 的调用方直接 resolve 为重新拉取后的最新权威值。
   - 在旧响应到达前，连续的失效事件合并只发一次在途请求；`lane.assigned` 同时失效 `lanes` 与 `runs` 时，两者的 fetcher 各自独立发起请求，互不干扰。

3. **事件权威与双编辑器写入保护（AC 2, AC 3, E-157, E-318, E-356）**：
   - 流水线开关及设置页（顶栏与 `#/settings/pipeline`）共用同一个全局单例 `sharedPipelineSource` 与底层 `resource-cache`，所有编辑器共享相同的内存缓存与 `pendingPatch` 写入锁，彻底杜绝了双编辑器并发提交不同四键配置导致相互覆盖的问题。
   - **防迟到 GET 覆盖事件权威值**：无论是收到内联数据的完整事件，还是截断的设置事件，均立即递增 `sourceVersion`。在事件之前已发出的迟到 GET 响应到达时因版本过期而被安全丢弃，绝不能覆盖回流事件的权威值。
   - **生产恢复入口与注销零残留**：通过真实 `registerResyncHandler` 和 `sseClient.onClearBuffer` 注册恢复回调。当最后一个订阅者离开时，事件总线订阅（unsub）、连接恢复监听、SSE 重放清空监听以及底层 `resource-cache` 的 key 登记与数据缓存（`unregister`）全部彻底注销并清除，杜绝长连接监听与内存泄漏。
   - 恢复补拉使用 `refetchAll()` 调用所有已登记资源的 fetcher。完整事件后的 GET 结果若与事件四键不一致，则使缓存失效并保留事件值；已注销的旧请求返回后也不得重新登记或写回缓存。

4. **单测环境隔离与真实浏览器验收（AC 4, AC 5）**：
   - 在 `pipeline-toggles.test.tsx` 中，确保受控并发测试在第二次 fetcher 调用时正确 resolve，并在所有挂载用例结束时显式执行 `await act(async () => { root.unmount(); })`，彻底释放全局监听。
   - 在真实无 mock、无路由拦截的 Fastify daemon 和真实 Chromium 浏览器中，完成了首次配对、设置 GET/PATCH、SSE 回流、顶栏与设置页实时同步以及样式 token（`--page`、Public Sans 字体）生效的全流程验证，录制标准动态 GIF 并附入 PR。
