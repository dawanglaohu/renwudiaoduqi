# M8-T7　收口修复派发、跨批语义与人工撤回

- 所属模块：[[M8]]　**派发调度**——决定什么时候把哪个任务、用哪个 agent 与哪个模型、以什么权限派出去，并按批次、并行窗口、每 agent 并发与路径冲突限流，在三个闸门处停或放行、失败或重派时重新入队；判定本批分支是否都进了 HEAD、触发收口运行、按收口报告派修复运行与管理收口轮次也归它。凡涉及顺序、名额、放行、重派的都归它
- 前置依赖：[[M8-T6]]、[[M7-T5]]
- 完成后解锁：无，它不卡别人

## 输入 / 产出

- **输入**：M8-T6 的有效裁定与开放项；M7-T5 的返工提示词组装；M8-T2 的冲突判定
- **产出**：`service/wrapup.ts` 的修复派发段、`domain/task-state.ts` 的 `origin` 分支与 `deriveTaskInHead()`、`http/routes/tasks.ts` 的 `recall` 端点、`domain/path-clash.ts` 的同收口串行规则、shared 的 `TaskDto.inHead` / `crossBatchFix`

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 有效裁定 open 时按 `planWrapupFixes` 分组，每个任务派一次修复运行：`origin='wrapup-fix'`、`spawned_by_run_id`=收口运行、`batch_id`=触发批次、`attempt_no+1`、`rework_count=0`、`workspaceWrite`、复用收口 worktree（`reuse`），agent/model/effort 取该任务最近实施运行快照，agent 不可用则该组不派并计入 unassigned
提示词 = R 条目原文 + 返工规则段（[[E-275]]）
2) 同一收口派出的修复运行互相串行（`queued_reason` 以 `wrapup-fix-serial:` 开头），与在途任务路径冲突照 [[E-46]] 排队
修复运行走正常审查，代码中不存在按 origin 跳过审查的分支（[[E-280]]、决策 70）
3) 本轮修复运行全部 landed 且收口分支 `is_in_head=1` 且轮次 < 2 → tick 触发第 2 轮
第 2 轮仍 open、或开放项全部无主 → `needs_attention` 不派第 3 轮（[[E-276]]、[[E-290]]）
4) 跨批：修复运行归触发批次、任务行归原批次
已 `done` 的批次不因跨批修复重触发收口、`done` 不回退
批次计数按最近一次非修复运行，任务行标跨批修复（[[E-275]]）
5) `POST /tasks/:taskId/recall` comment 必填，起 `origin='wrapup-fix'`、`spawned_by_run_id` 为空的修复运行走正常审查
该任务已有在途修复/返工运行或本批收口运行在跑 → `E_FIX_RUN_IN_FLIGHT`
不计入 [[E-55]] 计数
每任务同时只允许一条在途修复运行（[[E-293]]、[[E-300]]）
6) `TaskDto.inHead` 三态由 `deriveTaskInHead()` 算出（[[E-298]] 的数据侧）

## 必须处理的边界

- [[E-275]]　收口发现跨批问题
    - 触发：BUGS/NOT_FIXED 条目「涉及」前置批次的任务
    - 期望：给该任务派修复运行（`origin=wrapup-fix`、attempt_no+1、归触发批次），任务原 landed 记录不改；已 done 的前置批次不重触发收口、done 不回退；前置批次「已落地 x/n」按最近一次非修复运行计，任务行标「跨批修复」并呼吸
- [[E-276]]　第 2 轮收口仍 open
    - 触发：自动轮次达上限（2）时有效裁定仍为 open
    - 期望：批次 `needs_attention`，不派第 3 轮修复运行、不自动再收口；开批次级收口闸门等人
- [[E-280]]　修复运行与在途任务抢路径
    - 触发：修复运行的有效路径与同批在途任务有交集，或同一收口派出多条修复运行
    - 期望：前者按 M8-T2 排队等对方 landed；同一收口运行派出的修复运行互相冲突（共用收口工作区），`queued_reason=wrapup-fix-serial:〈runId〉` 逐个跑；不为修复运行新建 worktree
- [[E-290]]　TESTS 失败项无「涉及 〈任务ID〉」
    - 触发：收口报告的测试失败行没写任务号，或任务 ID 不在文档里
    - 期望：进 unassigned，有效裁定为 open；有其他可派条目照派、第 2 轮复跑兜底；全部开放项无主才 `needs_attention`（可派修复条目为零）；不猜归属、不去重
- [[E-293]]　人工撤回已自动 landed 的任务
    - 触发：落地闸门自动时人在收口前发现审查误判
    - 期望：`POST /tasks/:taskId/recall` 附言必填，起一次修复运行（`origin=wrapup-fix`、spawned_by 为空、在原 worktree 与分支上 attempt_no+1）走正常审查；该任务已有在途修复/返工运行或本批收口运行在跑时返回 409；不计入 E-55 自动返工上限；手机端不放此入口
- [[E-298]]　任务行的「进 HEAD」标记
    - 触发：任务已验收、未验收或从未派发
    - 期望：三态：true「进 HEAD」、false「未进 HEAD」（title 显示 method）、null「—」；同色不用色相；前端只读 `TaskDto.inHead`，不由分支名或运行状态推断
- [[E-300]]　同一任务被重复判定要修
    - 触发：两轮收口或两个批次的收口同时给同一任务开修复条目，或撤回撞上在途修复
    - 期望：每任务同时只允许一条在途修复运行；后到的合并进落地清单提示而不再派；重复撤回返回 409
- [[E-46]]　同批任务抢同一批文件
    - 触发：同批内两个任务的 `taskPaths` 有交集
    - 期望：后者排队，等前者到达「已落地」（不是「已退出」）才起；worktree 隔离不作为放行理由
- [[E-55]]　全自动下审查反复判 rework
    - 触发：审查连续不通过
    - 期望：重试上限默认 2 次，超限转「待人确认」，不无限自动改；回灌、恢复后回灌、新开返工运行三种投递方式计入同一个计数
