## 实施沉淀

<!-- notes:begin -->
- `attempt_no` 是运行历史序号，不能由记录数推导；历史允许跳号。在重跑写事务内读取本任务最大值并加一，保留数据库唯一约束。
- 唯一约束异常只表明写入冲突。只有同幂等键且任务、种类、父运行及冻结载荷相符的记录可以作为成功结果；任意活跃实施运行不能替代查 bug 子运行。
- `runs.lane_no` 保留历史位置，失败释放后的实际占用以任务泳道为准。查 bug 重跑以 `queued`、空泳道入队，由现有 scheduler-tick 重新分配空槽；其父实施运行停在审查阶段，不占额外进程名额。每次准入读取当前运行状态，避免同轮排队记录互相阻塞或超过并发上限。
- 插入查 bug、恢复父运行、清除任务人工状态和替代 `bughunt_failed` 闸门必须在同一事务提交。事务回滚时保留原失败上下文及可处理闸门；再次启动或执行失败仍由既有查 bug 终结路径生成失败闸门，不增加返工次数。
- HTTP 重跑只提交一次写事务，提交后通知已有调度 job；泳道准入和进程启动由原生产路径完成。出队调用必须接住启动 Promise 的拒绝，不能让已落定失败闸门的异常继续成为未处理拒绝。测试使用真实数据库与容器，仅通过容器替换进程等外部依赖。
- 最终验收分别记录完整检查、生命周期集成与 Batch 14 浏览器结果。Windows 本机实例锁权限阻止服务启动时保留失败证据；Linux 浏览器证据不代替 Windows、macOS、Ubuntu 发布矩阵，任一平台失败仍阻断三平台发布。
