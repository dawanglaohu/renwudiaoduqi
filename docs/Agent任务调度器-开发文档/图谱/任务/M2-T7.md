## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) `50-routes.ts` 里不再存在兜底注册循环
arch 测试断言「实际注册集合 === `ROUTES`」且没有任何两条路由共用同一个 handler 函数对象（[[E-215]]、[[E-216]]）
2) `POST /documents/:docId/refresh` 重读 `docs-data.js`：指纹不变 → `{changed:false, flags}` 且不发事件
任务行 accept 变化 → `changed:true`、`flags.hasAcceptChanged:true`、发 `system.docs_changed`
文件不可读 → `is_source_readable=0`、`409 E_DOC_SOURCE_UNREADABLE`，已有记录不删（[[E-17]]、[[E-19]]、[[E-82]]）
3) `GET /documents/:docId/tasks?batchId&state&cursor&limit`：`state` 值域 = 13 个运行状态 + `never_dispatched`，其他值 `E_VALIDATION`
筛选在 SQL 里 `LEFT JOIN` 最新一次 run 实现、`manual_state` 优先（09 节派生规则）
游标分页 `limit` 默认 50 上限 200，`nextCursor` 到底为 `null`，不在前端内存过滤
4) `GET /documents/:docId/batches` 返回 `BatchDto[]`（含 `canWrapup` / `notInHeadCount`）按 `batchNo` 升序
不存在的 `docId` → `404 E_NOT_FOUND`
5) 三条路由无令牌 `401` 走同一错误信封，集成测试真起 Fastify 逐条断言（[[E-08]]）

## 必须处理的边界

- [[E-08]]　daemon 被隧道暴露到公网
    - 触发：用户自行接入 Tailscale/frp
    - 期望：鉴权与加密默认开启；代码中不得存在「局域网内免鉴权」分支
- [[E-17]]　漏判或误判文档变更
    - 触发：重建仅改变时间戳，或任务行不变但范围、条款、提示词编译器已变
    - 期望：校验 schemaVersion=1 与任务包哈希一致性；对按任务 ID 排序的 id/contractHash 列表算指纹，识别任务增删和契约变化，generated 与 mtime 不作变更依据
- [[E-19]]　验收标准被事后改动
    - 触发：同一 id 的 input/output/accept 文本被改过
    - 期望：派发时把这三段快照进任务记录；列表标「文档已更新，与派发时不一致」
- [[E-215]]　加字段只改了类型
    - 触发：请求体加字段，改了 TS 接口没改 JSON Schema
    - 期望：**编译期失败**：每个请求体类型旁强制配一份 `as const satisfies readonly (keyof T)[]` 的键清单并做穷尽断言，漏字段则 `tsc` 报错
- [[E-216]]　加字段只改了 schema
    - 触发：改了 JSON Schema 没改 TS 接口
    - 期望：契约测试断言「`schema.properties` 的键集合 === 该类型的键清单常量」，不等即失败
- [[E-82]]　文档源不可读或任务包不可派发
    - 触发：文件被删、解析失败、缺协议字段或版本不一致；或合法任务包的 ready=false
    - 期望：源不可读时保留全部记录与快照、提示原因并冻结新派发；合法但待契约复核时仅阻止该任务派发并说明 reasons，不清空数据、不视为代码验收失败

## 实施沉淀

<!-- notes:begin -->
1. `listTasksWithDerivedStateStmt` 采用惰性 prepare（首次调用时 prepare），而非在 `createTasksRepo` 构造时立即 prepare：部分既有测试（如 `landing.test.ts`）在仅建有 `tasks` 表的临时 SQLite 实例上构建 `tasksRepo`，构造期立即 prepare 跨表 `LEFT JOIN runs` 的 SQL 会导致无 `runs` 表的用例报错。
2. 游标分页基于 `task_key ASC` 排序并使用 `t.task_key > ?` 推进，依托 `tasks` 表 `UNIQUE (doc_id, task_key)` 约束保证单调性；当客户端以任务主键 `id` 作为游标传入时，repo 会自动解析出对应的 `task_key` 进行比较，保证游标入参兼容性。
3. `refreshDocument` 的变更判定分为两层：`content_fingerprint` 比对判定文档是否发生实质改动并决定是否推送 `system.docs_changed` 事件；`dispatchSnapshotsRepo.refreshDocDiff` 判定当前任务与最新派发快照在验收标准、提示词和删除状态上的三标记。若文档源不可读，置 `is_source_readable = 0`，保留既有任务、快照及批次记录，抛出 `409 E_DOC_SOURCE_UNREADABLE`（E-82）。
4. `50-routes.ts` 兜底注册循环删除后，Fastify 架构测试断言注册集合与 `ROUTES` 精确相等且无两条路由共用 handler 函数对象，杜绝了多路由共享兜底闭包导致契约假绿的隐患（E-215、E-216）。
5. `TaskDto` 扩展文档变化标记字段（`hasAcceptChanged`, `hasPromptChanged`, `isRemovedFromDoc`），并在 `toTaskDto` 中将 `TaskRow` 存储的 0/1 标记转换为布尔值，使客户端任务列表接口能逐任务呈现快照后的变更状态（E-19）。
6. `refreshDocument` 将文档元数据更新、任务持久化及快照差异比对纳入单次 service 级 `unitOfWork.run`；向 `persistParsedTasks` 传入 `true` 使其复用外层事务，避免嵌套。后段失败时数据库修改全部回滚；恢复后重试仍能识别变更，并在提交后发布 `system.docs_changed` 事件。
<!-- notes:end -->
