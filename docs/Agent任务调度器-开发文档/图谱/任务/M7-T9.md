2) 集成测试（真容器 + 假子进程）：假实施进程退出码 0 后 `evaluateMechanicalCheck` 被调一次、`kind=review` 运行行被 INSERT、`task.review_verdict` 发出
假审查进程吐 `VERDICT: pass` 后出现 `waiting` 闸门行，`GET /api/v1/gates?pending` 返回它，`POST /api/v1/gates/:gateId/decide` 传 `pass` 后实施运行迁 `landed` 并发 `task.landed` 带 `by:human`（[[E-53]]、[[E-57]]）
3) `reconcile-runs` 启动期把库里预置的 `running` 且 pid 不存在的行标 `interrupted`，pid 存在的标「失联」，不推定成功（[[E-123]]）

4) `disk-watch` 超阈值置「停止新派发」后 `POST /runs` 返回错误信封且已有运行继续
`log-index-repair` 启动期跑一次即 `stop()`（[[E-104]]）
5) route 与 job 复用同一批 service 方法：arch 测试断言 `jobs/` 下无 `repo/` import，`http/routes/gates.ts` 与 tick 拿到的是同一个 `gateService` 实例（08 节隔离规则）

## 必须处理的边界

- [[E-104]]　存储盘写满
    - 触发：追加写失败
    - 期望：立即停止新派发并明确报错；恢复后要能继续追加，已有记录不得损坏
- [[E-120]]　长思考被误判停滞
    - 触发：超过阈值但 NDJSON 仍在输出
    - 期望：只标「疑似停滞」的弱提示，不改运行状态；只有完全无流事件超阈值才升级为醒目告警
- [[E-123]]　daemon 重启后的孤儿记录
    - 触发：重启后仍有状态为「运行中」的记录
    - 期望：启动时按 PID 对账，进程不存在则标「异常终止（daemon 重启）」，绝不推定成功
- [[E-53]]　落地闸门可设自动
    - 触发：三个闸门各自可设「自动」或「等我确认」
    - 期望：落地闸门默认「等我确认」，可切到「自动」：自动只表示审查 pass 后直接进 `landed`（已验收），产品仍不执行任何 git 操作（决策 12）；UI 三个开关同一形态、第三个不再置灰，切到自动时行内常驻一句说明而不弹确认框
- [[E-57]]　两端同时点确认
    - 触发：手机与桌面同时对同一闸门确认
    - 期望：幂等，第二次提示「已由另一端确认」，不产生两次派发

## 实施沉淀

<!-- notes:begin -->
1. 组合根依赖解耦与退出回调挂接：`reviewService`、`gateService` 与 `runService` 间存在事件与状态迁移交叉调用。组合根使用 holder 闭包引用 `reviewServiceHolder.current` 将 `evaluateMechanicalCheck` 与 `finalizeReview` 注册至 `runService` 的进程退出监听链，彻底消除循环构造风险并维持模块单向注入约束。
2. 进程退出路径的多态分流与防重入：`attachProcess` 针对 implementation-like 运行在 exitCode 0 时执行机械检查通过后插入 `kind=review` 审查运行并唤起审查 agent；针对 `kind=review` 退出触发 `finalizeReview` 提取 logstore 文本完成三态裁决。若调用方已预置 `onExit` 勾子处理过状态，通过执行状态与标志位短路规避重复结算。
3. 审查裁定驱动闸门流向与人工决断闭环：审查 agent 输出经 `readReviewReportText` 优先提取 `agent_message_chunk`（回落 raw），由 `evaluateReviewVerdict` 结构化裁决后发布 `task.review_verdict`。在落地闸门默认 manual 设置下自动沉淀 waiting 闸门；人工调用 `/api/v1/gates/:gateId/decide` 决策 pass 时，单事务同步将任务及其实施运行推进至 `landed` 并下发 `by: 'human'` 的 `task.landed` 事件，二次决断幂等拦截报 409。
4. 后台任务全集边界与安全运行：容器 jobs 数组严格收拢为规范规定的五个任务。`reconcile-runs` 启动按 PID 对账，进程消失标 `interrupted`、存在标 `orphaned`，绝不推定成功；`stall-detector` 超时只发弱告警不杀进程；`disk-watch` 触发停止派发标志后由包装层在 HTTP 路由层直接返回 507 错误信封，已有运行不受破坏。
