## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) `POST /api/v1/batches/:batchId/assignments` 整批覆写：未列出的任务草稿置 NULL
`taskId` 不属于该批或已派出 → `E_VALIDATION` 带 `details.field`
同一 `taskId` 重复 → `E_VALIDATION`
`agentId` 不在注册表 → `E_VALIDATION`
`logged_out` 的 agent 照常可写（[[E-108]]、[[E-336]]）
2) 响应 `drafts[].sessionNo` = 该 agent 占并发额度的运行数 + 同 agent 草稿按 taskKey 字典序的序号：单测 codex 已有 1 条活跃运行、两条草稿 → 序号 2 与 3，claude 零活跃一条草稿 → 1（[[E-31]]）
3) `preview` 由 `calculateBatchConcurrency()` 算出：`windowCount` 为本批此刻可放行任务数、`userSetting` 为 `documents.lane_count`、`bottleneck` 三值之一、`isFull = active + drafted ≥ limit`
单测三种瓶颈各一例，`userSetting` 大于 `windowCount` 时 `exceedsWindowCount:true`（[[E-52]]、[[E-245]]）
4) 某 agent `isFull` 时其余任务指派别家不受影响：集成测试 codex 满额、claude 空闲，`POST /batches/:id/start` 后 tick 先派 claude 的任务，codex 的排队（[[E-47]]）
5) tick 派出的实施运行 `agent_id` / `model_name` 逐字等于草稿，`runs.session_no` 等于预览给出的 `sessionNo`，`GET /runs/:id` 的 `RunDto.sessionNo` 下发同值
无草稿的任务回落第一个可派 agent（M8-T3 现行行为不变）

## 必须处理的边界

- [[E-108]]　零运行空态
    - 触发：首次使用或全部空闲
    - 期望：空态直接是「选文档 → 选批次 → 选模型 → 派发」的四步引导，而不是一张插画
- [[E-245]]　窗口数设得比机器扛得住的大
    - 触发：用户把窗口数设成 6 但机器只跑得动 2
    - 期望：设置值只是**上限**，实际并发取 min(设置, 每 agent 上限, 机器资源, 路径冲突)；**设置值不被运行时静默改写**，UI 显示是哪一项成了瓶颈
- [[E-31]]　同一 agent 并发多任务
    - 触发：一个 agent 被同时派多个任务
    - 期望：每任务独立 session 与独立工作区（grok 用自带 --worktree，其余用 git worktree 兜底），并设每 agent 并发上限
- [[E-336]]　agent 判定为 `logged_out` 时派发
    - 触发：用户仍把任务指派给它并派发
    - 期望：**照常派发**（决策 108）；徽标与指派行显示「未登录：在终端运行 〈登录命令〉 后点刷新」；派发失败按 E-36 原样展示 agent 报错，零产出退出按 E-348 转人；代码中不存在按登录态拒绝 `POST /runs` 的路径（单测断言 `assertCanDispatch()` 不读登录缓存）
- [[E-47]]　单 agent 并发满但窗口有空位
    - 触发：某 agent 达到并发上限，整体窗口未满
    - 期望：空位让给其他 agent 的任务，不空转等待
- [[E-52]]　并发瓶颈来源不明
    - 触发：实际并发数低于用户预期
    - 期望：实际并发取 min(窗口数, 每 agent 上限, 用户设定)，UI 显示这三者中哪一个成了瓶颈；用户可向下调，向上超过窗口数需显式解锁并提示后果

## 实施沉淀

<!-- notes:begin -->
1. `windowCount` 只看依赖层级，不看路径冲突与契约就绪：
契约把它定义为「本批依赖层级下此刻可放行任务数」，所以 `listReleasableTaskIds()` 只排除 landed、在途、终态失败、已移除和前置未落地的任务。路径冲突与 `is_contract_ready` 是 tick 的另一层过滤（tasksBlocked），若也算进去，预览的窗口会随文档改动抖动，而它本该只随依赖图变。没有草稿时 `calculateBatchConcurrency()` 对空 assignments 取 agentLimit=1，预览的 bottleneck 恒为 `agent_limit`——这是 M8-T1 的既定行为，测试明确断言了；前端别把它当异常，草稿一出现就正常了。

2. `sessionNo` 两处算法一致但来源不同，且依赖 tick 的串行 INSERT：
预览用 `numberDraftSessions()`（占额度运行数 + 同 agent 草稿 taskKey 序），派发用 `nextSessionNoFor()` 在 INSERT 事务内重新数。不把预览号直接写进运行，是因为草稿到派发之间活跃运行数会变——预览是「此刻会是第几个」，不是承诺。AC 5 两边对得上，靠的是 tick 按 taskKey 序逐个 `createRun`、每次 INSERT 后 `listActive()` 立刻能看到前一条；谁把 tick 改成并行 `createRun`，`session_no` 就会重号。

3. 「已派出」用四个事实判定，orphaned 例外：
landed（manual_state 或任一 landed 运行）、有在途运行、最近一次运行终态失败（failed / aborted / interrupted，tick 不自动重派，草稿对它无意义，重派走 M8-T5）、`is_removed_from_doc`。orphaned 既不在 `listActive()` 里也不算终态失败，所以孤儿任务仍可改草稿——对账后重派时正好用得上。

4. 草稿 agent 不可派时不改派：
`resolveAgentForTask()` 返回草稿 agent，`isAgentDispatchable` 为假就进 tasksBlocked(agent_unavailable)。否掉的做法是「草稿 agent 不可用就回落第一个可派 agent」——那会把用户明确指派给 claude 的任务偷偷派给 codex；E-336 要 logged_out 照常派发，真不可用就该报出来让人处理。

5. E-336 靠「服务根本拿不到登录态」保证：
`listRegistryAgents` 只投影 agentId / maxConcurrency / effortVendorMap，单测用正则断言 `service/assignments.ts` 与 `service/dispatch.ts` 不出现 logged_out / getLogin / loginCache / refreshLogin。将来有人往 `RegistryAgentSummary` 加 login 字段，这条测试会先挡住。

6. vendor effort 的取值域没有复用 `updateAgent()` 里那段：
它是 agents.ts 的私有闭包，且域为空时会触发一次 live 探测。容器里的 `listVendorEffortDomain` 走 `agentService.listAgentModels()` 读缓存，并把注册表 `effortVendorMap` 三个值作为基线，草稿写入不会被探测超时拖住。

7. 容器的 `listDispatchableAgents` 必须带注册表 `maxConcurrency`：
预览的 `isFull` 与 tick 的 `agent_limit_reached` 必须用同一个上限，否则面板说满了 tick 还在派。`concurrencyLimit` 缺席时 tick 对所有 agent 恒用 `DEFAULT_AGENT_CONCURRENCY_LIMIT`（2），注册表 maxConcurrency=1 的 agent 会被派两条。该常量放在 domain/concurrency.ts 而不是 dispatch.ts 里，就是让预览与 tick 只能取同一个缺省值。

8. tasks 表 SELECT 走列存在性探测而不是直接改常量：
`createTasksRepo()` 对 `bug_prompt` / `lane_no` 就是按 `PRAGMA table_info` 探测后再拼列的，`assignment_draft_json` 沿用同一套：以 `'\nFROM tasks\n'` 为锚点追加，四条 SELECT 常量不改。`setAssignmentDraft()` 在列缺失时抛 E_INTERNAL，不像 `setLaneNo()` 那样静默 no-op：草稿写不进去应当让请求失败，而不是返回 200 什么都没存。

9. 整批覆写只清「待派」任务的草稿：
已派出任务的 `assignment_draft_json` 保留作历史（09 节，M8-T9 的 `assignment_json` 逐字抄它），所以 GET 的 drafts 数组过滤掉了非待派任务。前端不要按「列非空」推断待派。

10. 手写 Fastify 的测试必须传 `ajv.customOptions.removeAdditional:false`：
不传时 `fastify()` 默认把额外字段剥掉并返回 200，断言 400 的用例会误判；`http/server.ts` 是显式关掉的，测试要照抄那一行。
