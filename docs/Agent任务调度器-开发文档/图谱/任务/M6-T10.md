# M6-T10　任务终态会话归档与不复用断言

- 所属模块：[[M6]]　**运行监管**——管一次运行从启动到结束的全过程：状态机（「已退出」与「已落地」分开）、收流与落盘编排、按游标分段回读与厂商会话文件的只读引用、进度信号、停滞检测、中止与 daemon 重启后的对账、回话投递；任务到达终态后结束并归档该任务全部会话（进程还在走 `killTree` 两阶段），归档后会话引用只读、不得复用，也归它。凡「这一次运行现在怎么样、它说过什么」的都归它
- 前置依赖：[[M6-T1]]、[[M6-T6]]、[[M1-T7]]
- 完成后解锁：[[M8-T8]]

## 输入 / 产出

- **输入**：M6-T1 的状态机与终态判定；M6-T6 的回话投递结果与 `ProcessRegistry`；M1-T7 的 `platform.killTree` 两阶段；09 节的 `session_archived_at` / `lane_no` 列定义
- **产出**：`service/session-archive.ts`（`archiveTaskInTx()` / `terminateArchived()`）、`service/session-guard.ts`（`assertSessionRefFree()` / `assertNotArchived()`）、`service/run.ts` 终态迁移的后置接线、`repo/runs.ts` 的 `findByVendorSessionRef` / `listByTask` / `markSessionsArchived`、`test/arch/session-isolation.test.ts`、`test/integration/session-archive.test.ts`、新增一个普通迁移（`runs.session_archived_at`、`runs.lane_no`、`tasks.lane_no`、`ux_tasks_lane` 部分唯一索引、`(lane_no)` 索引）、shared 的 `task.sessions_archived` 与 `lane.released` 事件及 `E_SESSION_ARCHIVED` 错误码、`boot/container.ts` 接线（把归档守卫注入 `messageService`，使归档后投递真的返回 409）

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 归档只有一个触发点：`kind='implement'` 行迁到 landed／failed／aborted／interrupted 的同一事务里，对该任务 `session_archived_at IS NULL` 的全部运行行批量写 `session_archived_at`，同事务把 `tasks.lane_no` 置 NULL（`changes===1` 才收集 `lane.released`）
事务内不 await、不 killTree、不 publish（[[E-302]]）
2) 事务后对 `pid` 非空且注册表仍持有的运行逐个 `platform.killTree` 两阶段，存活的收进 `residualPids`，然后才发 `task.sessions_archived{taskId, runIds, killedPids, residualPids}`
残留不阻塞槽位释放、不等进程死亡（[[E-322]]）
3) `awaiting_human` 只置 `tasks.lane_no` NULL、不归档，会话保持可回灌与可续接（[[E-54]]、[[E-326]]）
4) `POST /runs/:id/messages`、返工回灌与审查续接命中 `session_archived_at` 非空的行返回 409 `E_SESSION_ARCHIVED`
`vendor_session_ref` 原样保留只读，不删不改不拷贝（[[E-96]]、[[E-302]]）
5) `assertSessionRefFree({taskId, vendorSessionRef})` 在其他任务任一运行的引用与之相等时抛 `E_SESSION_ARCHIVED` 并带 `conflictTaskKey`
同一任务多轮共享引用放行
代码中不存在 `UNIQUE(vendor_session_ref)`（[[E-303]]）
6) `test/arch/session-isolation.test.ts` 静态扫 `src/service/**` 每个 `runsRepo.insert(` 调用点，断言同一函数体内出现 `assertSessionRefFree(`
集成剧本「归档后投递 409」「跨任务复用引用 409」「同任务第 2 轮共享引用 200」「续接目标已归档 409」四条通过
7) 新列全部可空、旧库直开不回填
`killTree` 与残留计数按 16 节埋点记日志

## 必须处理的边界

- [[E-302]]　任务终态时会话进程还在
    - 触发：任务进入 landed／failed／aborted／interrupted，而该任务的实施／审查／查 bug 会话进程仍存活
    - 期望：结束并归档该任务全部会话：进程走 `platform.killTree` 两阶段（E-119），每条运行写 `session_archived_at`，`vendor_session_ref` 从此只作只读引用；同一泳道的下一个任务一律新建会话，**绝不把已归档会话拿来跑新任务**
- [[E-303]]　泳道补位时复用了旧会话引用
    - 触发：新建运行的 `vendor_session_ref`（或续接目标会话）等于其他任务任一运行的引用
    - 期望：拒绝派发并返回 `E_SESSION_ARCHIVED`，`details` 带冲突的 taskKey 与 runId；泳道保持空闲、下一次 tick 重试；service 层校验与 arch 测试各挡一道，不靠人 review
- [[E-322]]　归档时进程残留
    - 触发：`killTree` 两阶段后该任务仍有存活子进程
    - 期望：归档照常完成、泳道照常释放（槽位按任务不按进程）；`task.sessions_archived` payload 带 `residualPids` 与计数，顶栏横幅「N 个会话进程未能终止」并给「杀掉」入口（复用 E-02 的处置侧）；残留进程的会话引用同样不得被复用（E-303）
- [[E-326]]　任务停在人工闸门期间的泳道与会话
    - 触发：运行以任何原因进入 `awaiting_human`（pass 等确认、E-55 超限、审查未完成、doc-issue、查 bug 转人等），或 daemon 重启后成为 `orphaned`
    - 期望：同一事务里 `tasks.lane_no` 置 NULL、发 `lane.released{reason:'awaiting_human'}`，下一 tick 补位；该任务全部运行**不写 `session_archived_at`、不 killTree**，进程自然退出只留 `vendor_session_ref` 供恢复；路径锁仍按 E-46 到 landed 才释放；`awaiting_reply` 不释放泳道、继续占额度；人放行→landed 或人判失败→failed 才按 E-302 归档，此时不再发 `lane.released`；等待不过期、不自动放行（E-58），daemon 重启不改其状态；停靠中的任务不在甲板上，入口只有批次树「等你」行、全局未处理徽标与任务／运行详情里的审批卡
- [[E-54]]　闸门等确认而人长时间不来
    - 触发：夜间无人值守，任务停在闸门前
    - 期望：该任务释放并发额度、不占窗口，其他任务继续；仅其下游依赖任务被动等待
- [[E-96]]　厂商会话文件的所有权
    - 触发：会话记录位于 `~/.claude/projects`、`~/.codex/sessions` 等厂商目录
    - 期望：只读打开、只存路径与偏移；任何清理/归档策略永不删除或改写这些文件（删了会破坏 `claude --resume` 之类的原生续接）

## 实施沉淀

<!-- notes:begin -->
1. 归档触发点唯一性：归档仅由 `kind='implement'` 行迁入终态（`landed` / `failed` / `aborted` / `interrupted`）触发。审查和查 bug 作为附属运行，其退出或落定不能归档整个任务的会话，否则会提前截断返工回环与多轮续接所需的活跃上下文。
2. 为什么不用 SQLite `UNIQUE(vendor_session_ref)`：审查续接（M7-T7）允许同一任务内部的第 N+1 轮审查运行共享第 N 轮的会话引用；SQLite 部分唯一索引无法表达「允许相同 task_id 重复、禁止跨 task_id 碰撞」的条件，故必须由 service 层 `assertSessionRefFree` 与架构测试 `session-isolation.test.ts` 静态扫描构成两道防线。
3. 严格遵循事务三段法：better-sqlite3 持有 WAL 写锁期间绝不执行异步 I/O。事务内只执行 `markSessionsArchived` 与 `tasks.lane_no = NULL` 并收集待终止 PID；事务返回后异步调 `killTree` 两阶段并发布 `task.sessions_archived`，避免外部进程终止耗时导致数据库锁超时。
4. 残留进程与槽位解耦：槽位按任务计数而非按操作系统进程计数。若某些 agent 子进程在两阶段 `killTree` 后存活，不阻塞槽位释放和后续泳道补位，残留 PID 记录进 `residualPids` 并记 warn 日志，交由顶栏告警横幅提示人工强杀。判定残留只看「不是 `terminated`」：`survived` 与 `not-process-owner`（EPERM，进程仍在但不归我们）都必须进 `residualPids`，否则活着的会话进程会被当成已终止、顶栏计数漏报（E-322）。
5. `awaiting_human` 与 `orphaned` 只放槽位不归档：闸门停靠期间会话进程自然退出，保留 `vendor_session_ref` 供审批放行后原生续接；若在此时归档会使后续人工放行回灌或续接返回 `E_SESSION_ARCHIVED` 导致流程锁死。
6. `lane.released` 只在 `clearLaneNo()` 返回 `changes===1` 时收集：`tasks.lane_no` 已为 NULL 说明该槽位此前释放过（典型是 `awaiting_human` 停靠时释放、人放行后迁 `landed`），E-326 要求此时不得再发一次 `lane.released`；终态事件 reason 用本次目标状态（`landed`／`failed`／`aborted`／`interrupted`），闸门停靠固定 `awaiting_human`，两者都在事务内收集、事务后 publish。
