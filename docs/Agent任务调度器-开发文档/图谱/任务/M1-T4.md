# M1-T4　日志正文追加写、字节偏移索引与切片

- 所属模块：[[M1]]　**运行底座**——让 daemon 在这台机器上稳定跑起来并把字节落到磁盘上：进程单实例与端口、启动自检、开机自启注册、数据目录、结构化存储的连接与迁移、日志正文的追加写与字节偏移索引、以及全部平台差异（进程树终止、路径规范化与长路径、配置目录、子进程编码）的唯一收口。凡与操作系统、磁盘、进程存活打交道而不带任何业务概念的都归它
- 前置依赖：[[M1-T2]]
- 完成后解锁：[[M1-T5]]、[[M6-T2]]、[[M6-T8]]

## 输入 / 产出

- **输入**：M1-T2 的库连接
- **产出**：`src/logstore/`：`AppendQueue` / 文件读写与恢复扫描 / 200MB 切片；`repo/events-index-repo.ts`、`repo/log-segments-repo.ts` 保存索引；`service/logstore.ts` 编排先文件后索引；`jobs/log-index-repair.ts` 的启动入口调用该 service，扫描与写库不放在 job 内

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 恒先 append 文件成功再写索引行，代码中不存在反序路径
2) 单次运行超 200MB 时按大小切片并在 `log_segments` 记边界（[[E-149]]）
3) 崩溃重启后从最后一条索引的 `byte_offset+byte_len` 扫到 EOF 补齐
「索引比文件多」记 `error` 而非静默修正（[[E-24]]）
4) 日志文件被手工删除时返回 `E_LOG_FILE_MISSING` 类型化结果而非抛异常（[[E-151]]）

## 必须处理的边界

- [[E-149]]　单次运行日志过大
    - 触发：超过 200MB
    - 期望：按大小切片并在索引表记录段边界，UI 按段拉取，不生成无法打开的巨型单文件
- [[E-151]]　日志文件被手工删除
    - 触发：用户清理了某次运行的日志
    - 期望：列表与元数据仍正常显示，日志区提示「日志文件已丢失」，页面不整体报错
- [[E-24]]　单任务日志膨胀
    - 触发：会话输出达到几十 MB
    - 期望：落盘归档并轮转，UI 只加载尾部与分页，内存不留全量

## 实施沉淀

<!-- notes:begin -->
- 正常追加由 `appendEventLine` 在正文与换行均追加成功后写索引；`raw.log` 不写事件索引。恢复扫描也有索引写入入口。
- 切片阈值 `SEGMENT_SIZE_LIMIT_BYTES` 默认 200 MiB，可通过 `segmentSizeLimitBytes` 注入较小值验证边界。0 号段命名为 `raw.log` / `events.ndjson`，后续段命名为 `raw-1.log` / `events-1.ndjson`。
- `readSegmentPage` 使用内部字节游标 `<fileSeq>:<byteOffset>`，格式或数值无效时返回 `E_VALIDATION`。对外日志 API 的 `fromSeq`、`direction` 与双端游标仍以 10 节为准，由 M6-T8 接线。
- `log-index-repair` 的扫描入口补写文件尾部的事件索引；发现索引位置超过文件长度时，将 `corrupt:` 条目加入报告，不截断文件或删除索引。
- `fileLenSync` 将 `ENOENT` 转成 `null`，`listDirectory` 将目录不存在转成空列表；分页读取的文件长度预检查据此返回 `E_LOG_FILE_MISSING`。
<!-- notes:end -->
