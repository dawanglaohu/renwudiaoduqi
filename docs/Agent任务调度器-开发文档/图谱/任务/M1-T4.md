# M1-T4　日志正文追加写、字节偏移索引与切片

- 所属模块：[[M1]]　**运行底座**——让 daemon 在这台机器上稳定跑起来并把字节落到磁盘上：进程单实例与端口、启动自检、开机自启注册、数据目录、结构化存储的连接与迁移、日志正文的追加写与字节偏移索引、以及全部平台差异（进程树终止、路径规范化与长路径、配置目录、子进程编码）的唯一收口。凡与操作系统、磁盘、进程存活打交道而不带任何业务概念的都归它
- 前置依赖：[[M1-T2]]
- 完成后解锁：[[M1-T5]]、[[M6-T2]]、[[M6-T8]]

## 输入 / 产出

- **输入**：M1-T2 的库连接
- **产出**：`src/logstore/`：`AppendQueue` / 偏移索引 / 200MB 切片 / `log-index-repair`

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 恒先 append 文件成功再写索引行，代码中不存在反序路径
2) 单次运行超 200MB 时按大小切片并在 `log_segments` 记边界（[[E-149]]）
3) 崩溃重启后从最后一条索引的 `byte_offset+byte_len` 扫到 EOF 补齐
「索引比文件多」记 `error` 而非静默修正（[[E-24]]）
4) 日志文件被手工删除时返回 `E_LOG_FILE_MISSING` 类型化结果而非抛异常（[[E-151]]）

## 必须处理的边界

- [[E-149]]　单次运行日志过大
    - 触发：超过 200MB
    - 期望：按大小切片并在索引表记录段边界，UI 按段拉取，不生成无法打开的巨型单文件
- [[E-151]]　日志文件被手工删除
    - 触发：用户清理了某次运行的日志
    - 期望：列表与元数据仍正常显示，日志区提示「日志文件已丢失」，页面不整体报错
- [[E-24]]　单任务日志膨胀
    - 触发：会话输出达到几十 MB
    - 期望：落盘归档并轮转，UI 只加载尾部与分页，内存不留全量

## 实施沉淀

<!-- notes:begin -->
- 索引落库的调用点只有一个：appendEventLine 在 `await queue.append()` 之后执行 insertIndex，这样代码里不存在能先写索引的路径。raw.log 没有索引写入。
- 切片阈值 SEGMENT_SIZE_LIMIT_BYTES 是注入参数（run-writer 构造函数），单测里传 1024 字节就能跑到 rotate 分支；生产用默认 200 MB。文件名规则：0 号段仍为 raw.log/events.ndjson，轮替后追加 `raw-1.log` / `events-1.ndjson`。
- readSegmentPage 的游标格式字面量 `<fileSeq>:<byteOffset>` 是 API 边界，篡改或格式错误都返回 E_VALIDATION 类型化结果而不是 throw，前端不用按 HTTP 状态码分支。
- log-index-repair 既不修文件也不修库：文件比索引多就补齐，索引比文件多就把 `corrupt:` 放进报告里由上层决定，不静默吞掉。
- Node fs 层把 all ENOENT 包装成 null/空列表，只有 LogFileSystem.fileLenSync 允许返回 null；reader 见到 null 就返回 E_LOG_FILE_MISSING，不自己 try/catch ENOENT。
<!-- notes:end -->
