## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 任务、依赖、批次、自有并行窗口、验收标准与边界正确落库
两段提示词取 dispatch[id].implementation/review，有效范围取 handoff.effectivePaths[id]，保存 contract_hash、is_contract_ready 与 contract_reasons_json
ready=false 的合法任务可查看但禁止新派发，不能当成代码验收失败（[[E-17]]、[[E-82]]）
2) `deps` 指向不存在的 id 或成环时导入即校验，禁止进入自动批次派发
仅在人工确认依赖异常且当前上游 ready=true 时允许手动单点，确认不写回文档复核证据，ready=false 仍返回 E_DOC_CONTRACT_PENDING，**不因一条脏边卡死整个交接台**（[[E-20]]）
3) 多份文档按文档路径 + 指纹隔离，任务 id 不跨项目冲突，列表按文档分组不混排（[[E-21]]、[[E-87]]）
4) 依赖成环时与上游同规则**就地截断为层 0**（落进第 1 批），并在导入报告与 UI 列出环上任务 id，该批派发前**强制人工确认**依赖异常且上游 ready=true
人工确认不修改或绕过 ready（[[E-241]]）
5) `deps` 指向不存在的任务 id 时只计入存在的前驱，**被忽略的幽灵 id 必须在导入报告里列出**（[[E-242]]）
6) 批次号**不作持久标识**，每次导入按当前分层重算
历史派发记录只认任务 id 与快照（[[E-243]]）
7) 全部任务无依赖时只有「第 1 批」，界面照常按批次呈现，**不退化成无批次列表**（[[E-244]]）

## 必须处理的边界

- [[E-17]]　漏判或误判文档变更
    - 触发：重建仅改变时间戳，或任务行不变但范围、条款、提示词编译器已变
    - 期望：校验 schemaVersion=1 与任务包哈希一致性；对按任务 ID 排序的 id/contractHash 列表算指纹，识别任务增删和契约变化，generated 与 mtime 不作变更依据
- [[E-20]]　依赖脏数据
    - 触发：deps 指向不存在的 id，或依赖成环
    - 期望：导入时校验并告警，禁止进入自动批次派发；手动单点须先人工确认依赖异常且当前上游 ready=true，ready=false 仍返回 E_DOC_CONTRACT_PENDING，人工确认不写回文档复核证据；不得因一条脏边卡死整个交接台
- [[E-21]]　多份文档同时接入
    - 触发：用户接入多个项目的文档
    - 期望：按 pres.handoff 的 repo/branchPrefix 加文档指纹分工作区，任务 id 不跨项目冲突
- [[E-241]]　任务依赖成环
    - 触发：导入时 `deps` 构成环
    - 期望：与上游 `layerOf` 同规则**就地截断为层 0**（成环任务落进第 1 批），同时在导入报告与 UI 打显式告警列出环上的任务 id，该批派发前**强制人工确认**依赖异常且当前上游 ready=true；确认不修改或绕过 ready，ready=false 仍返回 E_DOC_CONTRACT_PENDING，不静默
- [[E-242]]　deps 引用了幽灵任务
    - 触发：`deps` 指向 tasks 中不存在的 id
    - 期望：与 `layerOf` 一致只计入存在的前驱，但**被忽略的幽灵 id 必须在导入报告里列出**
- [[E-243]]　文档重出导致批次号位移
    - 触发：依赖变化，分层结果整体改变
    - 期望：批次号**不作任何持久标识**，`tasks.batch_id` 每次导入按当前分层重算；历史派发记录只认任务 id 与派发快照，**不认批次号**
- [[E-244]]　全部任务无依赖
    - 触发：分层结果只有一层
    - 期望：只有「第 1 批」，界面照常按批次呈现，**不因只有一批而退化成无批次列表**
- [[E-82]]　文档源不可读或任务包不可派发
    - 触发：文件被删、解析失败、缺协议字段或版本不一致；或合法任务包的 ready=false
    - 期望：源不可读时保留全部记录与快照、提示原因并冻结新派发；合法但待契约复核时仅阻止该任务派发并说明 reasons，不清空数据、不视为代码验收失败
- [[E-87]]　同时接管多份文档
    - 触发：用户接入多个项目
    - 期望：按文档路径 + 指纹隔离，任务列表按文档分组，跨文档不混排、不共用批次编号

## 实施沉淀

<!-- notes:begin -->
批次分层与成环截断：环上所有任务统一截断为层 0（落入第 1 批，batch_no=1）。若仅将环上任务赋值为 0 而不更新后续拓扑计算，下游任务会基于环的原始深度产生断层批次号；因此分层算法先将环节点层号锁定为 0，再按拓扑计算下游节点的相对层级，保证批次编号连续。

批次与任务持久化：`tasks.id` 是系统级持久标识，受 `runs`、`dispatch_snapshots` 等外键约束。重新导入时必须按 `(doc_id, task_key)` 匹配并复用既有 `tasks.id` 与 `manual_state`，仅更新 `batch_id`、提示词与契约数据。批次行同样按 `(doc_id, batch_no)` 复用既有批次 ID，文档重新分层后未被任何任务引用的旧批次通过 `deleteUnusedForDoc` 级联清理。

脏数据与交接台可用性：幽灵依赖与成环不阻断数据落库，保证交接台与任务列表正常可用；依赖异常通过 `DependencyValidationReport` 输出，并将 `canAutoDispatch` 置为 false，阻断自动批次派发。

多文档隔离：`tasks` 与 `batches` 均绑定 `doc_id` 并具备 `UNIQUE(doc_id, task_key)` 与 `UNIQUE(doc_id, batch_no)` 约束，多项目接入时任务与批次编号完全正交。
<!-- notes:end -->
