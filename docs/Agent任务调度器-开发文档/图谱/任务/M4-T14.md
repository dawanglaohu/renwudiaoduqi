## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) `GET /agents/:id/models` 返回 `{models: [{name, source, provider?, effortOptions?, isCurrentConfig, isDefault?, note?}], isComplete, refreshedAt, liveFailure, currentConfig, isRefreshing}`（**不含登录态**，登录态只在 `AgentEntryDto.login`，决策 130），`source` 五值按 `live → config → builtin → history` 合并、`name` 精确比较同名只保留更靠前者、daemon 不产出 `manual`
`isComplete === live.ok`
config 当前值不在 `live` 时仍以 `source:'config'` 列出并 `isCurrentConfig:true`（[[E-338]]、[[E-350]]）
2) `live` 按注册表 `modelsLive.kind` 分派：`command` 走 `executeProbeProcess()` 后按 `parser` 调 grok／pi 文本解析器（pi 的参数从注册表 `['--list-models']` 读，代码中不再出现 `--models`）
`codex_app_server` 走 JSON-RPC：stdin 逐行写 `initialize` → `initialized` → `model/list`，忽略无 id 通知与非本请求 id 的响应，`hidden:true` 过滤，`nextCursor` 非 null 时**不追页**（翻页参数名未实测，04 节）、清单照返回并 warn，收齐即 `kill()`
`none` 返回 `not_supported`
超时按注册表 `modelsLive.timeoutMs`（出厂 5000、codex 10000，缺失回落 5000、上限 60000）
`live` 失败只写 `liveFailure`、HTTP 200、清单回落 config + builtin + history、不阻塞派发（[[E-38]]、[[E-345]]）
3) `?refresh=1` 删 `liveCache` 与登录缓存后并行起一次 `live` 与一次 `refreshLogin()`（pi 的 `providers` 取本次 `live` 表第一列 DISTINCT、`defaultProvider` 取 `read-models.ts` 新增的 `currentConfigProvider`，`live` 失败只传 `[defaultProvider]`），等两者 settle 再返回
缺省命中缓存直接用，未命中且有在途则**不等待**、用旧或空 `live` 立即返回并 `isRefreshing:true`
同一 agent 同时只一个 `live` 子进程（[[E-339]]）
4) history 由 `repo/runs.ts` 一条 SQL 派生：`state IN (SUCCEEDED_RUN_STATES)`、`model_name` 非空、按 `agent_id` 全局、`GROUP BY model_name ORDER BY MAX(ended_at) DESC` 取 40 再由适配器 `normalizeHistoryModelName()`（pi 剥 `:〈thinking〉` 后缀）去重截 20
不建表、不缓存、`repo` 里无厂商串（[[E-340]]）
5) `builtinModels` 是通用字段（claude 出厂 `opus` / `sonnet` / `haiku` / `opus[1m]` 各带 note），条目 `name` 含空白或控制字符拒绝该条 agent 并 warn
代码中不存在按 agentId 特判 claude 的分支（[[E-350]]）
6) 思考强度值形状 `EffortValue = {tier} ｜ {vendor} ｜ null`，落 `runs.effort_tier`（三档 CHECK 不改）与新列 `runs.effort_vendor` 恒不同时非空，`fromEffortColumns()` 遇双非空抛 `E_INTERNAL`

7) `PATCH /agents/:id` 收 `defaultEffortTier` 与 `clearOverrides`（`POST /runs` 收 `effort` 的接线归 M8-T9，本任务只交付 `assertVendorEffortInDomain()` 与 shared `CreateRunBody.effort` 类型）：`{vendor}` 经 `assertVendorEffortInDomain()` 校验只允许来自 config 当前值或 `live` 取值域，否则 `E_VALIDATION` 带 `allowed[]`

## 必须处理的边界

- [[E-255]]　思考强度档位无效或超出该模型取值域
    - 触发：用户选了高档但该模型只接受 low/medium；或厂商改了取值域
    - 期望：派发前校验，不通过则**就地说清原因与改法**（「`gpt-5.6-mini` 不接受思考强度 `高`，可选 低/中」），不静默降档也不静默丢弃；校验不了时按「不支持」处理走 E-254
- [[E-338]]　`live` 成功但清单不含配置当前值
    - 触发：`grok models`／`pi --list-models`／codex `model/list` 返回成功，但 `config.toml`／`settings.json` 里的当前模型名不在其中（用户手填了别名或已下线模型）
    - 期望：仍以 `source:'config'` 单独列出该项、标「当前配置 · 清单未列」并作默认选中；不改写、不做别名归并；选它派发原样透传，失败按 E-36
- [[E-339]]　刷新期间与并发刷新
    - 触发：用户点「刷新清单」后 `live` 与登录探测在途；同一 agent 被连点或 `availability_changed` 与手动刷新 5 秒内重叠
    - 期望：在途期间非 refresh 的 `GET /agents/:id/models` **不等待**，用旧 `live`（有缓存）或空 `live`（无缓存）+ config + builtin + history 立即返回并 `isRefreshing:true`；同一 agent 同时只一个 `live` 子进程、一个登录探测（`inflight` Map 去重，后续调用复用同一 promise）；刷新按钮在途时 disabled；`live` 失败不抛错、HTTP 200、`liveFailure` 字段说明原因
- [[E-340]]　history 来源的取值
    - 触发：打开指派面板或设置页时派生「该 agent 历史用过的模型」
    - 期望：只从 `runs` 派生一条 SQL：`state` 为成功终态 `landed`、`model_name` 非空、按 `agent_id` 全局（不分文档、不分 kind）、DISTINCT、按最近一次 `ended_at` 倒序、最多 20 条；`awaiting_human`（不论 reason）、`failed`、`aborted` 与人工从 `awaiting_human` 直接标 landed 且无成功运行的都不计；pi 的模型串剥掉 `:〈thinking〉` 后缀、保留 `provider/model` 前缀（只在 `adapters/pi` 做）；与 `live`／`config` 同名的归靠前来源、history 组去重；历史模型已下线仍列出不标「已下线」；每次现查不缓存，同一库重启后顺序逐字节相同
- [[E-342]]　覆盖 agent 与实施 agent 不同家
    - 触发：`reviewOverride.agentId` 或固定收口指派与任务指派的 agent 不同家（如 codex 任务由 claude 审查）
    - 期望：模型不跨家带：覆盖未给 `modelName` 时为 null（跟随覆盖 agent 配置，E-35）并记 warning `model_dropped_cross_family`；思考强度用 `remapEffortAcrossAgents()`：三档 `{tier}` 原样保留、`{vendor}` 在源家映射表反查回三档、反查不到或目标家 `effortVendorMap` 为 null → null 并记 warning `effort_unmappable`，参照条显示「—」且 title 说明「〈值〉 无法映射到 〈agent〉」；权限档不在指派里，审查仍固定只读档（E-135）
- [[E-345]]　codex app-server 不可用、握手失败或超时
    - 触发：`codex app-server` 起不来、`initialize`／`model/list` 返回 `error`、协议字段变化，或 10 秒（codex 出厂 `modelsLive.timeoutMs`）内无响应
    - 期望：`live` 缺失：`isComplete:false`、`liveFailure.reason` 为 `rpc_error`／`unparsable`／`timeout`／`spawn_failed`，清单回落 `config + builtin + history`，HTTP 200 不报错；设置页提示「实时清单获取失败（〈原因〉，N 秒），可刷新重试」，超时值来自注册表则提示里带该值；stderr 上 `codex_models_manager` 的远端刷新 ERROR 只进日志不影响 `ok`；协议里无 id 的通知（如 `remoteControl/status/changed`）与非本请求 id 的响应一律忽略；收齐后 `kill()` 不等它自然退出；派发不受影响
- [[E-350]]　清单同名去重、别名与「当前配置」的位次
    - 触发：同一模型名同时出现在多个来源；claude 的 `config` 当前值本身是别名（本机 `opus[1m]`）；注册表 `builtinModels` 为空或条目非法
    - 期望：按 `live → config → builtin → history` 顺序追加，`name` 精确比较（不 trim、不大小写归一、不做别名归并，E-45），同名只保留更靠前者，daemon 去重后前端不再去重；`config` 当前值是别名时只出现一次、归 config 组并默认选中，builtin 组不重复；`builtinModels` 缺失或空数组 → builtin 组不渲染；条目 `name` 含空白或控制字符 → 注册表加载时拒绝**该条 agent**并 warn，其余 agent 照列；非 claude 的 agent 填了 `builtinModels` 同样列出（通用字段，不特判）；将来 claude 有了列模型命令，`live` 同名胜出、builtin 组自动缩小；claude 永远 `isComplete:false` → 下拉底部固定一行「清单可能不全，可手填」，「刷新清单」对它只重读配置与历史；选了别名后运行失败按 E-36 原样展示、不从清单移除
- [[E-351]]　思考强度出现厂商原值
    - 触发：配置文件当前值超出三档（codex `xhigh`、pi `xhigh`）；用户在设置页或指派面板选了厂商原值；配置值拼错；所选模型的 `live` 取值域不含该值
    - 期望：值形状 `EffortValue = {tier} ｜ {vendor} ｜ null`，存储 `runs.effort_tier`（三档 CHECK 不改）与新列 `runs.effort_vendor` 恒不同时非空；`{vendor}` **只允许来自 `config` 当前值或 `live` 取值域**：`POST /runs`、`PATCH /agents/:id`、快照写入前校验，不在域内 → `E_VALIDATION`（`details.field:'effort'`、`allowed[]`），手填厂商值同样拒绝；派发时 `{vendor}` 原样传不映射，显示层显示原值；配置值既不在映射表也不在 `live` 域（如 `xhighh`）→ 仍作「当前配置」显示原值并加「无法识别」角标（`currentConfig.effortRecognized:false`），选它照传、失败按 E-36；所选模型的 `effortOptions` 不含该值（gpt-5.2 无 `max`）或三档映射后的厂商值不在其中 → 警告「该模型不支持 〈值〉」，不禁用、不换值；`effortVendorMap` 为 null 的 agent（dsh）传非 null → `E_VALIDATION`（reason `effort_unsupported`）；自报值比较对 `{vendor}` 用原串相等，`normalizeReportedEffort` 的 `xhigh→high` 只用于自报比较不用于存储；pi 模型串自带 `:xhigh` 且同时选了思考强度 → 显式选择优先、剥后缀改传 `--thinking` 并记一条 warn；设置页三行「内置默认／你的覆盖／当前生效」思考强度与模型同规则，当前生效 = 覆盖 ?? 配置 ?? 内置；旧快照缺 effort 字段读作 null 显示「—」
- [[E-358]]　设置页的分层值、覆盖与清除
    - 触发：打开设置页 agent 卡片；用户设覆盖、显式「覆盖为跟随」或点「恢复默认」；配置文件缺字段或解析失败；dsh
    - 期望：`AgentEntryDto.layers` 三层 `{builtin, config, override, hasOverride}`（模型与思考强度各一份），`effective` 由 service 按「覆盖 ?? 配置 ?? 内置」算出，前端不从清单 config 组反推；`config` 为 null 时三行该格「—」不弹错误；`hasOverride:false` 时生效 = 配置 ?? 内置，`hasOverride:true, override:null` 时生效 null（不传参，即使配置文件有值）；配置文件里的厂商原值以 `{vendor}` 原样携带；每个字段各自一个「恢复默认」，无覆盖时置灰不隐藏、title「当前没有覆盖」；「恢复默认」发 `PATCH /agents/:id {clearOverrides:['defaultModel']}`，只清该字段；`defaultEffortTier: null` 不在 `clearOverrides` 里 → 写入「覆盖为跟随」；body 同时含 `clearOverrides:['x']` 与 `x` → `E_VALIDATION`，重复或未知字段名 → `E_VALIDATION`，空数组视为未提供；PATCH 失败「你的覆盖」保持原值不乐观清空、按 E-36 原样展示；对 dsh 传 `clearOverrides:['defaultEffortTier']` 幂等成功，dsh 的思考强度块显示「该 agent 不支持」不渲染三行与按钮；用户点「刷新」后 `config` 与 `effective` 随缓存更新、`override` 不动；已派快照不受清除影响；`<400px` 三行竖排、按钮排在三行之下（决策 125、128、132）
- [[E-38]]　列模型命令超时或失败
    - 触发：`grok models` / `pi --list-models` / codex app-server `model/list` 超过注册表 `modelsLive.timeoutMs`（出厂默认 5 秒，codex 出厂 10 秒，按家可覆盖）或退出码非 0
    - 期望：清单降级为「配置文件当前值 + 内置别名 + 该 agent 历史用过的模型 + 手填」，`isComplete:false`、`liveFailure` 说明原因，UI 标注「清单可能不全」，绝不阻塞派发（决策 120）
