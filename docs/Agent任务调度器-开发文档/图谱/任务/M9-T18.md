## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 四步引导第三步是**逐任务指派**而不是「给整批选一个模型」：每行一个任务，各自选 agent／模型／思考强度，已指派行显示所选值可点回改（[[E-108]] 的第三步）
2) **同一个 agent 允许被指派多次，每次是一个独立会话**并显示将要使用的会话序号（[[E-31]]、决策
7、决策 52）
3) 第四步显示并发三者取 min 的结果，并**明确指出是并行窗口、该 agent 上限还是用户设定成了瓶颈**，不只给一个可放行数字（[[E-52]]）
4) 某 agent 已达并发上限时其余任务仍可指派给别家，**不空转等待**（[[E-47]] 的呈现侧）
5) **数据来源与写入路径**（2026-09-19 补丁，决策 136）：会话序号、agent 已用／上限／是否满额、有效并发、瓶颈来源、是否越过窗口一律读 `GET /api/v1/batches/:batchId/assignments` 的 `drafts[].sessionNo` 与 `preview`，用户每次改选后 `POST` 同一端点整批覆写并用返回值刷新，组件不按数组顺序自算序号、不用 `Math.min` 自算并发、字段缺失显示「—」

## 必须处理的边界

- [[E-108]]　零运行空态
    - 触发：首次使用或全部空闲
    - 期望：空态直接是「选文档 → 选批次 → 选模型 → 派发」的四步引导，而不是一张插画
- [[E-31]]　同一 agent 并发多任务
    - 触发：一个 agent 被同时派多个任务
    - 期望：每任务独立 session 与独立工作区（grok 用自带 --worktree，其余用 git worktree 兜底），并设每 agent 并发上限
- [[E-47]]　单 agent 并发满但窗口有空位
    - 触发：某 agent 达到并发上限，整体窗口未满
    - 期望：空位让给其他 agent 的任务，不空转等待
- [[E-52]]　并发瓶颈来源不明
    - 触发：实际并发数低于用户预期
    - 期望：实际并发取 min(窗口数, 每 agent 上限, 用户设定)，UI 显示这三者中哪一个成了瓶颈；用户可向下调，向上超过窗口数需显式解锁并提示后果

## 实施沉淀

<!-- notes:begin -->
1. 逐行独立配置而非整批套用（AC 1、E-108）：否决了「整批一键统一套用模型」的快捷开关或批量指派按钮。四步引导的核心是逐任务独立治理，批量套用会破坏对每个任务模型与思考强度的精细权衡，也容易把思考强度参数误赋给不支持的 agent。界面坚持每行独立配置，已指派行可随时点「修改指派」回改。
2. 会话序号由调度器给出，界面只呈现（AC 2、E-31）：同一个 agent 被指派给多个任务时是相互隔离的独立 session。序号取 `GET /api/v1/batches/:batchId/assignments` 的 `drafts[].sessionNo`（该 agent 占用额度的运行数 + 同 agent 草稿按 taskKey 排序的名次），前端不按行序自算、不累加、草稿未写入时显示「—」。用户因此能在派发前看清哪些任务是同一 agent 的第几条会话，不会误以为它们共享上下文或工作树。
3. 单 agent 满额时空位让给别家（AC 4、E-47）：`preview.agentCapacities[]` 的 `active`/`limit`/`isFull` 直接驱动行内提示与顶部容量指标；某个 agent 满额只影响它自己那一行，其他任务照常可选别的 agent，绝不把全局派发按钮或别的 agent 置灰。
4. 并发瓶颈的归因权在 daemon（AC 3、E-52）：有效并发取 `preview.effectiveConcurrency`，瓶颈取 `preview.bottleneck`（三值域），逐 agent 数值直接列出 `preview.agentCapacities`，前端不做 `Math.min`、不聚合、不自算越界。用户设定只在 daemon 允许的范围内调节——向上超过并行窗口数必须先显式解锁，并在卡片里常驻后果提示（超出部分只会排队，不会带来物理加速）。
5. 思考强度与缺省值展示纪律（M4-T6、E-254、E-34）：不支持思考强度的 agent 强制置 `null` 并显示「—」，不补 `low`/`medium` 默认档；还没有选 agent 时说明写「请先选择 Agent」，不替 daemon 断言某 agent 不支持。切换 agent 即重置模型与思考强度覆盖（E-34）。所有 daemon 字段未就绪一律显示「—」，不补 `0` 或 `2` 冒充有效状态。
6. 数据来源与写入路径单点化（AC 5、决策 136）：文档、批次、可指派任务、agent 与模型清单全部经 `src/api/` 的 http-client 与 shared `ROUTES` 表获取，路径不写字面量；改选后整批 `POST` 同一端点，界面用返回值刷新而不是本地改数。因此 `run-deck-view.tsx` 的零运行分支不再持有任何演示数组，取数失败就地 inline notice 而不替换整页。
7. 分层与槽位契约（07 节、19 节第 7 条）：`assign-panel.tsx` 是纯 props 展示组件，只维护输入框开合与用户尚未提交的选择；取数、store 写入与错误规格化都在 `features/run-deck/` 的 hook 里；四步外壳由 M9-T16 的 `EmptyOnboarding` 提供，第三步与第四步正文分别经 `step3Slot` / `step4Slot` 注入，外壳本身不持有指派状态。
8. 无障碍与触控目标（R3、11 节）：全部交互控件用 `focus-visible:shadow-[0_0_0_3px_var(--needs-soft)]` 焦点环，没有无替代的 `outline-none`；手机档按钮、选择器与解锁复选框都满足 44×44 触控底线。
9. 运行甲板可达性：零运行四步引导要在真实浏览器里打开，`app/app.tsx` 必须装配 `deck` 与 `pair` 两个键，否则 `#/` 只渲染路由占位块。本任务只加这两个键，七键必填表与其余路由装配仍归 M9-T25；该最小接线已记入本任务有效范围。
