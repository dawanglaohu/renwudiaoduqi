## 实施沉淀

<!-- notes:begin -->
1. 容器装配与依赖环破除：`container.ts` 中 `reviewService` 依赖 `bughuntService`（审查 pass 分流），而 `bughuntService` 的结果处理依赖 `reviewService`（FIXED 有 diff 且 rework_count < 2 时需通知原审查会话再审一轮）。采用 Holder 惰性代理模式打破双向依赖，在 `createContainer` 阶段安全连接，避免循环构造。
2. 泳道占用与 agent 并发继承：bughunt 作为实施运行的子运行，严格沿用同一任务占有的泳道，不得因为泳道检查被丢弃在泳道外；在计算并发时，必须将正在占道等待的父实施运行排除在并发上限计数之外，否则当并发上限为 1 时 bughunt 子运行会永远卡在 `queued(agent_limit_reached)`。
3. 退出监听与 logstore 流刷盘时序：在进程式执行模式下，进程退出事件到达前必须确保 logstore 缓冲已刷盘，`finalizeBughunt` 回读报告文本时才能获取到完整五段内容；单测模拟 `emitLine` 时需保证微任务与 logstore 刷盘事件交错完成。
4. 人工闸门状态机一致性：bughunt 失败后经 HTTP rerun 触发原子重跑时，原 `bughunt_failed` 闸门被置为 `decided(superseded)`，同时实施运行由 `awaiting_human` 恢复为 `reviewing`，任务恢复占用泳道且不增加 `rework_count`；人工 reject 打回时则按 E-329 获取当前工作区 diff 统计，并向返工指令顶部注入未提交改动提示。
<!-- notes:end -->
