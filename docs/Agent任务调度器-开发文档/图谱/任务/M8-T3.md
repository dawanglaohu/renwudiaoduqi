# M8-T3　批次推进与幂等派发

- 所属模块：[[M8]]　**派发调度**——决定什么时候把哪个任务、用哪个 agent 与哪个模型、以什么权限派出去，并按批次、并行窗口、每 agent 并发与路径冲突限流，在三个闸门处停或放行、失败或重派时重新入队；判定本批分支是否都进了 HEAD、触发收口运行、按收口报告派修复运行与管理收口轮次也归它；泳道（窗口槽位）分配、任务终态后的补位、查 bug 与收口模式两个开关的持久化同样归它——泳道分配是它算出的派生数据。凡涉及顺序、名额、放行、重派的都归它；任务指派写进派发快照、阶段取值链（任务指派 → 阶段覆盖 → agent 默认）与收口指派设置也归它——它是唯一决定「这一阶段用谁跑」的地方，M7 只消费结果

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) `scheduler-tick` 全局一把内存互斥量，**禁止并发 tick、禁止重入**，同一任务不会被派两次
2) 幂等键唯一，两端同时点派发时第二次返回既有 run 而非起第二个进程（[[E-126]]）
3) 批内某任务失败或审查未过时不阻塞同批其他无依赖任务
下一批启动条件是本批 `done`——全部「已落地」且批次状态为 `done`，前一批未 done 时 `POST /batches/:id/start` 返回既有前置检查错误并在 `details.previousBatchState` 写明（[[E-49]]、[[E-281]]）
4) daemon 重启或断电恢复后按持久化状态续跑，会话还活着就重挂、已死的标「中断」等人决定，**任何情况下不自动重派**（[[E-51]]）
5) 批次执行途中任务 ID/contractHash 指纹变化时已派任务用快照跑完，后续派发自动暂停待确认
自动、手动和重派入口在创建新运行前都检查 is_contract_ready，未通过返回 E_DOC_CONTRACT_PENDING 并列出原因，人工确认不绕过文档契约阻断（[[E-50]]、[[E-82]]）

## 必须处理的边界

- [[E-126]]　两台设备同时派发同一任务
    - 触发：并发点击
    - 期望：daemon 侧按任务加幂等键，第二次返回「已在运行」而不是起第二个进程
- [[E-281]]　落地闸门自动但本批收口未跑
    - 触发：三闸门全自动，本批全部任务已自动 landed，收口尚未 clean/fixed
    - 期望：下一批不派发：启动条件是本批 `done`（全部 landed 且最近一轮收口有效裁定 clean／fixed）；`POST /batches/:id/start` 对前一批未 done 返回既有前置检查错误并在 details 写 `previousBatchState`
- [[E-49]]　批内某任务失败或审查未过
    - 触发：一批中个别任务卡住
    - 期望：不阻塞同批其他无依赖任务；但下一批的启动条件是本批 `done`——全部「已落地」（已验收）**且最近一轮收口有效裁定为 clean 或 fixed**，未解决的任务或未收口的批次都会让下一批停在那里等人
- [[E-50]]　批次执行途中文档变了
    - 触发：执行期间任务 ID/contractHash 指纹变化，包括任务行未变而范围、条款或提示词变化
    - 期望：已派任务继续用快照跑完，后续派发自动暂停并要人确认新文档，绝不热改在途任务
- [[E-51]]　daemon 重启或断电恢复
    - 触发：进程死后重新拉起，部分会话可能还活着
    - 期望：按持久化状态续跑；会话还活着就重挂，已死的标「中断」等人决定；任何情况下不自动重派（防止重复写同一批文件）
- [[E-82]]　文档源不可读或任务包不可派发
    - 触发：文件被删、解析失败、缺协议字段或版本不一致；或合法任务包的 ready=false
    - 期望：源不可读时保留全部记录与快照、提示原因并冻结新派发；合法但待契约复核时仅阻止该任务派发并说明 reasons，不清空数据、不视为代码验收失败

## 实施沉淀

<!-- notes:begin -->
1. 幂等防重靠两层，不是纯应用层逻辑：
`runs.idempotency_key UNIQUE` 是并发点击的最终兜底；应用层先查幂等键、再查同任务在途运行，只是避免把 UNIQUE 冲突当正常路径。冲突回退必须判 SQLite `code`（`SQLITE_CONSTRAINT_UNIQUE`），禁止 `err.message.includes('UNIQUE constraint failed')`。快照 INSERT 与 run INSERT 必须进同一个 `unitOfWork.run`，否则第二次请求可能看到半成品。

2. 批次推进闸门：
下一批启动的硬条件是前一批 `state === 'done'` 且任务全落地。未满足时 `POST /batches/:id/start` 返回 `E_VALIDATION` 并写 `details.previousBatchState`。同批失败任务不阻断无依赖兄弟，但批次本身不得推进。

3. 契约阻断不可绕过：
自动 tick、手动 createRun、rerun 都检查 `is_contract_ready`。未就绪抛 `E_DOC_CONTRACT_PENDING` 并带回 reasons。文档中途变更只暂停后续自动派发，在途任务继续吃快照。

4. 接线与 agent 取值：
`scheduler-tick` 必须进 `container.jobs`，本任务端点必须进 `50-routes` 的 `customRegisteredPaths`，否则运行期永远是未实现占位。自动派发禁止写死 `codex`；注册表没有可用 agent 时进 `tasksBlocked`，不要落孤儿 run。
5. 工作区检查：手动派发、批次启动、重派与自动调度在创建运行前解析文档来源并检查本机 Git 仓库。删除、目录占位、格式损坏及协议版本错误冻结新派发，保留记录；合法任务 ID/contractHash 指纹变更返回 E_SNAPSHOT_STALE，等待刷新确认，不标记不可读。无新运行候选的文档不重复探测 Git。已派出的排队、审查与查 bug 运行继续使用冻结快照，批次落地推进也不受来源失效影响。重派响应丢失后的同键重试返回已接受的运行，不增加尝试、快照或窗口。
6. readiness 不进入契约指纹，预检仍逐任务读取本次 ready/reasons。待复核任务返回 E_DOC_CONTRACT_PENDING 并附原因，自动派发在路径冲突与并发分配前移除它，已就绪的兄弟任务继续派发。收口的文档检查不能替代后续任务检查。预检与整轮提交之间允许其他文档执行异步检查，提交时同步核对原绑定并重新读取来源、解析契约及就绪状态；未刷新到数据库的删除或改写也阻止新运行。整轮分配保持同一事务，其余文档及已有快照不受来源失效影响。
7. 设置更新触发的自动调度与手动派发可同时预检。自动候选提交时重新查询任务运行历史；手动入口已创建运行时跳过新分配，保留已接受的运行与快照。手动入口在自动派发先完成时复用在途运行，两种顺序都只占用一次尝试与快照，避免重复实施阻塞后续审查或查 bug 的并发额度。
8. 手动派发的提交前来源检查放在事务外，检查与事务之间没有异步等待。来源被删除或损坏时，文档持续报告不可读，历史任务、运行、快照和窗口分配保持原状；派发事务仍负责运行与快照的原子写入。
