# M8-T3　批次推进与幂等派发

- 所属模块：[[M8]]　**派发调度**——决定什么时候把哪个任务、用哪个 agent 与哪个模型、以什么权限派出去，并按批次、并行窗口、每 agent 并发与路径冲突限流，在三个闸门处停或放行、失败或重派时重新入队；判定本批分支是否都进了 HEAD、触发收口运行、按收口报告派修复运行与管理收口轮次也归它；泳道（窗口槽位）分配、任务终态后的补位、查 bug 与收口模式两个开关的持久化同样归它——泳道分配是它算出的派生数据。凡涉及顺序、名额、放行、重派的都归它；任务指派写进派发快照、阶段取值链（任务指派 → 阶段覆盖 → agent 默认）与收口指派设置也归它——它是唯一决定「这一阶段用谁跑」的地方，M7 只消费结果

- 完成后解锁：[[M8-T4]]、[[M8-T5]]、[[M8-T6]]、[[M8-T8]]

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) `scheduler-tick` 全局一把内存互斥量，**禁止并发 tick、禁止重入**，同一任务不会被派两次
2) 幂等键唯一，两端同时点派发时第二次返回既有 run 而非起第二个进程（[[E-126]]）
3) 批内某任务失败或审查未过时不阻塞同批其他无依赖任务
下一批启动条件是本批 `done`——全部「已落地」且批次状态为 `done`，前一批未 done 时 `POST /batches/:id/start` 返回既有前置检查错误并在 `details.previousBatchState` 写明（[[E-49]]、[[E-281]]）
4) daemon 重启或断电恢复后按持久化状态续跑，会话还活着就重挂、已死的标「中断」等人决定，**任何情况下不自动重派**（[[E-51]]）
5) 批次执行途中任务 ID/contractHash 指纹变化时已派任务用快照跑完，后续派发自动暂停待确认
自动、手动和重派入口在创建新运行前都检查 is_contract_ready，未通过返回 E_DOC_CONTRACT_PENDING 并列出原因，人工确认不绕过文档契约阻断（[[E-50]]、[[E-82]]）

## 必须处理的边界

- [[E-126]]　两台设备同时派发同一任务
    - 触发：并发点击
    - 期望：daemon 侧按任务加幂等键，第二次返回「已在运行」而不是起第二个进程
- [[E-281]]　落地闸门自动但本批收口未跑
    - 触发：三闸门全自动，本批全部任务已自动 landed，收口尚未 clean/fixed
    - 期望：下一批不派发：启动条件是本批 `done`（全部 landed 且最近一轮收口有效裁定 clean／fixed）；`POST /batches/:id/start` 对前一批未 done 返回既有前置检查错误并在 details 写 `previousBatchState`
- [[E-49]]　批内某任务失败或审查未过
    - 触发：一批中个别任务卡住
    - 期望：不阻塞同批其他无依赖任务；但下一批的启动条件是本批 `done`——全部「已落地」（已验收）**且最近一轮收口有效裁定为 clean 或 fixed**，未解决的任务或未收口的批次都会让下一批停在那里等人
- [[E-50]]　批次执行途中文档变了
    - 触发：执行期间任务 ID/contractHash 指纹变化，包括任务行未变而范围、条款或提示词变化
    - 期望：已派任务继续用快照跑完，后续派发自动暂停并要人确认新文档，绝不热改在途任务
- [[E-51]]　daemon 重启或断电恢复
    - 触发：进程死后重新拉起，部分会话可能还活着
    - 期望：按持久化状态续跑；会话还活着就重挂，已死的标「中断」等人决定；任何情况下不自动重派（防止重复写同一批文件）
- [[E-82]]　文档源不可读或任务包不可派发
    - 触发：文件被删、解析失败、缺协议字段或版本不一致；或合法任务包的 ready=false
    - 期望：源不可读时保留全部记录与快照、提示原因并冻结新派发；合法但待契约复核时仅阻止该任务派发并说明 reasons，不清空数据、不视为代码验收失败

## 实施沉淀

<!-- notes:begin -->
1. 幂等派发与在途运行防重：
并发派发不仅需要在数据库层面靠 runs 表的 `idempotency_key UNIQUE` 约束兜底，还必须在应用层先检查同任务在途活跃运行（queued、starting、running、reviewing 等状态）。两端并发派发时直接返回既有活跃 run 而非抛出阻断异常或另起子进程（E-126），同时捕获并发写入时 SQLite 抛出的 UNIQUE constraint failed 错误回退至已落库记录，彻底规避跨设备并发点击下的双进程冲突。

2. 批次推进与下一批启动的前置闸门：
批次状态流转坚持「全批任务均落地且批次置为 done」作为下一批启动的硬性充要条件（E-49、E-281）。若前置批次处于 running/paused 或存在任一未落地任务，`POST /batches/:id/start` 必须返回类型化 `E_VALIDATION` 并在 details 中明确写出 `previousBatchState`；同批任务失败时不阻塞其他无依赖任务继续执行，但批次整体停留在非 done 状态阻断下游。

3. 契约就绪态拦截与人工确认不可绕过：
无论自动调度、手动派发还是重跑接口，在创建运行前必须严格核验 `task.is_contract_ready`（AC 5、E-50、E-82）。未复核就绪的任务无论是否有上层人工强制指令均阻断并抛出 `E_DOC_CONTRACT_PENDING`，同时在 details.reasons 回吐未就绪原因，确保契约未稳定的任务绝不被派发；文档中途变更产生的新标记仅暂停后续自动派发，在途任务持续基于快照独立执行完毕。

4. 调度 Tick 内存互斥与重启断电免自动重派：
`scheduler-tick` job 与 `DispatchService.tick()` 双层采用内存排他锁互斥量，禁止并发 tick 与重入调用，保证放行评估与并发槽位计数在单时刻唯一。针对 daemon 重启或断电恢复场景，处于终态（interrupted、orphaned、failed、aborted）的运行在任何情况下禁止调度器自动重派（E-51），防止并发重跑重复写入已污染的工作区，重试权严格留给人工决策。
