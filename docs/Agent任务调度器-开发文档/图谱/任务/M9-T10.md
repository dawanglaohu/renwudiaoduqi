# M9-T10　审批卡与闸门交互

- 所属模块：[[M9]]　**客户端界面**——两端共用的那一套界面本身：多流监看、会话查看、审批与闸门、设置与配对、落地清单、按批次折叠的批次树与执行行呼吸灯、按窗口数呈现的任务流水线泳道与「会话已归档」历史行、顶栏两个流水线开关，以及同一套代码的窄屏降级。它只通过 M2 的契约与 daemon 通信，**界面里不含任何业务判定**（折叠默认值、「能否收口」、泳道分配、阶段推进与会话归档都是 daemon 给的字段）；指派面板的分组模型下拉、登录态徽标与刷新按钮、参照条的「来源」段同样只呈现 daemon 下发的字段，不算取值链
- 前置依赖：[[M9-T7]]、[[M8-T4]]
- 完成后解锁：[[M9-T20]]

## 输入 / 产出

- **输入**：M8-T4 的闸门数据
- **产出**：`components/gate-card.tsx`

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 审批卡**就地插在该流时间轴里**，禁止 import dialog、禁止 `createPortal`，**不弹全局模态**打断其他还在跑的流（[[E-109]]）
2) 四段固定顺序：要做什么／影响什么／**凭什么（带可点链接回产出该结论的那一步）**／三个动作，「改一下」不是可选项
3) 底部写明「无人应答不会自动批准，任务保持等待」
4) 全局只用一个未处理计数徽标提示
5) 手机上审批派发前闸门时文案必须写「批准派发」，**不得含糊成「同意」**（[[E-182]]）

## 必须处理的边界

- [[E-109]]　半自动命中审批点
    - 触发：某个流需要人批准，其他流还在跑
    - 期望：审批卡就地插在该流的时间轴里，全局只用一个未处理计数徽标提示；不弹全局模态打断其他还在跑的流
- [[E-182]]　审批文案含糊
    - 触发：用户在手机上审批「派发前闸门」
    - 期望：文案必须如实写「批准派发」，不得含糊成「同意」，否则用户不知道自己刚刚启动了一次运行

## 实施沉淀

<!-- notes:begin -->
- **内联渲染与模态禁令（E-109）**：审批卡必须直接就地内嵌于对应运行泳道的时间轴槽位中，禁止引入任何 Dialog 组件或 `createPortal` 挂载全局浮层。多流并行监看时，全局模态会遮挡正在运行的其他流，并造成整个调度服务已暂停的假象；审批卡仅阻断其所在单条流，其余流维持正常推进。全屏范围仅允许顶栏渲染唯一的 `GatePendingBadge` 计数徽标。
- **四段顺序与回溯链接不可裁剪**：严格遵循「要做什么 → 影响什么 → 凭什么 → 三动作」次序。第 2 段影响指标大数（26px 等宽）在可逆操作下采用 `--needs` 暖色、不可逆操作（如分支落地合入主干）强制采用 `--down` 警告色。第 3 段「凭什么」必须包含直达产生结论步骤的可点击回溯锚点（`data-action="goto-step"`），防止用户在长序列多步骤执行中丢失因果证据。
- **「改一下」不是可选项**：仅有「批准」与「拒绝」两种极端动作会诱导用户为了微调参数而被迫放行或全量打回重跑。审批卡始终常驻提供 `[改一下]` 操作通道，与 `[批准并继续]`、`[拒绝]` 组成三项固定动作。
- **移动端派发文案防歧义强制兜底（E-182）**：在手机视口（`isMobile` 或 `phone`/`phone-xs` 密度档）下审批派发前闸门时，主按钮文案强制计算为「批准派发」，绝不使用「同意」，避免移动端窄屏交互下误触启动长耗时真实任务。即使外部上层错误传入 `approveLabel="同意"`，组件内部判定逻辑也会将其防御性清洗为「批准派发」。
- **视觉层级与 Token 约束**：审批卡采用整卡全量暖色微染（`bg-[var(--needs-soft)]`）搭配 1px `var(--needs)` 边框，拒绝左侧 3px 彩条的低质感模板化手法。卡内 primary 批准按钮使用纯实底样式，禁止使用 `--glow` 辉光（`--glow` 规则限定全页仅左栏全局派发按钮可用）。
