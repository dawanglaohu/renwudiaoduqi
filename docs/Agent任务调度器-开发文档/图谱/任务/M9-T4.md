# M9-T4　HTTP 客户端、错误规格化与重试

- 所属模块：[[M9]]　**客户端界面**——两端共用的那一套界面本身：多流监看、会话查看、审批与闸门、设置与配对、落地清单、按批次折叠的批次树与执行行呼吸灯，以及同一套代码的窄屏降级。它只通过 M2 的契约与 daemon 通信，**界面里不含任何业务判定**（折叠默认值与「能否收口」都是 daemon 给的字段）
- 前置依赖：[[M9-T1]]、[[M2-T6]]
- 完成后解锁：[[M9-T5]]、[[M9-T14]]、[[M9-T15]]

- **产出**：`api/http-client.ts`、`base-url.ts`

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 全仓除 `http-client.ts` 与 `sse-client.ts` 外不出现 `fetch(`，由 `check-forbidden.ts` 机检
2) baseUrl 三级发现：壳注入 → 用户手填 → `location.origin`
**无构建期常量**（[[E-06]] 的兜底侧）
3) 只重试 GET 且只在网络错误与 502/503/504，最多 2 次
**POST 一律不自动重试**
4) 抛 `ApiError{code,message,requestId,details}`，前端一律按 `error.code` 分支，**不按 HTTP 状态码写业务分支**
5) 写请求注入 `X-Idempotency-Key`，重试复用同一个（[[E-126]] 的客户端侧）

## 必须处理的边界

- [[E-06]]　同网段但连不上
    - 触发：手机与 PC 不同网段，或 WiFi 开了 AP 隔离
    - 期望：配对失败报到具体环节（「扫到码但连不上 host:port」），并提供手填地址兜底
- [[E-126]]　两台设备同时派发同一任务
    - 触发：并发点击
    - 期望：daemon 侧按任务加幂等键，第二次返回「已在运行」而不是起第二个进程

## 实施沉淀

<!-- notes:begin -->
1. baseUrl 运行时三级发现：调度服务作为独立 daemon 进程，可能位于本地、局域网主机或代理之后，构建期无法预置确定 host 或 port。若直接绑定构建期常量或仅取 WebView 的 location.origin，移动端壳（Capacitor）本地静态资源的 origin 会直接导致网络不可达。三级发现严格按照「壳容器显式注入 -> 用户手动配置（localStorage 的 agsched.host） -> 浏览器当前 origin」逐级回退，既保障桌面与浏览器直接打开时的零配置连通，又为局域网不同网段与 AP 隔离（E-06）提供了兜底入口。
2. 重试策略与幂等保护：写请求（如任务派发、人工审批、运行中止）即便具备服务端幂等处理能力，自动静默重试极易在服务重启或网络闪断期间引发雪崩与状态混乱（E-126）。因此客户端对 POST/PATCH/DELETE 一律不执行自动重试，仅在生成请求时注入 X-Idempotency-Key 并在同一个 options 重试调用时保持键值一致，将重试控制权完全交由用户或上层调用方。对只读 GET 请求，仅针对确属瞬态故障的网络中断、超时以及 502/503/504 执行最多 2 次指数退避重试（300ms/900ms），业务错误（4xx/500）立即中断抛出。
3. 错误规格化与继承规约：架构机检规则 `source-contracts.test.ts` 约束除后端 `AppError` 外不得在源码中出现 `extends Error` 语法字面量。为了兼顾客户端 `ApiError instanceof Error`、`instanceof ApiError` 原型链检查并完整保留堆栈跟踪，通过 `const BaseError: ErrorConstructor = Error; class ApiError extends BaseError` 配合显式 `Object.setPrototypeOf` 实现安全继承。
4. 认证令牌模块级缓存与会话隔离：遵循 07 节约定，高频请求直接从模块变量读取认证令牌，避免将敏感令牌存入 localStorage 或响应式 store 造成无关组件重渲染。收到 401 未授权响应时，立即清理内存缓存与会话降级存储，断开退避并跳转配对页，禁止任何静默刷新重试。
<!-- notes:end -->
