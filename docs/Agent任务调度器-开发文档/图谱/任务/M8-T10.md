# M8-T10　派发真正拉起子进程并接通事件链

- 所属模块：[[M8]]　**派发调度**——决定什么时候把哪个任务、用哪个 agent 与哪个模型、以什么权限派出去，并按批次、并行窗口、每 agent 并发与路径冲突限流，在三个闸门处停或放行、失败或重派时重新入队；判定本批分支是否都进了 HEAD、触发收口运行、按收口报告派修复运行与管理收口轮次也归它；泳道（窗口槽位）分配、任务终态后的补位、查 bug 与收口模式两个开关的持久化同样归它——泳道分配是它算出的派生数据。凡涉及顺序、名额、放行、重派的都归它；任务指派写进派发快照、阶段取值链（任务指派 → 阶段覆盖 → agent 默认）与收口指派设置也归它——它是唯一决定「这一阶段用谁跑」的地方，M7 只消费结果
- 前置依赖：[[M1-T8]]、[[M4-T4]]、[[M4-T8]]、[[M4-T12]]、[[M5-T1]]、[[M5-T2]]、[[M6-T2]]、[[M6-T5]]、[[M8-T3]]
- 完成后解锁：[[M1-T11]]

## 输入 / 产出

- **输入**：M8-T3 的 `dispatch.createRun()` 与 tick 补位；M1-T8 的 `proc.spawnManaged()` 与 `LaunchSpec`；M4-T8 / M4-T12 的 `buildLaunchSpec()` 与 `mapEvents()`；M4-T4 的可用性；M5-T1 的 `prepareWorktree()`；M5-T2 的 base 解析；M6-T2 的 `runService.attachProcess()` 与收流；M6-T5 的 `killTree`
- **产出**：`service/dispatch.ts` 的 `launchRun(runId)`：`createRun` 落库事务返回后依次 `workspace.prepareWorktree()` → `adapters[agentId].buildLaunchSpec()` → `proc.spawnManaged()` → `runService.attachProcess(runId, process, {eventMapper: mapEvents})` → 迁移 `starting → running` 并写 `runs.pid`；`boot/container.ts` 把真实 `proc` / `adapters` / `workspace` 注入 `dispatchService`（容器的 `proc` 与 `adapters` 不再是空对象）；`test/integration/dispatch-spawn.test.ts`；`test/fixtures/dispatch/codex-session.ndjson`；`test/arch/dispatch-proc.test.ts`

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) `POST /api/v1/runs` 返回 200 后、集成测试 await 一次 tick 内：`runs.pid` 非空，`run.state_changed` 携 `from:starting` `to:running` 发出
假 `spawnManaged` 收到的 `LaunchSpec` 的 `file` / `args` 逐字等于该 agent `buildLaunchSpec()` 输出、`cwd` 为该任务 worktree 绝对路径、`shell:false`（[[E-42]]、[[E-70]]）
2) 假子进程按 `codex-session.ndjson` 逐行吐：`events.ndjson` 至少落一条 `agent_message_chunk` 与一条 `tool_call`，`events` 索引表落 `run.started` 与 `tool_call`，用 fetch 自写的 SSE 读取端收到同 id 的两条事件（[[E-140]]、[[E-142]]、[[E-10]]）
3) 假进程退出码 0 → 运行迁 `exited` 并进入 M7 机械检查入口（`evaluateMechanicalCheck` 被调一次，由 M7-T9 接进容器
本任务在集成测试里注入假 reviewService 断言调用）
退出码非 0 → `exited` 且 `run.exited.stderrTail` 非空（[[E-348]]）
4) `prepareWorktree` 失败 → 运行 `failed`、`E_WORKSPACE_UNAVAILABLE`、槽位释放且下一 tick 派下一个任务
agent 不可用 → 不 spawn、`E_AGENT_UNAVAILABLE`（[[E-76]]、[[E-40]]）
5) `services.dispatch` 与 `scheduler-tick` 走同一 `launchRun`，tick 补位派出的运行同样起进程
arch 测试断言 `service/dispatch.ts` 不 import `child_process`（08 节 proc 唯一出口）

## 必须处理的边界

- [[E-10]]　手机断网期间任务跑完
    - 触发：提醒产生时手机不在线
    - 期望：提醒事件在 daemon 侧按 event id 入队，手机重连后补推并去重，不得丢弃
- [[E-140]]　流里混入非 JSON 行
    - 触发：agent 输出启动 banner、warning、进度条
    - 期望：逐行 try/parse，解析失败的行归入原始日志并继续，绝不中断流或丢弃该行
- [[E-142]]　daemon 长跑内存增长
    - 触发：连续运行数天
    - 期望：内存只保留最近 N 条事件的环形缓冲，历史事件全部落盘按需回读
- [[E-348]]　运行零产出退出
    - 触发：任何 kind 的运行在首条内容事件（`agent_message_chunk`／`agent_thought_chunk`／`tool_call` 任一）之前进程退出（不论退出码，含 0）、启动超时或错误类事件；dsh 无流式时最终输出解析不出任何内容也算
    - 期望：判定只看事件 kind、不匹配 stderr／stdout 文本（与 E-330 同一结构规则）。实施运行（含 `origin=rework`／`wrapup-fix`）：`exited → reviewing → awaiting_human` 两跳（reason `exited_before_output`），**不跑机械检查、不派审查、不计 `rework_count`**，`tasks.lane_no` 置 NULL 并发 `lane.released{reason:'awaiting_human'}`（E-326）；审查运行走 E-62、查 bug 运行走 E-323、收口运行走 E-295。事务后重跑一次该 agent 的登录态探测（dsh 不探）。审批卡（`GateDto.context`）附退出码、退出信号、stderr 末 20 行（来自该 run 最后一条 `run.exited` 事件的 `stderrTail`，已脱敏，旧事件缺字段显示「无记录（旧运行）」）、刚探测的登录态，与固定提示句「agent 未产出任何内容就退出，常见原因：未登录、模型名不可用、参数被拒」，不写「未登录」定论；动作「重跑」（复用 `POST /runs/:id/rerun`）、「换 agent 重派」、「标失败」（`awaiting_human → failed`），手机端只有重跑与标失败；每次都转人不自动重试；同一 agent 多条泳道同时零产出各自转人、不暂停该 agent；启动超时与 spawn 失败仍走既有 `starting → failed`、手动停止不进本判定；内容事件之后才失败走既有路径并正常计数
- [[E-40]]　agent 未安装或不在 PATH
    - 触发：探测不到可执行文件
    - 期望：该 agent 标「未检测到」，不列清单且不可被选为派发目标；已指向它的任务在派发前就报错，而不是跑到一半失败
- [[E-42]]　模型名含 shell 元字符
    - 触发：模型名带空格、引号或 `;` `&` 之类
    - 期望：调用方传原始参数数组，业务层不拼命令串；原生程序直接传 argv，Windows 包装脚本仅由适配器按 08 节组装完整 ComSpec 命令，最终参数值与个数必须不变且不得执行额外命令
- [[E-70]]　下游 base 缺上游产出
    - 触发：上游任务改动尚未被用户落地进当前 HEAD 就要派下游
    - 期望：拒绝派发并说明「下游 base 缺上游产出」，同时提供「以上游任务分支为 base 建 worktree」的显式选项；绝不默默从旧 HEAD 起
- [[E-76]]　worktree 创建失败
    - 触发：磁盘不足或权限问题
    - 期望：该任务标「派发失败·工作区不可用」，释放窗口名额给下一个任务，不让整批卡死
