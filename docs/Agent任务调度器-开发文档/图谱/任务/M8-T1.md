# M8-T1　并发窗口计算与瓶颈归因

- 所属模块：[[M8]]　**派发调度**——决定什么时候把哪个任务、用哪个 agent 与哪个模型、以什么权限派出去，并按批次、并行窗口、每 agent 并发与路径冲突限流，在三个闸门处停或放行、失败或重派时重新入队；判定本批分支是否都进了 HEAD、触发收口运行、按收口报告派修复运行与管理收口轮次也归它。凡涉及顺序、名额、放行、重派的都归它
- 前置依赖：[[M3-T2]]、[[M4-T1]]
- 完成后解锁：[[M8-T2]]

## 输入 / 产出

- **输入**：M3-T2 的批次与窗口数；M4-T1 的并发上限
- **产出**：`domain/concurrency.ts`

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 实际并发取 `min(窗口数, 每 agent 上限, 用户设定)`，并显示这三者中**哪一个成了瓶颈**（[[E-52]]）
2) 单 agent 并发已满但窗口还有空位时，空位让给其他 agent 的任务，不空转等待（[[E-47]]）
3) 窗口数为 1 或依赖纯串行时退化为逐个派，**不报错、不提示「无法并行」**（[[E-48]]）
4) 纯函数实现，可被直接单测
5) 用户设的窗口数只是**上限**，实际并发取 min(设置, 每 agent 上限, 机器资源, 路径冲突)，**设置值不被运行时静默改写**（[[E-245]]）

## 必须处理的边界

- [[E-245]]　窗口数设得比机器扛得住的大
    - 触发：用户把窗口数设成 6 但机器只跑得动 2
    - 期望：设置值只是**上限**，实际并发取 min(设置, 每 agent 上限, 机器资源, 路径冲突)；**设置值不被运行时静默改写**，UI 显示是哪一项成了瓶颈
- [[E-47]]　单 agent 并发满但窗口有空位
    - 触发：某 agent 达到并发上限，整体窗口未满
    - 期望：空位让给其他 agent 的任务，不空转等待
- [[E-48]]　窗口数为 1 或依赖纯串行
    - 触发：依赖链无法并行
    - 期望：退化为逐个派，不报错、不提示「无法并行」
- [[E-52]]　并发瓶颈来源不明
    - 触发：实际并发数低于用户预期
    - 期望：实际并发取 min(窗口数, 每 agent 上限, 用户设定)，UI 显示这三者中哪一个成了瓶颈；用户可向下调，向上超过窗口数需显式解锁并提示后果

## 实施沉淀

<!-- notes:begin -->
用户设定只作上限、绝不静默改写（E-245）：`userSetting` 表达的是用户意图天花板，在受到机器资源瓶颈（`machineResource`）或同批路径冲突（`pathConflictLimit`）限制时，函数仅压低 `effectiveConcurrency` 并将瓶颈归因为物理约束，返回值中完整保留未被篡改的原始 `userSetting`。若在调度期静默重写用户配置，机器资源释放后用户设定将不可恢复，且前端无法向用户归因「为什么当前只跑了 2 个窗口」。

多因素打平时的确定性裁决（E-52）：当外部硬件限制、每 agent 上限、依赖窗口与用户设置数值打平时，`bottlenecks` 数组完整保留所有并列因子供前端展示，单值 `bottleneck` 严格遵循「路径冲突（硬文件锁） > 机器资源（硬件瓶颈） > 每 agent 上限（配额限制） > 拓扑窗口（依赖图深度） > 用户设定（偏好参数）」优先级排序，防止多端在展示瓶颈时因并列打平产生闪烁或语义分歧。

单 agent 满额空位顺延机制（E-47）：`allocateConcurrencySlots` 遍历候选任务队列时，若某一高优先级任务因所属 agent 活跃运行数已达 `maxConcurrency` 而无法派发，调度器直接将其标记为 `agent_limit_reached` 并将空余窗口额度留给后续排队且所属 agent 仍有容量的任务，绝不阻塞整个窗口或空转等待。

纯串行退化无害化（E-48）：当依赖完全线性拓扑或 `windowCount <= 1` 时，调度计算仅置位 `isDegradedToSerial = true` 并将有效并发设为 1，逐个派发候选任务，绝不向外抛出异常或展示「无法并行」等警告文案。
<!-- notes:end -->
