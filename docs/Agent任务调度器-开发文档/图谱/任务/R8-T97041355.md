## 实施沉淀

<!-- notes:begin -->
1. **Jev 裁决落地与风险说明**：
   - 裁决依据：Jev adjudicate pick=A（置信度 low 0.33，记风险；spec_change=yes）。
   - 核心规则：仅在 agent 自身协议提供结构化错误字段（如 JSON-RPC error 对象的 code/type）时才精确归因为 `run.model_rejected`；绝不从 stderr 或 free-text 字符串正则猜测。无结构化拒绝信号时一律退回 E-348（零产出转 awaiting_human，reason: `exited_before_output`）。
   - 风险：若厂商变更了 error 结构或未提供结构化 code，模型名无效将表现为 E-348 人工卡片而非直接标失败。目前实际验证的 agent 家数为 1 家（Codex 原生 app-server）；Claude 及 generic-acp 能力位声明 `reportsModelRejection: false`。
2. **E_MODEL_INVALID 移除决策**：
   - 模型失效在派发异步化后不再作为 HTTP 同步创建的 422 错误抛出，统一由子进程事件管道触发 `run.model_rejected`。因此从 `routes.ts`、`codes.ts` 以及 10 节错误码表同步剔除，经 `scripts/check-error-codes.mjs` 校验 48 个错误码完美一致。
3. **架构守卫与泳道释放**：
   - `handleModelInvalid` 在 `rerun.ts` 内保证了 `runsRepo.updateState({ state: 'failed', queuedReason: '派发失败·模型无效' })`、`tasksRepo.clearLaneNo(taskId)`、发布 `lane.released{reason:'failed'}`，并通过 `gatesRepo.supersedePendingByRunIds` 使审批卡失效。
   - `attachProcess` 在分发事件时若遇 `run.model_rejected`，于事务写入前同步调用 `handleModelInvalid`，使运行在进程 exit 到达前已进入终态，确保随后的退出事件自然跳过 E-348 的 `exited -> reviewing -> awaiting_human`。
   - Arch 规范在 `dispatch-proc.test.ts` 中建立机械防线，禁止在 `service/` 与 `jobs/` 下对 stdout/stderr 文本做猜词匹配。
