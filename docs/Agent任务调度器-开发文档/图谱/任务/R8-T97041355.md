## 实施沉淀

<!-- notes:begin -->
1. **Jev 裁决落地与风险说明**：
   - 裁决依据：Jev adjudicate pick=A（置信度 low 0.33，记风险；spec_change=yes）。
   - 核心规则：仅在 agent 自身协议提供结构化错误字段（如 JSON-RPC error 对象的 code/type）时才精确归因为 `run.model_rejected`；绝不从 stderr 或 free-text 字符串正则猜测。无结构化拒绝信号时一律退回 E-348（零产出转 awaiting_human，reason: `exited_before_output`）。
   - 风险与当前阻断：实际验证的模型专用结构化拒绝信号为 0 家。Codex CLI 0.156.1 与 0.157.0 的真实无效模型运行在 app-server `turn/completed` 中只有 `error.codexErrorInfo: other`，没有模型专用 code/type；exec 也只有自由文本。当前六家 adapter 的 `reportsModelRejection` 均为 false。正向映射测试只验证假设的未来字段，不能证明本任务验收 2；模型无效的零产出运行仍按 E-348 转人工。
2. **E_MODEL_INVALID 移除决策**：
   - 模型失效在派发异步化后不再作为 HTTP 同步创建的 422 错误抛出。只有未来 agent 提供可核查的模型专用结构化拒绝信号时，才允许经子进程事件管道触发 `run.model_rejected`。因此从 `routes.ts`、`codes.ts` 以及 10 节错误码表同步剔除。
3. **架构守卫与原子提交（返工第 1 轮 R1/R2）**：
   - `handleModelInvalid` 在 `rerun.ts` 内使用 `unitOfWork.run` 事务保证 `runsRepo.updateState({ state: 'failed', queuedReason: '派发失败·模型无效' })`、`tasksRepo.clearLaneNo(taskId)`、`gatesRepo.supersedePendingByRunIds` 原子提交。
   - 事务提交后，状态机产生的事件先落盘至 `logstore.appendEvent` 再由 EventBus 发布。
   - `attachProcess` 在收到 `run.model_rejected` 时，先执行 `await ingestEvent(runId, env)`（先落盘到 events.ndjson 再发布到 bus），随后再异步调用 `handleModelInvalid`。所有写操作由 `trackWrite` 统一纳入 `pendingWrites` 屏障。
   - 子进程在模型被拒后即使紧接着退出，`onExit` 中的 `while (pendingWrites.size > 0)` 屏障确保落盘与状态迁移已执行完毕，退出处理器检查到 run 已是 terminal 态（failed），直接绕开 E-348 零产出逻辑，杜绝竞争与误入 awaiting_human。同时增加异常捕获记录与回归测试。
   - 假设的 `turn/failed` 与带模型专用 code/type 的 `turn/completed` 测试只验证解析器条件逻辑。真实 Codex app-server 的通用 `codexErrorInfo: other` 负例以及自由文本与普通 stderr 负例保持不归因；正向真实录制和生产入口复验仍待厂商信号。
