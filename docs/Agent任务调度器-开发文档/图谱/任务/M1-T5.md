# M1-T5　磁盘占用统计、写满兜底与受限删除原语

- 所属模块：[[M1]]　**运行底座**——让 daemon 在这台机器上稳定跑起来并把字节落到磁盘上：进程单实例与端口、启动自检、开机自启注册、数据目录、结构化存储的连接与迁移、日志正文的追加写与字节偏移索引、以及全部平台差异（进程树终止、路径规范化与长路径、配置目录、子进程编码）的唯一收口。凡与操作系统、磁盘、进程存活打交道而不带任何业务概念的都归它
- 前置依赖：[[M1-T4]]
- 完成后解锁：[[M6-T9]]

## 输入 / 产出

- **输入**：M1-T4 的 logstore
- **产出**：`disk-watch` job、`deleteByPath` / `truncate` / `usage` 三个不带业务语义的原语、`http/routes/system.ts`

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 占用超阈值发 `system.disk_warning` 并置「停止新派发」标志（[[E-103]]）
2) 存储盘写满时立即停止新派发并明确报错
恢复后能继续追加且已有记录不损坏（[[E-104]]）
3) M1 只上报写满，**绝不自行删除任何正文**（[[E-205]]）
4) 收到白名单目录之外的删除请求一律拒绝并记违规日志（[[E-206]]）
5) 删除目标正被读取（EBUSY）时返回可重试错误而非抛异常（[[E-204]]）

## 必须处理的边界

- [[E-103]]　磁盘占用达告警阈值
    - 触发：捕获的日志累积过多
    - 期望：顶部横幅列出占用最大的几个任务，提供「按任务 / 按时间归档」的手动入口；默认不自动删除
- [[E-104]]　存储盘写满
    - 触发：追加写失败
    - 期望：立即停止新派发并明确报错；恢复后要能继续追加，已有记录不得损坏
- [[E-204]]　要清的文件正被读
    - 触发：M6 判定某份正文该清，但会话查看器正按偏移分段读它（Windows EBUSY）
    - 期望：M1 的删除原语返回**可重试错误而非抛异常**；M6 本轮跳过该文件、下一轮重试，不向用户报错
- [[E-205]]　磁盘写满时谁来删
    - 触发：M1 检测到写满
    - 期望：M1 **只上报「写满」事件并停写/降级，绝不自行删除任何正文**；由 M6 按策略决定删哪些；策略判定「无可删」则升级为告警并暂停对应运行的写入
- [[E-206]]　清理候选集越界
    - 触发：候选集里混进了任务记录或三段快照
    - 期望：候选集只能由 M6 按「自己捕获的运行输出」目录白名单枚举生成；**M1 收到白名单目录之外的删除请求一律拒绝执行并记违规日志**

## 实施沉淀

<!-- notes:begin -->
- **白名单防御与原语无业务语义**：`deleteByPath` 与 `truncate` 仅核验路径是否归属于 `whitelistRoot`（运行日志目录），严禁向上穿越，同时将 `app.db`、`daemon.json`、`pairing-code.txt`、`instance.lock` 列入防护黑名单。原语不感知任务状态、三段快照或保留策略等业务概念；越界请求一律拒绝并触发违规日志记录（E-206）。
- **占用与锁异常非异常化**：Windows 平台会话查看器等分段读取文件时会独占文件句柄导致 `EBUSY`/`EPERM`。若原语直接抛出原生异常将导致清理流程崩溃。原语就地拦截该错误并返回 `{ ok: false, retryable: true, code: 'EBUSY' }`，由业务层跳过当前轮次并在下轮重试（E-204）。
- **写满熔断与 M1 只报不删原则**：追加写失败（`ENOSPC`）或巡检超过告警阈值时，M1 立即触发 `isDispatchHalted` 标志并发布 `system.disk_warning` 事件，但绝不自行删除任何正文（E-205）。日志清理与归档决策完全收归上层策略模块。底层写满时已有正文字节与 SQLite 索引不发生损坏，待空间释放后可继续追加（E-104）。
- **后台巡检隔离与防重入**：`disk-watch` 遵循 5 分钟定时调度，仅调 `systemService` 统一业务接口，不持有 HTTP 上下文，不直接操作底层存储；每次 tick 设内存防重入锁，内部捕获所有异常转交日志记录，杜绝抛入 `unhandledRejection`。
<!-- notes:end -->
