- 前置依赖：[[M9-T1]]
- 完成后解锁：无，它不卡别人

## 输入 / 产出

- **输入**：07 节的七条路径
- **产出**：`app/routes.tsx`、`navigateTo()`、`route-guard.tsx`

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 七条平铺路径 + 两个单段参数，hash 模式
三种加载源（daemon `/`、`tauri://localhost`、`https://localhost`）下行为一致
2) 命中未登记 hash 时渲染「未知路径」页并给「回到运行甲板」，保留顶栏，**绝不白屏、绝不抛异常**（[[E-222]]）
3) 路径参数指向不存在的对象时由**页面自身**渲染「该运行不存在或已被清理」，不由路由层判 404（[[E-223]]）
4) 首次加载 hash 为空时启动即归一化为 `#/`，**无中间态白屏**（[[E-224]]）
5) 组件内不出现 `location.hash = ...`，导航一律经 `navigateTo()`

## 必须处理的边界

- [[E-222]]　命中未登记的 hash
    - 触发：`#/xxx` 或 `#/run/` 缺参数
    - 期望：渲染「未知路径」页并给「回到运行甲板」，保留顶栏；**绝不白屏、绝不抛异常**
- [[E-223]]　路径参数指向不存在的对象
    - 触发：运行已清理、任务已从文档移除
    - 期望：由**页面自身**渲染「该运行不存在或已被清理」，不由路由层判 404，壳与顶栏保持在位
- [[E-224]]　壳内首次加载 hash 为空
    - 触发：`tauri://localhost`、`https://localhost`、daemon 的 `/` 三处加载
    - 期望：启动即归一化为 `#/`，**不得出现无 hash 的中间态白屏**

## 实施沉淀

<!-- notes:begin -->
- 为什么采用平铺 hash 路由而非 browser history：同一套构建产物需被 daemon 静态托管根路径 `/`、桌面壳 `tauri://localhost` 以及移动壳 `https://localhost` 三处直接消费。history 模式要求三处宿主分别维护 fallback 重写逻辑，且桌面/移动通知系统唤起深层路由时只需传递 `#/run/:id` 即可由 WebView 原生调度。
- 为什么路由层决不校验对象存在性（E-223）：若路由匹配时耦合实体检查，在数据未完全同步或弱网断连期间易将合法对象瞬时误判为 404，破坏壳与顶栏布局；将参数校验限定在单段 URL 语法，而将实体存在状态交由页面与容器通过服务端事件与快照自主呈现「该运行不存在或已被清理」，可保持壳架构绝对稳定。
- 为什么必须同步快照而禁止异步 useEffect 解析（E-224）：通过 `useSyncExternalStore` 与模块级 `initializeHash()` 紧密配合，首屏初始快照从第 0 帧起即同步归一化为有效路由（如 `#/`），彻底消除了异步 state 初始化时产生的空白中间帧。
- 鉴权守卫架构定点约束：守卫仅在 `route-guard.tsx` 单点执行，只检查内存中是否存在设备令牌；除 `#/pair` 作为唯一免守卫路由外，未配对访问一律强制收敛到配对流程，下辖业务页面与展示组件明令禁止再判登录态或拓展角色分支。
<!-- notes:end -->
