# M3-T3　派发快照与三个变更标记

- 所属模块：[[M3]]　**文档接入**——把 `docs-data.js` 变成本产品唯一的任务真相源（任务、依赖、批次、并行窗口、验收标准、边界编号、实施与审查两段提示词），并负责内容指纹、派发时快照与文档重出后的三个标记；收口提示词 `dispatchBatches` 的按任务集合匹配也归它。凡「这条数据来自文档」的都归它
- 前置依赖：[[M3-T2]]
- 完成后解锁：[[M3-T5]]、[[M8-T9]]

## 输入 / 产出

- **输入**：M3-T2 的任务表
- **产出**：`repo/dispatch-snapshots.ts`、比对逻辑、横幅数据

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 派发那一刻把 input/output/accept、两段提示词、contract_hash 与有效路径作为同一版本逐字快照进运行记录（[[E-19]]）
2) 文档重出后逐字符比对产出三个布尔标记：任务已消失／验收标准已变／提示词已变
契约哈希不同也纳入提示词变更标记，不能因任务行相同漏掉范围或条款变化，并给出受影响任务的过滤列表（[[E-77]]、[[E-78]]）
3) 任务 id 消失但仍有在途运行时不终止不删记录，标「已从文档移除」并禁止再次派发（[[E-77]]、[[E-18]]）
4) 同一任务重派多轮时比对只针对**最近一次**派发快照，历史轮次只读保留（[[E-80]]）
5) 文档在派发瞬间被重新生成时以派发那一刻读到的内容写快照，事后补比对，**绝不回滚已发出的运行**（[[E-81]]）

## 必须处理的边界

- [[E-18]]　任务从文档中消失
    - 触发：文档重新生成后某任务 id 已不存在，但本地有运行记录
    - 期望：标「文档中已移除」并保留历史与会话链接，不静默删除
- [[E-19]]　验收标准被事后改动
    - 触发：同一 id 的 input/output/accept 文本被改过
    - 期望：派发时把这三段快照进任务记录；列表标「文档已更新，与派发时不一致」
- [[E-77]]　任务从文档消失但仍在跑
    - 触发：新文档里该任务 ID 已不存在，本地有在途运行
    - 期望：不终止运行、不删记录，卡片标「已从文档移除」，禁止再次派发，允许手动归档
- [[E-78]]　验收标准在验收前变了
    - 触发：accept 段文本变了且任务处于「已退出未验收」
    - 期望：卡片并列展示「派发时快照 / 当前文档」两段验收标准，主操作变为「重派」，但仍允许用户按旧标准手动判为已落地
- [[E-80]]　同任务重派多轮
    - 触发：一个任务有多次派发快照
    - 期望：比对只针对「最近一次派发的快照」，历史轮次的快照各自只读保留
- [[E-81]]　文档在派发瞬间被重新生成
    - 触发：派发与重新生成撞在一起
    - 期望：以派发那一刻读到的内容写入快照，事后补一次比对；绝不回滚已发出的运行

## 实施沉淀

<!-- notes:begin -->
1. **多轮派发快照的比对基准（E-80）**：同一任务发生重派时，比对基准必须严格锚定于该任务 `created_at DESC, id DESC LIMIT 1` 的最近一次快照。历史轮次的快照只读保留，不得原地 UPDATE 覆盖，否则回溯审查无法重建当时上下文；若以最初快照比对则会在多轮后产生虚假变更标记。
2. **契约哈希纳入提示词变更判定（E-77、E-78）**：文档重出后，提示词模板字符串可能完全未变，但任务有效路径（taskPaths/supportPaths）或边界约束调整会导致 `contract_hash` 变化。比对逻辑将哈希差异视同提示词变更（`hasPromptChanged = true`），防止遗漏影响代码实施范围的隐式变更。
3. **派发并发与在途运行不可逆保障（E-81）**：派发瞬间与文档重新导入发生碰撞时，快照严格以派发时读到的数据落库，运行由调用方随后创建。后续比对只刷新 tasks 表的 `has_accept_changed` 和 `has_prompt_changed` 标记与横幅，绝不回滚、中止或级联变更正在运行的进程。
4. **移除任务与在途运行隔离（E-18、E-77）**：新文档中消失的任务仅设置 `is_removed_from_doc = 1`，不删除任务记录及外键依赖（runs、events、logs）。在途运行保持正常推进，但入口处 `takeSnapshotForTask` 强制抛出 `E_TASK_REMOVED_FROM_DOC`，彻底切断再次派发路径。
5. **派发即换比对基准（E-19、E-78、E-80）**：`takeSnapshotForTask` 落库后把该任务的 `has_accept_changed`／`has_prompt_changed` 归零。新快照读到的内容此刻就是当前文档，相对上一个快照的变更标记已不成立；不归零会让任务卡留着过期角标，并让 E-180 的「旧快照盲跑」拦截误伤刚派发的新快照。
6. **阻断原因分类（E-82）**：禁派发有两种成因，错误码必须分开——只有真的从文档消失才报 `E_TASK_REMOVED_FROM_DOC`；仍在文档里但 `is_contract_ready = 0` 报 `E_DOC_CONTRACT_PENDING` 并把 `contract_reasons_json` 解成 `details.reasons`。混用会让「待复核」的任务被标成「已移除」，也吞掉前端要展示的 reasons。
