## 实施沉淀

<!-- notes:begin -->
- **实现选择**：
  1. 真实端到端测试链路不使用任何 mock transport、路由拦截、sessionStorage 注入或代码测试钩子，通过正式 daemon bootstrap (`bootstrapServer`)、真实 Vite 生产构建产物托管、真实 Chromium 浏览器（Playwright）完整串联配对、导入向导、逐任务指派、阶段派发、子进程运行、SSE 事件流推送、人工审批卡流转及八段收口报告呈现。
  2. 真实状态驱动 GIF 录制：采用纯 TypeScript 实现标准的 GIF89a 调色板与 LZW 变长字典编码器，无任何 native 库依赖（如 gifencoder、canvas），从浏览器真实 `page.screenshot()` 取帧，按 8 个真实业务状态节点记录，产出 `e2e/artifacts/batch-14-composition.gif` 及对应的 `timeline.json`。
- **踩坑与缺陷修复**：
  1. `packages/daemon/src/service/dispatch.ts` 在 wrapup 模式下构建 launchSpec 遗漏了 `execPath: wrapupLaunchSpecData.execPath`，导致在 Windows 等平台下，未传入绝对路径的 agent 回落为相对可执行名 `'codex'`，被平台分类器 `classifyPathForHost` 拒绝并报错 `Invalid executable path for win32: codex`，触发 `spawn_failed`。补齐传入 `execPath` 彻底解决该问题。
  2. Windows 平台下的 `wrapForComSpec` 会检测命令行参数中是否包含 `\n` 或 `\r`。在 wrapup 运行中，整篇八段收口提示词作为参数传递，必然触发参数拒绝。为此在 Windows 下通过系统内置 `csc.exe` 动态编译几 KB 的原生 `composition-agent.exe` PE 二进制，避免走 ComSpec，透明透传标准流与换行参数。
  3. 收口任务启动前必须释放落地任务的泳道占用：在直接更新数据库将前置任务标为 `landed` 时，必须同步将 `tasks.lane_no = NULL` 与 `runs.lane_no = NULL`，否则调度服务判定所有泳道被占满，收口任务会一直卡在 `queued` 状态无法派发。
- **关于收口记录与文档系统**：
  1. 契约中声明的收口记录 `_run/batches/batch-14-20260925.md` 包含返工任务（```task）。按照 `build_docs.py` 第一性原理检查，包含返工任务的收口记录其 `verdict` 必须保持 `open`，且作为系统源文件参与输入指纹计算。因此在该返工任务落地前，保持原记录不改写，符合“原任务与原收口记录不改写”原则，待本返工任务落地后在下一轮批次收口中生成关闭记录。
