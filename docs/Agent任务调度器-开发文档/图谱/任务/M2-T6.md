## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 架构测试断言「Fastify 实际注册的 method+path 集合 === `routes.ts` 常量表」，多一条少一条都失败
2) 请求体加字段只改 TS 接口未改 Schema 时 `tsc` 报错（键清单 `as const satisfies` 穷尽断言）（[[E-215]]）
3) 只改 Schema 未改 TS 接口时契约测试失败（[[E-216]]）
4) 所有请求体 Schema 统一 `additionalProperties:false`，多余字段返回 400 并列出字段名，不静默丢弃（[[E-217]]）
5) `check-error-codes.mjs` 断言 `codes.ts` 的键集合与 10 节错误码表逐行一致，**方向是「文档为源、代码为投影」**，不一致即 `pnpm -w check` 失败

## 必须处理的边界

- [[E-215]]　加字段只改了类型
    - 触发：请求体加字段，改了 TS 接口没改 JSON Schema
    - 期望：**编译期失败**：每个请求体类型旁强制配一份 `as const satisfies readonly (keyof T)[]` 的键清单并做穷尽断言，漏字段则 `tsc` 报错
- [[E-216]]　加字段只改了 schema
    - 触发：改了 JSON Schema 没改 TS 接口
    - 期望：契约测试断言「`schema.properties` 的键集合 === 该类型的键清单常量」，不等即失败
- [[E-217]]　客户端发来多余字段
    - 触发：请求体含 schema 未声明的字段
    - 期望：所有请求体 schema 统一 `additionalProperties: false`，返回 400 **并在错误体里列出多余字段名**，不静默丢弃

## 实施沉淀

<!-- notes:begin -->
1. **Fastify 默认静默丢弃多余字段（E-217 防御）**：Fastify 默认内置 AJV 配置开启了 `removeAdditional: true`，在收到未声明字段时会自动将其剥离并继续放行，导致显式声明 `additionalProperties: false` 的 Schema 依旧返回 200。必须在 `Fastify({ ajv: { customOptions: { removeAdditional: false, allErrors: true } } })` 中显式重置为 `false`，并开启 `allErrors: true`，才能让 AJV 产生 `additionalProperties` 校验错误并将全部未知属性名收集到 `error.validation`。
2. **Fastify 封装边界与子作用域错误处理**：Fastify 的子 scope（如挂载在 `/api/v1` 的 `apiScope`）在路由注册阶段会固化该作用域当前的错误处理行为。当插件按 `00→90` 顺序注册时，`90-error-handler` 挂载在根实例尾部，子 scope 的路由在预验证失败时不会自动回溯到后注册的根错误处理器，而是回落至 Fastify 原生报错格式。因此在 `routesPlugin` 内部对当前 `apiScope` 实例显式调用 `await errorHandlerPlugin(instance, {})` 注入统一错误格式，确保 `/api/v1` 下所有端点的请求校验异常均严格落入 `{error: {code: 'E_VALIDATION', details: {extraFields}}}` 信封。
3. **双向防漂移三角锚定（E-215、E-216）**：为杜绝手写 TS 接口与 JSON Schema 之间的字段漂移，构建「TS 接口 ↔ 键清单常量 ↔ JSON Schema」三位一体的闭环：
   - 类型侧：每个请求体配套 `as const satisfies readonly (keyof T)[]`，并辅以 `[Exclude<keyof T, Tuple[number]>] extends [never] ? true : never` 编译期穷尽赋值断言，任何 TS 接口增加字段未同步键清单即触发 `tsc` 报错（E-215）。
   - Schema 侧：架构测试通过 `REQUEST_BODY_SCHEMAS` 遍历全部 11 处 Schema，对比 `Object.keys(schema.properties)` 与键清单常量集合完全相等，任何 Schema 增加字段未同步 TS 接口即触发测试红灯（E-216）。
4. **错误码文档为源的投影约束**：10 节表格是全仓错误码唯一事实源。`scripts/check-error-codes.mjs` 解析 Markdown 表格作为源（Source of Truth），核验 `codes.ts` 每条错误码的 `code`、`origin`、`defaultHttpStatus` 与 `retryable`，并串联进入 `pnpm -w check` 成为发布阻断门禁。
5. **2026-09-11 复验补丁**：`pipeline-automation-20260910` 在 10 节错误码表新增 `E_BATCH_NOT_WRAPPABLE`、`E_WRAPUP_ROUND_LIMIT`、`E_FIX_RUN_IN_FLIGHT` 三条（真正消费它们的是 M8-T6/M8-T7 的收口与撤回运行）。本任务负责的投影随之跟进：`codes.ts` 补齐三条，并把两处钉死数字改为由源推导——AC 5 的条数从 10 节原文现读并加断言「脚本已进 `pnpm -w check`」，AC 2 改为断言 `ROUTES` 里带 `bodySchema` 的端点集合与 `REQUEST_BODY_SCHEMAS` 集合相等。这样文档再增条目只会要求跟进 `codes.ts`，不会再让本任务测试因数字过期而红。
