# M9-T20　收口泳道、收口报告面板与批次落地清单

- 所属模块：[[M9]]　**客户端界面**——两端共用的那一套界面本身：多流监看、会话查看、审批与闸门、设置与配对、落地清单、按批次折叠的批次树与执行行呼吸灯、按窗口数呈现的任务流水线泳道与「会话已归档」历史行、顶栏两个流水线开关，以及同一套代码的窄屏降级。它只通过 M2 的契约与 daemon 通信，**界面里不含任何业务判定**（折叠默认值、「能否收口」、泳道分配、阶段推进与会话归档都是 daemon 给的字段）；指派面板的分组模型下拉、登录态徽标与刷新按钮、参照条的「来源」段同样只呈现 daemon 下发的字段，不算取值链
- 前置依赖：[[M9-T19]]、[[M9-T10]]
- 完成后解锁：[[M9-T21]]

## 输入 / 产出

- **输入**：M9-T19 的批次树与 `pulse-dot`；M9-T10 的审批卡；`GET /batches/:id/wrapups` 与 `POST /batches/:id/wrapup`
- **产出**：`components/wrapup-report.tsx`、`features/run-deck/wrapup-panel-container.tsx`、`components/stream-column.tsx` 的收口头部分支、`components/gate-card.tsx` 的条件动作与 `features/run-deck/use-gate-card.ts`、`pages/landing-page.tsx` 的批次级清单

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) `kind='wrapup'` 的运行占一条普通泳道，头部「批次收口 · 第 N 轮 · 第 M 批」，停止控件、参照条、运行轨渲染在 kind 分支之外，[[E-236]] 的逐档单测加 kind 维度断言停止控件存在（[[E-297]]、[[E-106]]）
2) 收口报告面板只展示 daemon 已解析字段（tests / findings / unassigned / landing / reportText），解析失败显示「解析失败」并直链原文，代码中不存在前端解析 `reportText` 的路径
findings 整行可点跳该任务，`isWellFormed=false` 行尾 chip「格式不全」，`promptSource='builtin'` 时头部 chip「文档未提供收口提示词」（[[E-297]]、[[E-286]] 的呈现侧）
3) 批次标题「收口」按钮只在 `canWrapup` 且非手机档渲染，请求在途禁用，接受后不改状态等 `batch.wrapup_started`
`E_BATCH_NOT_WRAPPABLE` / `E_WRAPUP_ROUND_LIMIT` 按 `details.reason` 给具名文案贴在该批标题下（[[E-157]]）
4) 审批卡第四个条件动作「投递原文到实施会话」（ghost）只在 `reviewVerdict='incomplete'` 且 `reworkText` 非空时出现，按目标运行 `capabilities.canReply` 灰掉并带 title，走 `POST /runs/:id/messages`，未送达时卡内 inline notice + 原文可复制（[[E-278]]、[[E-117]]、[[E-113]]）
5) 批次级落地清单列每轮收口分支与各修复分支各一行，附可复制命令，`inHead` 为真的行打勾（[[E-74]] 的批次侧）

## 必须处理的边界

- [[E-106]]　桌面端多流并置
    - 触发：同时 5 个以上运行流
    - 期望：多流并置（分栏或网格），每流各自带常驻停止控件；不做「一次只能看一个」的模态
- [[E-113]]　消息投递失败
    - 触发：进程已死或管道已断
    - 期望：消息落地为「未送达」并保留原文可复制，绝不静默丢弃或假装已发出
- [[E-117]]　agent 不具备注入能力
    - 触发：后续接入的 agent 没有消息注入通道
    - 期望：「可回话」做成能力位，UI 按能力位灰掉按钮，而不是点了才报错
- [[E-157]]　写操作与事件流打架
    - 触发：客户端发起「中止运行中的任务」
    - 期望：走 POST 接口，最终状态一律以回流事件为准，UI 不拿 POST 响应体直接改状态
- [[E-236]]　某一档漏掉停止键
    - 触发：档位分支影响了控件存在性
    - 期望：停止控件与审批槽位**必须渲染在所有档位分支之外**；分支只允许影响布局与截断。**配一条按档位枚举逐档断言停止控件存在的单测，把 E-106 变成机检**
- [[E-278]]　返工块解析不出 R 条目
    - 触发：VERDICT 为 rework 但围栏块与 REWORK 段都没有 `R〈n〉` 条目，或 VERDICT 行缺失
    - 期望：标「未结构化」：`review_verdict=incomplete`，原文全文存 `rework_text`，转 `awaiting_human`；审批卡给「投递原文到实施会话」按钮，按能力位灰掉；不猜语义、不裁剪
- [[E-286]]　收口自报裁定与实际不符
    - 触发：RECORD 段写 clean 但 BUGS 有未修条目、NOT_FIXED 非空或 TESTS fail
    - 期望：有效裁定由内容算出（open），自报值只存 `declared_verdict`；两者不一致记 warn，UI 同时显示两者；绝不按自报放行
- [[E-297]]　收口运行的界面落位
    - 触发：收口运行没有 task_id
    - 期望：流甲板占一条普通泳道（头部写「批次收口 · 第 N 轮 · 第 M 批」），停止控件、参照条、运行轨与实施流一致；批次树在该批标题下挂一行「批次收口 · 第 N 轮」；收口报告面板只显示 daemon 已解析字段，解析失败显示「解析失败」并直链原文；手机端不出「收口」按钮
- [[E-74]]　用户要落地
    - 触发：任务已验收，准备合并
    - 期望：提供只读落地清单（worktree 绝对路径、分支名、diff 摘要、可一键复制的 `gh stack` 命令文本），复制而不执行

## 实施沉淀

<!-- notes:begin -->
**返工第 1 轮（R1–R5 已实现，R6 受环境阻断）**

**收口控件只有一个**　AC3 约束的「收口」按钮在 `components/batch-tree.tsx` 第 4 槽（M9-T19 的产出）。本任务把在途与具名原因**喂进那颗按钮**（`wrapupPendingBatchId` / `wrapupFailureByBatch`），把上一轮自建的 `BatchWrapupControl` 删掉，只留 `BatchWrapupFailureLine` 画拒绝原因。接线时若又冒出第二颗「收口」按钮，就是回退。

**批次收口状态是模块级 store**　`wrapup-panel-container.tsx` 里的按批次 store 由运行甲板与任务列表页共用（`useBatchWrapupOverview`），否则同一批在两个页面会各发一次 POST、各存一份在途态。收口轮次另存 `runId→round`，只从 daemon 的事件 payload 或收口记录的 `runId` 取，前端不算 `max+1`。

**泳道列表是过渡实现**　daemon 侧 `runs.lane_no` 只有列和 DTO，**没有任何地方赋值**（只有实施运行→审查运行的复制），`packages/shared/src/api/lanes.ts` 与 `GET /lanes` 也不存在——那归 M8-T8（仍开放）与 M9-T21（E-317、E-333）。所以 `buildDeckLanes()` 在 web 里按「daemon 给了 laneNo 就照它排，否则按开始时间→运行 ID 稳定编号」拼泳道，纯粹为了让甲板显示真实运行。Jev 采纳 A（high 0.97，spec_change=no）。M9-T21 落地 `GET /lanes` 时这段必须整体替换，别在它上面继续加派生逻辑。

**投递目标是实施运行**　审查运行判「未结构化」时，原文要投回**被审的实施会话**：目标是 `run.parentRunId`，`capabilities.canReply` 取的也是那条实施运行的能力位（不是审查运行自己的）。取错会让按钮的灰/亮与实际能否投递相反。

**能力位只认 daemon**　`RunCapabilitiesDto` 挂在 `GET /runs` 与 `GET /runs/:id` 上，`canReply` 逐运行由 `MessageService.canReply()` 回答（agent 位 ∩ 管道可写），`canResume` 取 agent 位。快照里的运行**没有**这一位（`SnapshotResponse.runs` 由 dispatch 的 `toRunDtoWithInHeadWarning` 出来，不经路由），所以甲板必须另取 `GET /runs`，不能图省事只读快照。

**`reworkText` 目前恒为 null**　原文在 daemon 侧**根本没落库**：`runs.rework_text` 不在任何迁移里，`RunRow` 不选它、`toRunDto` 不映射它，`service/rework.ts:787` 调 `updateReworkCount` 时**没传 `reworkText`**。本任务把客户端的取用路径（`RunDto.reworkText` → 审批卡原文 → 复制/投递）接通了，但真实服务里这一位永远是 null，所以「全文复制」在端到端上还差 daemon 三步：新迁移加列、repo 读列并映射、rework 服务把解析出的原文传下去。Jev 采纳 A（low 0.17，spec_change=unsure）——即本任务不越权改 `repo/runs.ts`、`service/rework.ts` 与迁移，由审查方补路径。

**快照的 gates 恒为空**　`service/dispatch.ts` 的 `getSnapshot()` 返回 `gates: Object.freeze([])`，所以甲板上的审批卡**不能**从快照取闸门；本任务改从 `GET /api/v1/gates` 取，按 `runId` 匹配待处理闸门。缺了这一步就只能画一颗点了没反应的「批准」。

**R6 的阻断点（两条，都不是本任务代码的问题）**　①产品入口 `node bootstrap.mjs` 在本机起不来：实例锁要求 `daemon.lock` 只对 Administrators/SYSTEM 可写，非提权会话既满足不了 DACL 也写不进锁文件（实测把目录 DACL 收紧后立刻 `Access denied`）。②改用 `startDaemon()` 注入点（仅替换锁适配器，其余全是产品代码）后服务确实起来了、真文档也导进来了（111 个任务 / 17 个批次 / 5 个 agent），但**每一次真实派发都在造工作树这一步失败**：`worktree.ts:213` 用 `executableName: 'git'` 走平台的固定搜索目录，而 git 不在那些目录里（`Executable not found in the fixed platform locations`），run 一律落到 `failed / workspace_unavailable`，错误还被 dispatch 的 catch 吞成同一句。没有一条运行能跑起来，就既凑不出五流并置，也走不到收口轮次（收口还要求整批已落地且分支都进了 HEAD）。这两条要出端到端 GIF 必须先解决：给 git 一个可配置/可解析的路径、以及非提权下的锁策略。

**收口控件的落点**　AC3 约束的那颗「收口」按钮长在 `components/batch-tree.tsx`（M9-T19 的产出），该文件不在本任务有效路径里；把在途禁用与具名原因穿进去必须同时改 `batch-tree.tsx` 与 `features/run-deck/run-deck-view.tsx`。本任务在有效路径内自建 `BatchWrapupControl`（`data-placement="under-batch-title"`），由父级挂到批次标题之下。接线时两处按钮并存就是重复，只能留一处：或把 pending/failure 从容器传进 batch-tree 的那颗按钮，或让 batch-tree 不再画按钮。Jev fork-1 取 A（medium），spec_change 判 unsure。

**「解析失败」只能来自事件**　daemon 解析不出八段时**不写 `batch_wrapups` 行**（`service/wrapup.ts` 的 `!parsed.ok` 分支只把运行转 `awaiting_human` 并开闸门），所以 `GET /batches/:id/wrapups` 里永远看不到失败轮。面板的失败条目因此只认 `batch.wrapup_finished` 的 `verdict='unparsed'`——那是 daemon 自己下的结论，不是前端读原文得出的。不要改成「wrapups 少一轮就显示解析失败」：那会把界面逻辑绑死到 daemon 的写库时机上。

**原文只当字符串**　`reportText` 仅进可展开块。任何 `split('BATCH_SUMMARY')`、`JSON.parse(reportText)` 一类写法都会被 `wrapup-report.test.tsx` 的源码扫描挡下（E-297 要的是机检，不是自觉）。

**能力位必须由外部给**　RunDto 与 SnapshotResponse 都没有 capabilities，`canReply` 只活在 daemon 的 adapter 里，客户端可见契约里不存在这一位。`useGateCard` 因此把它当输入，**缺失即 false**（灰掉并写明 `capabilities.canReply=false`）。反过来取「缺失即 true、等 POST 报 E_CAPABILITY_UNSUPPORTED」会把 E-117 退化成「点了才报错」，正是那条边界要禁的。

**幂等键跨重试复用**　容器把 `idempotencyKey` 存在 ref 里，被拒后重试复用同一个；http-client 对 POST 不自动重试，key 一换，daemon 侧就多算一次收口尝试（去重靠 `runsRepo.findByIdempotencyKey`）。

**「已接受」不等于「已开始」**　POST 成功后控件只置在途并保持禁用，批次状态一个字不改，等 `batch.wrapup_started` 回流才清在途并重取。不要从 POST 响应里读 `batch.state` 当界面状态。

**批次命令是拼出来的**　`BatchWrapupLandingDto` 只有 worktree / 分支 / diffStat，没有任务级 `GET /tasks/:id/landing` 那样的 `commands[]`（daemon 在 `workspace/landing.ts` 生成 `gh stack push`）。批次行按 worktree → 分支 → 裸命令三档回落拼出同一形态的 `gh stack push`，绝不执行。daemon 哪天补上 `commands[]`，这里应改成直读。

**轨列常驻但按插槽渲染**　`spineSlot` 与 kind/档位无关地渲染，但只在传了插槽时占位。M9-T21 的 `pipeline-lane` 把阶段链塞进 body；若这里无条件加 20px 轨槽，会与阶段行自己的 20px 轨列叠成两列。

**逐档 × 逐 kind 的机检**　`stream-column` 里 `kind` 只允许出现在 head 段内换文案。单测除 15 组 kind×tier 组合断言停止键/参照条/轨列/审批槽位都在，还扫源码断言 `data-action="stop-stream"` 之后不再出现 `kind ===` / `tier ===`，把 E-236 从「人肉看一遍」变成改动即失败的约束。

**`initialWrapups` 是一次性种子**　容器拿它当首次取数的替代，之后不再重放：调用方若每次都传新数组，同步回 state 会自激重渲染（React 只在 `Object.is` 相等时才跳过）。要刷新走 `refetch()` 或等 `batch.wrapup_*` 事件——收口轮次本来就是事件驱动新增的。`unparsableEntries` 相反可以合并，因为它带「没有新条目就返回原引用」的短路。

**复制逻辑暂有三份**　`features/landing/landing-container.tsx`、`wrapup-panel-container.tsx`、`use-gate-card.ts` 各有一份剪贴板降级链（clipboard API → execCommand → 失败返回 false）。`src/lib/` 不在本任务有效路径里，第三份先就近放着；下一个碰这几处的任务应把它收进 `lib/`。

**清单里的 `.tsx` 与仓库里的 `.ts`**　`gate-card.test.ts` / `stream-column.test.ts` 是既有文件（任务提示词自己的「代码位置」段也引 `.ts`）。新建 `.tsx` 会让同一组件出现两个测试文件，所以在既有 `.ts` 上扩写；只有真正新增的 `wrapup-report.test.tsx` 按清单新建。
