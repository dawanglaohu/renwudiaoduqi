## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 三个闸门（派发前／审查后／落地前）各自可设「自动」或「等我确认」，落地闸门默认 `manual`、可设 `auto`
`auto` 只表示审查 pass 且审查后闸门也为自动时直接进 `landed`（已验收），代码中不存在任何 git 写操作
`gateOverrides` 允许含 `landing` 且只影响本批尚未到达该闸门的任务（[[E-53]]、[[E-56]]）
2) 预设：半自动 = 派发自动 + 审查后等确认
自动 = 审查 pass 自动进下一个，审查非 pass 一律停
闸门设置存 `settings(key='gates')`，缺行返回内置默认不插行，`value_json` 非法回落默认并 warn 不退出，PATCH 三字段整体写入缺一即 `E_VALIDATION`，写成功发 `settings.gates_changed`（[[E-292]]） 2b) `task.landed` payload 带 `by` 取 auto 或 human 与 `gateId`
3) 闸门等确认而人长时间不来时该任务**释放并发额度、不占窗口**，其他任务继续，仅下游依赖被动等待（[[E-54]]）
4) 执行中途改开关只影响尚未到达该闸门的任务，不需重启批次（[[E-56]]）
5) 两端同时点确认时幂等，第二次提示「已由另一端确认」，不产生两次派发（[[E-57]]）
6) 人工操作优先级高于自动推进，批次可中途暂停／接管，自动派发不得覆盖人的判断（[[E-05]]）

## 必须处理的边界

- [[E-05]]　批次中途人工干预
    - 触发：一批任务跑到一半，用户手动改了某个任务状态
    - 期望：人工操作优先级高于自动推进；批次可在中途暂停/接管，自动派发不得覆盖人的判断
- [[E-292]]　闸门设置存储缺行或损坏
    - 触发：`settings` 表无 key=gates 行，或 `value_json` 非法/含未知值
    - 期望：缺行返回内置默认 `{dispatch:auto, review:manual, landing:manual}` 不插行；非法值回落默认并 warn，不退出、不覆盖坏值直到下一次 PATCH；PATCH 三字段整体写入，缺字段或值不在 auto／manual 返回 `E_VALIDATION`；写成功发 `settings.gates_changed` 让另一端刷新
- [[E-53]]　落地闸门可设自动
    - 触发：三个闸门各自可设「自动」或「等我确认」
    - 期望：落地闸门默认「等我确认」，可切到「自动」：自动只表示审查 pass 后直接进 `landed`（已验收），产品仍不执行任何 git 操作（决策 12）；UI 三个开关同一形态、第三个不再置灰，切到自动时行内常驻一句说明而不弹确认框
- [[E-54]]　闸门等确认而人长时间不来
    - 触发：夜间无人值守，任务停在闸门前
    - 期望：该任务释放并发额度、不占窗口，其他任务继续；仅其下游依赖任务被动等待
- [[E-56]]　执行中途改闸门开关
    - 触发：用户在批次跑到一半时改设置
    - 期望：只影响尚未到达该闸门的任务；已在闸门前等待的任务按新设置立即放行或继续等，不需重启批次
- [[E-57]]　两端同时点确认
    - 触发：手机与桌面同时对同一闸门确认
    - 期望：幂等，第二次提示「已由另一端确认」，不产生两次派发

## 实施沉淀

<!-- notes:begin -->
1. **落地闸门自动化的语义边界**：落地闸门 `auto` 仅代表当审查 pass 且审查后闸门也为自动时，任务直接跃迁至 `landed` 终态并广播 `task.landed` 事件，全链路严格杜绝包含任何 git commit/push/merge 写操作。
2. **坏配置的防御性保真**：`settings` 表解析坏配置时，采取「内存回落默认 + warn 告警 + 库内原样保留不覆盖」策略；若在读操作中自动写回默认值，会冲掉外部排查损坏现场的依据，只有显式通过 API PATCH 全量合法值时方可覆盖写入。警告信息经由容器注入的真实 warn 出口记录，杜绝静默吞掉。
3. **批次级闸门覆盖的隔离性**：`startBatch` 提交的 `gateOverrides` 在批次调度生命周期内隔离维护，仅作用于该批次尚未到达该闸门的处理流程，既不侵入修改全局 `settings(key='gates')` 持久化行，也不影响已决断或已通过该闸门的历史任务。
4. **中途改设置的平滑重裁决**：当全局闸门设置切换时（E-56），`updateGates` 把「写 `settings(key='gates')`」与「对本次变更为 `auto` 的闸门种类扫描 `state='waiting'` 的记录立即放行并推进下游」放进**同一个 `unitOfWork.run`**——08 节规定一个 HTTP 请求最多开一次事务、跨 service 的复合写必须聚进同一个 run，重裁决函数只写库并返回待发事件，`settings.gates_changed` 与放行事件一律等事务返回后才 publish；仍为 `manual` 的闸门继续等待，整个过程批次状态保持 `running`，无需也不得重启批次。
5. **并发决断的无锁幂等**：针对手机与桌面两端同时点确认的场景（E-57），以 SQLite 行级 `state = 'waiting'` 为乐观条件更新；已被决断的闸门直接拦截并抛出 409 `E_GATE_ALREADY_DECIDED`，在 `details` 中回传已决断设备 ID、决断结果与时间戳，避免重复触发下游派发或重复通知。
6. **事务与副作用严格分离**：所有闸门决断、任务状态迁移及配置变更必须在同步 `UnitOfWork` 事务内提交；`settings.gates_changed`、`task.gate_passed` 及 `task.landed` 事件恒在事务提交后方可 publish，防止事务失败导致外部消费方收到幻象事件。
