# M6-T2　收流编排与落盘接线

- 所属模块：[[M6]]　**运行监管**——管一次运行从启动到结束的全过程：状态机（「已退出」与「已落地」分开）、收流与落盘编排、按游标分段回读与厂商会话文件的只读引用、进度信号、停滞检测、中止与 daemon 重启后的对账、回话投递。凡「这一次运行现在怎么样、它说过什么」的都归它
- 前置依赖：[[M6-T1]]、[[M1-T4]]、[[M1-T8]]
- 完成后解锁：[[M6-T3]]、[[M6-T8]]

## 输入 / 产出

- **输入**：M1-T4 的 logstore；M4 的归一化事件
- **产出**：`service/run.ts` 的收流路径

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 每条归一化事件写一行 `events.ndjson`（**全量原文永不截断**），每条原始输出行写一行 `raw.log`
2) `events` 索引表只收里程碑事件，高频 `*_chunk` 不进表
3) 事务回调内不出现 `await` 与任何异步副作用
事件发布在事务返回后（[[E-142]] 的对偶面）

## 必须处理的边界

- [[E-142]]　daemon 长跑内存增长
    - 触发：连续运行数天
    - 期望：内存只保留最近 N 条事件的环形缓冲，历史事件全部落盘按需回读

## 实施沉淀

<!-- notes:begin -->
- **写序与落盘接线**：收流路径与 M1-T4 的 `logstoreService` 对接。对子进程原始输出（stdout/stderr），剥除末尾多余 `\r?\n` 后由 `logstore.appendRaw` 统一追加并帧化写入 `raw.log`，单段超 200MB 自动触发分段。归一化事件由 `logstore.appendEvent` 写入 `events.ndjson`，保持全量原文永不截断。
- **里程碑索引过滤**：`events` 索引表过滤复用 `@agent-scheduler/shared/api/events` 的 `isMilestoneEventKind` 判定。`agent_message_chunk`、`agent_thought_chunk`、`available_commands_update` 等高频流式片段仅追加文件，不写入 SQLite `events` 表，既避免写锁争用，又符合索引只查里程碑的设计。
- **事务与发布分离**：`transitionState` 等状态流转操作在 `unitOfWork.run` 事务回调中仅同步更新数据库（runs 表状态、结束时间、退出码），回调内严禁 `await`、严禁文件写与 `bus.publish`。待发事件收集在内存临时数组，等待事务成功返回后，才向 `bus` 发布并调用 `appendEvent`。
- **长跑内存控制（E-142）**：`RunService` 内部不缓存历史事件数组，所有事件落盘后即结束生命周期；内存中仅由 `EventBus` 下的固定 5000 条容量 `RingBuffer` 保留最近窗口供 SSE 断线重放；超 32 KiB 的大 payload 由 `logstore.appendEvent` 返回的 `location` 转换为 `locationRef` 传给 `bus.publish`，进入环形缓冲前替换为引用。进程退出时调用 `closeRunStream` 及时释放 writer。
- **未映射与容错机制（E-140/E-202）**：非 JSON 输出或损坏 JSON 行留在 `raw.log` 继续流转；能解析但未映射到已知 EventKind 的厂商事件不中断流，递增 `unmapped_event_count`，不臆造顶层 kind。
<!-- notes:end -->
