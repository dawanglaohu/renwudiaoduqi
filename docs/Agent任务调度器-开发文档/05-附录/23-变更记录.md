# 变更记录

本节记录**文档自身**的演进。0.1–0.8 都产生于 2026-08-31 的同一次无人值守运行——
之所以拆成八个版本而不是记成一条，是因为**中途用户补充了需求、调研结论推翻了一条既有决策**，
这两件事改变了后面的走向，合并成一行就看不出来了。
0.9 是次日的环境清账，不属于那次运行。

## 后续变更怎么记

文档章节与配置是事实源。审查方可依据原始需求和已定契约修正局部遗漏，在本表记录影响；不得删减验收标准迁就错误代码。

编辑前用 `maintain_docs.py begin` 保存基线，编辑后用同一补丁 ID 执行 `sync`，同步产物并复核受影响任务，再用 `verify` 登记证据。保持原任务、worktree 和 PR，代码仍有缺陷时只回传差异；已获授权的提交与落地继续执行。完整命令见 README 的「改了文档之后」。

`DOC_PATCH` 记录已完成的文档修补，裁定仍使用 `pass / rework / doc-issue`；只有尚缺决策或契约无法落实时才判 `doc-issue`，并只阻塞受影响工作。同步未完成或证据版本过期时不可派发；已在途运行继续使用派发快照。
