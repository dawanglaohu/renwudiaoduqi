CANDIDATE C-01
WHAT: 任务状态机与"完成"的判定口径——agent 进程退出不等于任务做完，需要定义 已派发/运行中/待确认/已验收/失败 各状态由什么信号进入。
HINT: "发派的任务可以看到进度与完成状态提醒"
COST_IF_SKIPPED: CLI 与桌面版 agent 都不产出"百分比"，只有"还在跑 / 退出了 / 退出码"。不定义判定口径，进度只能反映"进程还活着"，用户收到"完成"提醒后仍要逐个人工核对是真做完还是跑飞了，第 1 点等于没实现。
SIZE: 3-5 人天（状态机本身；每类 agent 的信号采集另计）
DIMENSION: 闭环缺口

CANDIDATE C-02
WHAT: 桌面机与手机之间的常驻中枢服务与推送链路（含外网可达与鉴权）。
HINT: "电脑桌面端 + 手机 app 端"、"可以看到进度与完成状态提醒"
COST_IF_SKIPPED: agent 全部跑在桌面机上，手机通常不在同一网络。没有中枢和推送，手机端只能同局域网内主动刷新，"提醒"变成"自己去看"；人一出门，手机端那一半完全失效。
SIZE: 8-14 人天（中枢服务 + 推送通道 + 鉴权 + 公网部署或穿透）
DIMENSION: 闭环缺口

CANDIDATE C-03
WHAT: 在会话视图里回话与授权——agent 中途提问或请求执行权限时，人能从调度器（尤其手机端）回一句、点同意。
HINT: "可以进入任务调度中查看发派agents出去的会话内容"（原话只给了"查看"）
COST_IF_SKIPPED: codex/claude 桌面端跑到一半问"是否执行该命令""这里我理解得对吗"，只读界面答不了，任务静默卡死直到人回到电脑前。夜间派活、出门看进度这两个最主要的使用场景直接作废。
SIZE: 5-8 人天（回写通道 + 移动端输入 + 每类 agent 的输入注入方式各不相同）
DIMENSION: 角色盲区（人作为被 agent 追问的一方）

CANDIDATE C-04
WHAT: 文档重新产出后的任务对齐——给文档版本与任务内容打指纹，标记在途/已完成派发记录的失效并提示重派。
HINT: "根据当前使用的技能产出的文档"、"基于这个任务产出的开发文档"
COST_IF_SKIPPED: 这份文档是可反复重新生成的产物，任务 ID、验收标准、提示词都会随之变。在途任务还在用旧提示词干活，交回来的产出对不上新验收标准；上一版已完成的任务在新版里可能已不存在，完成率与进度显示失真。
SIZE: 3-5 人天
DIMENSION: 生命周期

CANDIDATE C-05
WHAT: 任务数据的入口与交接台状态的双向同步——从阅读器读取结构化任务，并把调度器里的完成态写回交接台。
HINT: "根据文档产出的  任务交接台中的任务发派给不同的  agents  干活"
COST_IF_SKIPPED: 交接台本身已经在记录每个任务的完成态（侧边栏进度角标）。调度器另起一份状态后，同一个任务在两个地方显示不同结果，人不知道该信哪个；若连导入方式都不定义，用户得把几十个任务在调度器里重录一遍，只是把手工复制换了个地方。
SIZE: 4-6 人天
DIMENSION: 数据出入口

CANDIDATE C-06
WHAT: 产出回流——把 agent 干完的分支名/改动文件/PR 链接挂回对应任务记录。
HINT: "发派给不同的  agents  干活"、"完成状态"
COST_IF_SKIPPED: 只知道"完成"，看不到干了什么。验收时仍要手工去仓库翻是哪个分支、动了哪些文件；多个 agent 并行时更分不清哪一坨改动是谁的产出。派→干→验收的最后一步断在调度器外面。
SIZE: 3-5 人天
DIMENSION: 数据出入口

CANDIDATE C-07
WHAT: 中止 / 撤回 / 换一个 agent 重派，以及长时间无响应的超时检测。
HINT: "发派的任务可以看到进度与完成状态提醒"、"发派给不同的  agents"
COST_IF_SKIPPED: agent 死循环、跑偏、或者一开始就选错了 agent，任务会永久停在"运行中"。唯一的处理办法是走到桌面机手工杀进程——而手机端恰恰是用户要的那一半，在这个场景里它只能眼看着。
SIZE: 4-6 人天
DIMENSION: 失败恢复

CANDIDATE C-08
WHAT: agent 接入配置的自助维护（可执行路径、启动方式、登录态与密钥、工作目录、并发上限的注册表化）。
HINT: "如：codex 桌面版 + claude  桌面端 + pi cli + grok cli  + DeepSeek Harness"、"此类  agents  产品"
COST_IF_SKIPPED: 起步就是 5 个形态各异的 agent（2 个 GUI、2 个 CLI、1 个 harness），且这几家都在高频改命令行参数和登录方式。接入方式写死在代码里，任何一家改版都要改代码并重新打包桌面端和手机端两个客户端；"此类"暗示以后还会加第 6、第 7 个。
SIZE: 4-6 人天
DIMENSION: 运营维护

CANDIDATE C-09
WHAT: 并发隔离——同一仓库上多个任务同时开工时的工作区隔离，以及冲突任务的串行约束。
HINT: "任务调度器"、"发派给不同的  agents  干活"
COST_IF_SKIPPED: 交接台本来就把任务排进多条并行 lane，"发派给不同的 agents"天然是并行的。多个 agent 同时在同一个仓库工作区改文件，改动互相污染，没法一个任务一层地分开落地。不做的话只能一次派一个，"调度器"退化成"一键发起器"。
SIZE: 4-8 人天（每任务独立工作区 + 冲突检测与排队）
DIMENSION: 规模变化

CANDIDATE C-10
WHAT: 会话流的分段加载与保留上限（滚动加载、旧会话归档或清理）。
HINT: "可以进入任务调度中查看发派agents出去的会话内容"
COST_IF_SKIPPED: 单个 agent 会话是几十万字级的连续输出，一份文档几十个任务、还会重派多轮，会话库很快到 GB 级。手机端拉全量会话既慢又费流量，桌面端渲染也会卡住——第 2 点在真实数据量下打不开。
SIZE: 3-5 人天
DIMENSION: 规模变化

SIZE: 1 人天（批次级决定端点 + 三种动作的状态迁移 + 收口运行失败三种情形的归宿）

SIZE: 0.5 人天（派生状态与触发判定各加一条 origin=wrapup-fix 的分支 + 测试）

CANDIDATE C-202
WHAT: 查 bug 运行的执行参数：用哪个 agent／模型（取值来源）、权限档、跑在哪个工作区（同任务 worktree 与分支）、输出不合五段时的出口。已裁定的是它的开关、时机、提示词来源和结果分流，没裁定它自己怎么跑。
HINT: 「查 bug 窗口 可设置开关」；结果分流里「FIXED 非空→通知审查会话再审一轮」意味着这个窗口会改代码
COST_IF_SKIPPED: 开关一开，产品就要起一个运行，但没有一条规则说用谁、以什么权限、在哪跑。审查运行是 readOnly（E-135）、收口运行是 workspaceWrite（E-283）、收口 agent 取值有 E-287，查 bug 运行三者都没有对应条目。若实施者比照审查运行给 readOnly，FIXED 永远为空，「FIXED 非空→再审」分支成为死代码，本可当场修掉的 bug 全部落入 NOT_FIXED，S1/S2 直接转人；若比照重派开干净 worktree，FIXED 改动落在任务分支之外，落地清单收不到；若输出缺五段，没有定义的去向（文档其他运行的规矩是「解析不出一律转人，绝不默认放行」，E-274／E-62，但没写到这里）。上一轮同类候选 C-101「收口运行由哪个 agent 执行」已被采纳（决策 74），这是同一类缺口。
SIZE: 1 人天（agent／模型取值规则 + 权限档与工作区归属 + 五段解析失败出口 + 用例）
DIMENSION: 运营维护（附一条失败恢复子项：五段解析失败的出口）
