## 一个必须先想清楚的物理事实（不是岔路，是前提）

被发派的 agent（codex 桌面版、claude 桌面端、各种 cli）**装在用户的电脑上**，
手机上不可能跑它们。所以手机端**必然是电脑端的远程控制端**，不可能独立工作。
这条不拿去裁决——它不是偏好问题，是物理约束。它会直接进 01 节和 06 节。

由此派生出的**真岔路**是：手机怎么够到电脑（下面第 2 题）。

## 第 1 批：架构骨架（研究无关，可先发）

**问题 1：调度器的核心跑在哪？**
- 岔路成因：agent 装在 PC 上，手机够不到；核心放错地方，两个端都得重写。
- A：**本机常驻服务（daemon）+ 桌面 UI 只做壳**，手机连这个 daemon ——
  桌面关了任务还在跑；多一个进程要管，要处理开机自启、端口占用。
- B：**核心塞进桌面应用进程**，手机连桌面应用 ——
  少一个进程；但桌面窗口一关，正在跑的 agent 就没人收结果了。

**问题 2：手机怎么连到电脑？**
- 岔路成因：决定要不要写服务端、要不要买服务器、以及能不能在外网用。
- A：**只走局域网**（手机和电脑同一个 wifi），扫码配对 ——
  零服务器成本、零隐私外泄；出门就用不了。
- B：**自建中继服务器转发**，公网可用 ——
  在哪都能看；要买服务器、要做账号体系、会话内容过第三方，成本与责任都上一个台阶。
- C：**局域网优先 + 可选接入用户自己的隧道**（Tailscale/frp 之类，不自建）——
  出门能用且不碰用户数据；要用户自己会配一次。

**问题 3：任务数据怎么读进来？**
- 岔路成因：读法决定了文档一改，调度器要不要跟着改。
- A：**直接读 `docs-data.js`**（阅读器生成的那个文件，`window.DOCS` 里已经有
  tasks/modules/edges/handoff/taskPaths 全套结构化数据）——
  一次解析拿全；绑死在这个技能的产物格式上。
- B：**自己重新解析 24 节 markdown 表格** ——
  不依赖阅读器；等于把 build_docs.py 的解析逻辑抄一遍，格式一变两边都要改。

**问题 4：⏳ agent 适配范围怎么定？**（选项待调研结论定型）
- 岔路成因：五个目标形态不同（2 个 GUI + 2 个 CLI + 1 个 harness），
  能力很可能不对等。全做还是先做能做的，决定了工期和这个产品成不成立。

## 第 2 批：状态与持久化（研究无关）

**问题 5：进度状态从哪来？**
- 岔路成因：原话要「看到进度与完成状态提醒」，但 agent 未必主动上报。
- A：**只认结束态**（进程退出码 / 输出结束）——简单可靠；跑一小时的任务中间是黑盒。
- B：**流式解析 agent 输出**，从中间事件推进度 ——能看到「正在改哪个文件」；
  每个 agent 输出格式不同，适配成本按个数乘。

**问题 6：会话内容存哪、存多久？**
- 岔路成因：原话要「查看发派 agents 出去的会话内容」，但没说留多久。
- A：**全量落本地库，永久留**——随时回看；跑几十个任务后库会涨。
- B：**只留最近 N 次，旧的自动清**——可控；想回溯三周前的就没了。

**问题 7：任务状态和文档谁是准的？**
- 岔路成因：文档是单一事实源（技能铁律 7），但任务状态是运行时产生的。
- A：**状态只存调度器自己的库，不碰文档**——文档保持只读，不会被写坏。
- B：**把状态回写进文档目录**——一处可见；违反「实现期不许改文档」。

## 第 3 批：范围边界（研究无关）

**问题 8：管不管 git / PR？**
- 岔路成因：技能的落地流程是 gh stack 一任务一层。调度器要不要接这一段？
- A：**只管发派与回读，git 全留给人**——范围小、风险小；人还是要手工建 worktree、push。
- B：**顺手把 worktree 与 stack 也建了**——真自动化；一旦建错分支，
  破坏的是用户的仓库，而这次原话完全没提 git。

**问题 9：单人还是多人？**
- 岔路成因：决定要不要账号体系。
- A：**单人单机**（就是文档作者自己）——不做账号；
- B：**多人协作**——要账号、要权限、要冲突处理。
