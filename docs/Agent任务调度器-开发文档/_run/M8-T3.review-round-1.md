## REWORK

- R1（阻断）接线缺失：`scheduler-tick` job 从未被启动，本任务四条端点全部落到 `50-routes` 的「未实现」占位（`http/plugins/50-routes.ts:79-99` 对不在 `customRegisteredPaths`（`:54`）里的 `ROUTES` 一律注册 500 `E_INTERNAL`）。证据：`boot/container.ts:290` 的 `ContainerServices` 没有 `dispatch`，`:301` 的 `jobs` 恒为 `Object.freeze([])`；`http/routes/runs.ts:296` 的挂载条件是 `options?.dispatchService || container?.services?.dispatch`，两者都取不到 → 派发路由不挂；`registerBatchesRoutes`/`registerSnapshotRoute` 在 `50-routes.ts` 里根本没被 import。后果是 AC 1 在运行期不成立（互斥量所属的 job 不存在），且 `/api/v1/runs` 等端点返回 501 而非真实结果。改法：容器按 `platform → clock/ids → db → repos → logstore → events → proc → adapters → workspace → services → jobs` 顺序构造 dispatch 服务（注入 tasks/batches/documents/dispatchSnapshots/runs repo、clock、ids、bus/envelopeFactory 与 disk-watch 的停派标志）并放进 `services.dispatch`；`50-routes.ts` import 并调用 `registerBatchesRoutes`、`registerSnapshotRoute`，把本任务端点补进 `customRegisteredPaths`；`scheduler-tick` job 进 `container.jobs`。验证：新增一条走真实 boot 路径的回归用例（构造容器 → 建 server → 断言 `POST /api/v1/runs` 不是 501、`GET /api/v1/snapshot` 200、`container.jobs` 含 `scheduler-tick`）。

- R2（阻断）跨层：SQL 与运行仓储写在 service 层。`service/dispatch.ts:110`（`INSERT_RUN_SQL`）起，整张 runs 表的 `INSERT`/`SELECT`/`UPDATE` 语句、`runs` Row 类型（`:26`、`:60`）与 DTO 映射都在 `service/dispatch.ts` 内，并在 `:166` 自建 `createSqliteDispatchRunsRepo`、`:448` 兜底 `createSqliteDispatchRunsRepo(deps.database)`。08 节：**SQL 只许出现在 `repo/`，repo 之外出现 `SELECT/INSERT/UPDATE/DELETE/db.prepare` 一律架构测试判失败；全仓 15 个目录里没有 `repo/runs.ts` 之外的地方可以承载 runs 表**；`test/arch/layering.test.ts` 是这条禁令的执行者。改法：把 runs 仓储与 Row/映射整体搬进 `repo/runs.ts`（`service/dispatch.ts` 不得出现任何 SQL 字面量，也不得在 service 内 `db.prepare`），由 DI 传入；快照 INSERT 与 run INSERT 收进同一个 `unitOfWork.run(fn)`（回调内不 await、`bus.publish` 移到 `run()` 返回之后）。顺带修 `:606`、`:618`：并发兜底靠 `err.message` 字符串匹配分支，违反「禁止用 `err.message` 做字符串匹配来分支，一律判 `err.code`」——`db/open-database.ts` 的 `toDatabaseError` 已给 `E_DB_CONSTRAINT`，改为判 code。验证：加一条架构测试断言 `service/` 下出现 SQL 关键字即失败；`dispatch-contract.test.ts` 全绿。

- R3（阻断）硬编码 agent：`service/dispatch.ts:1125` 把派发候选的 `agentId` 写死成 `'codex'`（注释自称「后续支持指派覆盖」）。任务定义写明本层是「唯一决定这一阶段用谁跑」的地方、取值链为「任务指派 → 阶段覆盖 → agent 默认」，M7 只消费结果；`agentId` 不在 `runs` 表任何约束白名单里（`migrations/0001_init.sql:106` 只是 `TEXT NOT NULL`），所以 `codex` 不是注册表里存在或可用的 agent 时会写出一个永远不被调度的孤儿运行。改法：把 agent 取值走注入的注册表/指派入口，取不到时给出类型化原因并跳过该任务，不要落一个假 agentId；`deps.agentLimits`（`:1106`）的兜底数字同一处理，别在 service 里散落魔法默认值。若判断该取值链应由 M8-T9 统一落地，至少在 `:1125` 前置校验「该 agent 在注册表里且可用」，不可用时进 `tasksBlocked`。
