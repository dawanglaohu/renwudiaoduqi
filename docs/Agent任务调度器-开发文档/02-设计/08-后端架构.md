# 后端架构

本节决定 daemon 侧的代码放在哪、哪一层不许调什么。
**唯一的检验标准：这句话能不能直接写进代码。** 写不进去的就是没写。

所有分层禁令由 `test/arch/layering.test.ts` 用一张 `ALLOWED_IMPORTS` 邻接表
正则扫全部 `import` 语句**机器化断言**，违规即 `pnpm test` 失败——**不靠人 review**。

## 分层与调用方向

五层单向：

```
http/routes → service → (repo | logstore | proc | adapters | workspace | events) → (db | platform)
```

`domain` 是**零依赖叶子**：任何层都可 import 它，它不许 import 除 `shared` 之外的任何东西。

**禁止的反向与跨层调用（逐条写死）：**

- `repo` 禁止 import `service` / `http` / `events` / `proc` / `adapters`
- `service` **禁止 import `fastify`**——文件里不得出现 `FastifyRequest` / `FastifyReply` / `request.*`；
  需要 `actorDeviceId` 就作为普通函数参数传进来
- `proc` 与 `adapters` 禁止 import `repo` / `service`——它们只产出数据结构，**落库一律由 service 做**
- `events` 禁止 import `service`（否则发布与编排成环）
- `jobs` 禁止 import `http`，且只能调 `service`，不许直接摸 `repo` / `db`
- `http/routes` 禁止跨层直调 `repo` / `logstore` / `proc` / `adapters` / `workspace`，
  只能调 `service`。**唯一例外是 `sse.ts` 直接向 `events/bus` 订阅**
- **全仓禁止 barrel 文件**（任何目录不得有 `index.ts` 转出）——
  它会把跨层 import 藏进路径别名从而绕过检查

**会话引用不跨任务（E-303，决策 88）**：任何新建运行（派发、返工、修复、审查、查 bug、续接审查、重跑）落库前，
service 层必须断言它的 `vendor_session_ref`（续接时是目标会话引用）不等于**其他任务**任一运行的 `vendor_session_ref`，违反即拒绝并返回 `E_SESSION_ARCHIVED`；
同一任务内的续接审查行与首轮相等是允许的，所以这条**不能**用 SQLite 唯一索引表达，只能由 service 校验 + `test/arch/session-isolation.test.ts` 兜底——
后者扫全部创建运行的路径（`dispatch` / `rework` / `wrapup` / `bughunt-context` / `review` 各 service 与 `POST /runs` / `rerun` / `recall` 路由），
断言每条路径都经过同一个 `assertSessionNotShared()`，漏一条即失败。`session_archived_at` 非 NULL 的运行拒绝任何消息投递与续接，同样返回 `E_SESSION_ARCHIVED`。

## 数据层

**连接**：全进程恰好一个 `Database` 实例，由 `db/openDatabase(path)` 工厂在 `boot/` 创建后经 DI 传递。
**除该工厂外任何文件禁止 `new Database()`。**
打开后立即固定四条 PRAGMA：`journal_mode=WAL`、`busy_timeout=5000`（E-150）、
`foreign_keys=ON`、`synchronous=NORMAL`。**其余 PRAGMA 一律不设。**

**迁移**：放 `migrations/NNNN_名字.sql`，`db/migrate.ts` 在 `listen()` 之前按文件名升序
逐个在独立事务里执行并写 `schema_migrations(version, applied_at)`。
**已应用的文件禁止再修改**（只能新增一个迁移改回来），**不写 down 脚本**。

**唯一的 PRAGMA 例外（E-291，决策 84）**：扩枚举 CHECK 或放宽 NOT NULL 在 SQLite 里只能按官方
12 步法整表重建，而 `foreign_keys=ON` 下 `DROP TABLE` 会被子表引用挡住、`PRAGMA foreign_keys`
在事务内又是空操作。因此**首行恰为 `-- requires: foreign_keys=off` 的迁移文件**由 `migrate.ts`
在事务外先 `PRAGMA foreign_keys=OFF`，事务内执行全部语句，执行后 `PRAGMA foreign_key_check`
必须返回零行否则回滚并以非 0 退出（日志列出前 20 条违规，不带业务正文），`finally` 里开回 ON。
标记不在首行或拼写不符就按普通迁移执行。重建顺序恒为被引用者先；
禁止 `ALTER TABLE x RENAME TO x_old`（SQLite ≥3.26 会把子表外键一起改名）。
**重建不算改已应用文件**；除这一处外「其余 PRAGMA 一律不设」不变。

**SQL 边界**：SQL 只许出现在 `repo/` 目录。`repo` 之外任何文件出现
`SELECT` / `INSERT` / `UPDATE` / `DELETE` / `db.prepare` 一律由 arch 测试判失败。
`repo` 内部**禁止用模板字符串或 `+` 把值拼进 SQL**，参数一律 `?` 或具名绑定；
唯一允许的动态片段是 `ORDER BY` 与分页方向，且必须来自一张封闭枚举到列名的常量映射表
（`SORTABLE_COLUMNS`），**禁止把用户串直接当列名**。
预编译语句在 repo 工厂闭包里 `db.prepare` 一次并复用，**禁止在方法体里每次 prepare**。

**日志正文与 SQLite 的分工（写死）**：

- **正文只存文件**——每次运行两个文件：`raw.log`（stdout/stderr 交错的原始行）与
  `events.ndjson`（每行一个归一化信封）
- **SQLite 只存索引与可筛选字段**——
  `events(id, run_id, seq, ts, kind, scope, task_id, actor_device_id, file_seq, byte_offset, byte_len)`
  且**只索引里程碑事件**；`log_segments(run_id, stream, file_seq, path, byte_start, byte_end)`
  记 200MB 切片边界（E-149）
- **库里任何列都不得存事件 payload 正文**

**一致性靠单向写序保证**：**恒先 append 文件成功、再写索引行**。
反序绝对禁止——索引在前会读到未写入的垃圾字节。
崩溃后由 `log-index-repair` 从最后一条索引的 `byte_offset + byte_len` 扫到 EOF 补齐。
因此「**文件比索引多**」是允许的正常态，「**索引比文件多**」是数据损坏。

日志文件被用户手工删除时，repo 仍正常返回元数据，logstore 返回 `E_LOG_FILE_MISSING`
**类型化结果而不是抛异常**（E-151）。

## 中间件链

Fastify 只建一个实例、只监听一个端口。插件按文件名数字前缀注册，**顺序写死**：

```
00-request-id → 10-logging → 20-security-headers → 30-auth → 40-ratelimit
→ 50-routes → 80-static → 90-error-handler
```

- `00-request-id`：生成 `x-request-id` 并挂进 logger 上下文
- `10-logging`：Fastify 内置 logger，**`redact` 列表写死** `req.headers.authorization`、
  `*.token`、`*.pairingCode`、`*.deviceToken`
- `20-security-headers`：`X-Content-Type-Options: nosniff`，API 响应 `Cache-Control: no-store`
- `30-auth`：校验 `Authorization: Bearer 〈deviceToken〉`，把 `{deviceId}` 挂到 `request.actor`

**关键结构**：鉴权与限流**必须注册在 `/api/v1` 这个子 scope 内**
（`fastify.register(apiPlugin, {prefix:'/api/v1'})` 内部 `addHook('onRequest')`）。
**禁止把鉴权 hook 挂到根实例上**——Fastify 的封装边界一旦挂错，
会连带拦住静态资源或漏掉后注册的路由。

免鉴权白名单**只有三条且写死在一个常量数组里**：
`GET /api/v1/health`、`POST /api/v1/pair/claim`、`GET /api/v1/version`。
**代码中禁止出现任何基于 remoteAddress / 网段 / `isPrivateIp` 的绕过分支**（E-08）。
静态资源在根 scope 匿名可取，因为产物里不含任何用户数据——这是唯一的非鉴权面。

- `40-ratelimit`：**自写的内存滑动计数器（不引限流库）**，只挂 `/pair/*`，
  每 IP 每分钟 10 次，超限返回 429 **并立即作废当前配对码**（E-07）。其余端点不限流。
- SSE 路由在 `50-routes` 内注册，但**必须 `reply.hijack()` 后只操作 `reply.raw`**。
  写头固定 `Content-Type: text/event-stream`、`Cache-Control: no-cache, no-transform`、
  `Connection: keep-alive`、`X-Accel-Buffering: no`（E-154）；每 15 秒写一行 `:\n\n` 心跳；
  `request.raw.on('close')` 里注销订阅。**SSE 路由内禁止调用 `reply.send`。**
- `90-error-handler`：同时设 `setErrorHandler` 与 `setNotFoundHandler`，
  是**主要**允许出现 HTTP 状态码数字的地方。精确禁令：状态码数字**只允许出现在三个文件**——
`http/plugins/90-error-handler.ts`、`http/sse.ts`（握手 200 与关流用的 401/409）、
`http/plugins/30-auth.ts`（401/403，因为鉴权发生在 `onRequest` 钩子里、未必经过错误插件）。
其余文件出现三位数字面量由架构测试判失败。
统一错误处理限定映射：`elevate_once` 请求中的非法状态迁移 `E_INVALID_STATE_TRANSITION` 带 `operation: elevate_once` 上下文时映射为 409 Conflict（E-133）；其他状态机错误保持原有 HTTP 状态。
**所有成功响应统一 200**，不用 201/204——免得每个路由各挑一个。

**不注册 CORS 插件**——生产同源，开发用 Vite proxy。代码里出现 `@fastify/cors` 一律打回。

## 事务边界

**只有 `service/` 层能开事务**，入口唯一为注入的 `unitOfWork.run(fn)`（内部是 `db.transaction(fn)`）。
repo 方法**一律不自开事务**，必须能在事务内外同样执行。

**禁止嵌套**：`UnitOfWork` 持一个 `depth` 计数，`run()` 在 `depth > 0` 时直接抛 `E_TX_NESTED`，
**不许靠 savepoint 隐式吞掉**。

**事务回调内禁止出现 `await` 与任何异步/阻塞副作用**——better-sqlite3 是同步 API，
回调里一旦跨事件循环就会长时间独占 WAL 写锁。因此禁止在事务内 spawn 子进程、
读写日志文件、发 SSE、调 adapters 或 workspace。
**硬顺序恒为「先在事务里改库、事务返回后再做副作用」。**

本次新增的三条编排路径都照这个顺序写死，实施时不许颠倒：

- `wrapupService.triggerWrapup()`：事务**前**读批次/任务/运行、逐条 await 进 HEAD 判定、
  `docs.getWrapupContext()` 取材料、组装提示词、深拷贝注册表；事务**内**复核条件未变、
  INSERT 快照与 `kind='wrapup'` 的运行（`queued`）、`transitionBatch(→wrapping)`、收集事件；事务**后** publish 并 nudge tick。
- `wrapupService.recordWrapupResult()`：事务**前**从 logstore 读最终文本、`parseWrapupReport`、
  `planWrapupFixes`、为每组修复组装提示词与快照；事务**内** INSERT `batch_wrapups`、收口运行迁移、
  批次迁移、逐条 INSERT 修复运行；事务**后** publish。
- `reviewService.finalizeReviewRun()`：事务**前**解析审查输出；事务**内**写 `review_verdict` / `rework_text`；
  事务**返回后**才调 `reworkService.dispatchRework()` 做回灌／恢复／新开三种投递。
  返工那组写入（被审运行迁移、`rework_count + 1`、（新开分支时）INSERT 返工运行）与投递同属
  `dispatchRework()`：写入在它自己那一次事务里，投递在该事务返回之后，投递失败再由它用独立事务转 `awaiting_human`。
  **一次返工判定只有一个事务写 rework 字段**：`finalizeReviewRun()` 与人工打回路径只写 `review_verdict` /
  `rework_text` 与闸门裁定，**不得**重复写 `rework_count`、**不得**再迁移被审运行，也**不得**把
  `dispatchRework()` 包进自己的事务（禁止 A 调 B 各开事务）。事务上下文不向上传给 route、也不向下传给
  proc / adapters / logstore。

  `resolveAssignment({stage:'review'})`、覆盖 agent 跨家时深拷贝覆盖 agent 当前注册表条目；事务**内**（跨家时）INSERT 子快照（`parent_snapshot_id` 指向实施快照）与审查行；事务**后** spawn（决策 107、121，E-341、E-342、E-352）。
  `bughuntService.dispatchBughunt()`、`reworkService.dispatchRework()` 新开分支与 M8-T7 修复派发同法读快照，`stage` 分别为 `bughunt`／`rework`／`wrapup-fix`，**零回落**。
- `reviewService.finalizeReviewRun()` 的**第一步**（机械检查之前）：事务**前**拿到 `hasContentEvent`（收流路径维护的内存标记）；为 false 时事务**内** `reviewing → awaiting_human`（reason `exited_before_output`）、INSERT `gates` 行（comment `exited_before_output`）、`tasks.lane_no` 置 NULL、收集 `lane.released`，**不跑机械检查、不派审查、不写 `review_verdict`**；事务**后** publish 并 `agentService.refreshLogin(agentId, {trigger:'exited_before_output'})`（决策 118、119，E-348）。
- `agentService.refreshLogin()` 与 `listAgentModels({refresh})`：**不开事务**——它们只起探测子进程与读配置文件，history 那条 SQL 是只读查询；结果写内存缓存（`loginCache`／`liveCache`），每次登录探测结束都 publish `agent.availability_changed{reason:'login_changed', login}`（决策 108、115、130）；非 dsh 的 agent 在首次探测完成前 `login` 为 `{state:'unknown', reason:'not_probed', checkedAt:null, loginCommand}`（决策 133）。

事件发布同理：service 在事务内把待发事件收集进本地数组，`run()` 返回后才 `bus.publish`。
`bus.publish` 出现在事务回调内由 arch 测试判失败。

一个 HTTP 请求最多开一次事务。
组合多个 service 时**禁止「A 调 B、各自开事务」**——跨 service 的复合写必须新建一个
上层 service 方法，把双方的 repo 调用聚进同一个 `unitOfWork.run`。
事务上下文**不许作为参数向上传给 route，也不许向下传给 proc / adapters / logstore**。
**jobs 与 route 走完全相同的规则，没有「后台任务可以放松」的例外。**

**启动顺序（19 节 M1-T10 验收为唯一权威）**：配置装载 → 整机单实例锁 → 数据目录 → 打开库 → 跑迁移 → createContainer → 建 Fastify → listen → listen 成功后启动 jobs → 报告 ready。锁自 acquire 起持有到进程退出，期间不释放；listen 被外部进程占端口而失败时必须释放锁并以非 0 退出。

## 工具层

**不存在 `utils/` / `helpers/` / `common/` / `misc/` / `lib/` 目录**——
出现即打回（arch 测试断言目录名黑名单）。

- 有业务语义的纯函数一律进 `src/domain/`
- 跨包共用的纯函数进 `packages/shared/src/`
- 只被单个文件用到的私有函数就地放在该文件底部，**不许升格为共享工具**

**「不算工具」的口径写死为四条**：

1. 凡是碰 fs / net / db / 子进程的不算——属于对应的基础设施层
2. 凡是读 `Date.now()` / `Math.random()` / `crypto.randomUUID()` 的不算——
   **时钟与 id 必须从 DI 注入 `clock.now()` / `ids.newId()`**，否则 domain 无法被确定性测试
3. 凡是读 `process.env` / `process.platform` 的不算——分别归 `config/env.ts` 与 `platform/host.ts`
4. 凡是「把值格式化成给人看的中文字符串」的不算——**那是 web 层的事，daemon 不产出用户文案**

`domain/` 下每个文件必须能被 Vitest 直接 import 且**顶层零副作用**：
禁止顶层读文件、建连接、注册定时器。

## 错误体系

只有一个基类 `AppError extends Error`，字段固定：

```ts
{ code: ErrorCode, message: string, details?: Record<string, unknown>, cause?: unknown, retryable: boolean }
```

**不带 HTTP 状态码字段。禁止三层继承。**
只有在需要携带结构化附加字段时才允许直接继承出子类，第一版**只允许两个**：
`AgentProcessError`（带 `pid` / `exitCode` / `signal` / `stderrTail` / `launchSpecId`）与
`DocsSourceError`（带 `docsPath` / `offset`）。

每个基础设施模块必须在自己的边界把原生错误包成 AppError 并挂 `cause`：
`ENOENT` → `E_AGENT_EXEC_NOT_FOUND`、`SQLITE_BUSY` → `E_DB_BUSY`、AJV 校验失败 → `E_VALIDATION`。

**禁止让原生错误穿透到 service 之上；禁止 `catch {}` 空吞；
禁止用 `err.message` 做字符串匹配来分支**（一律判 `err.code`）。
除 `assertNever` 外**全仓禁止 `throw new Error('...')`**。

**只有 `http/plugins/90-error-handler.ts` 允许把 code 转成 HTTP 状态码**，
且它**直接读 `ERROR_CODES[code].defaultHttpStatus`**（06 节共用约定里那一份）。
**`errors/` 目录下不得出现第二张状态码表**——出现 `CODE_TO_STATUS` 一类常量即架构测试失败。
`origin === 'client'` 的条目 daemon 侧不注册；未登记的 code 与非 AppError 一律 500 + `E_INTERNAL`。

响应信封固定 `{error: {code, message, requestId, details?}}`。
非 AppError 的原始 message 与 stack **只写服务端日志、不回客户端**（`AGSCHED_DEV=1` 时才附 stack）。
daemon 侧 `message` 一律是英文开发者短句，**禁止在 daemon 里拼中文用户文案**。

## 配置加载

分三类，读取次数各不相同：

1. **进程配置**（端口 / 绑定地址 / 数据目录 / 日志级别 / dev 开关）——
   来自环境变量 + 当前平台用户应用数据目录下的 `daemon.json`，**启动时读一次**，
   `Object.freeze` 后经 DI 注入，**不支持热更**，改了必须重启
   （端口与数据目录热更没有安全语义，E-03 / E-150）
2. **agent 注册表**位于同一数据目录的 `agents.json`——**支持热加载**，
   实现固定为 `fs.watch` + 300ms 防抖 + **内容指纹去重**
   （编辑器保存会触发多次写事件，不去重会重载多次）。
   校验失败时**保留上一版**并发 `agent.availability_changed` 警告事件，
   **绝不因此退出 daemon**（E-94）；未知字段忽略并 warn，缺字段回落 `config/defaults.ts`
   （E-92 的「内置默认变了」靠 defaults 与用户覆盖**分开存两份**来算差）
3. **派发快照**——每次派发把注册表条目**逐字段深拷贝**进
   **`dispatch_snapshots.launch_spec_json`**（`runs.snapshot_id` 指向它，见 09 节），
   **在途运行只读该快照**，运行中的代码禁止再读注册表当前值（E-93）

`adapterKind` 的热切换**必须校验该 agent 无在途运行**，否则拒绝并保留旧值（E-189）。

平台默认目录不用 shell 字符串表达。boot 先冻结以下宿主输入，再注入 platform：

```ts
type PlatformHostInputs = Readonly<{
  platform: 'win32' | 'darwin' | 'linux'
  homedir: string
  appData?: string
  xdgDataHome?: string
}>
```

`platform/host.ts` 是全仓唯一读取 `process.platform` 与 `os.homedir()` 的文件；
`config/env.ts` 在启动时除五个 `AGSCHED_*` 产品变量外，只快照操作系统提供的
`APPDATA` 与 `XDG_DATA_HOME` 两个宿主路径输入。platform 只消费冻结值，不能自己读环境。
`appDataDir()` 必须返回**已规范化的本机绝对路径**：Windows 仅当 `APPDATA` 是绝对路径时
使用它，否则取 `path.join(homedir, 'AppData', 'Roaming')`；macOS 固定取
`path.join(homedir, 'Library', 'Application Support')`；Linux 仅当 `XDG_DATA_HOME`
是绝对路径时使用它，否则取 `path.join(homedir, '.local', 'share')`，最后追加
`agent-scheduler` 或开发态的 `agent-scheduler-dev`。任何返回值都不含 `~`、`${...}` 或
`%...%`；`homedir` 不是绝对路径时以 `E_DATA_DIR_UNRESOLVABLE` 终止启动（E-271）。

daemon 的桌面启动、自启与安装包共用一个不可拼 shell 的启动契约，定义在
`packages/shared/src/shell/daemon-launch-spec.ts`：

```ts
type DaemonLaunchSpec = Readonly<{ file: string; args: readonly string[]; cwd: string }>
```

运行时 `file` 与 `cwd` 必须是当前机器上的绝对路径，`args` 每项原样传递；若 daemon 是
Node 脚本，则 `file` 是随包分发的 Node 可执行文件、脚本绝对路径是 `args[0]`；若打成独立
可执行文件则 `args` 可为空。安装位置构建时未知且 macOS `.app` 可能被用户移动，
所以**禁止在安装包里预写绝对路径清单**。桌面壳每次启动都根据本次实际
`current_exe/resource_dir` 解析并校验一个 `DaemonLaunchSpec`，然后把同一个冻结对象交给
「启动 daemon」与 M1 的 `autostart.register(spec)/status(spec)/unregister()`；调用时恒为
`shell:false`。M10-T5 必须在含空格和 Unicode 的临时安装根目录执行该解析器与启动 smoke。
禁止只登记脚本路径、忽略参数或依赖调用者当前工作目录（E-209）。

**禁令**：除 `config/env.ts` 外任何文件禁止出现 `process.env`
（`proc/env.ts` 构造子进程环境是唯一白名单）；
除 `config/registry.ts` 外任何文件禁止读 `agents.json`；
请求处理路径里**禁止出现同步文件读取来取配置**（配置必须已在内存）。

## 依赖注入

手写 composition root：`boot/container.ts` 导出 `createContainer(config): AppContainer`，
构造顺序写死：

```
platform → clock/ids → db → repos → logstore → events(bus/idAllocator/ringBuffer)
→ proc → adapters → workspace → services → jobs
```

**不引入任何 DI 框架 / 装饰器 / 反射。**
依赖一律通过工厂函数参数传递，统一写法 `createXxxService(deps)` 返回对象字面量。
**除 AppError 及其两个子类外不写 class**（避免半个模块 class、半个模块闭包的两套风格）。

**禁止模块级可变单例**——形如 `export const db = openDatabase(...)`、
`export const bus = new Bus()` 一律打回。模块顶层只允许导出纯常量与纯函数。
理由：Vitest 并行用例会互相污染，且 E-150 的单实例语义由**进程锁**保证而不是靠模块变量。

全进程仅两个允许的单例：`boot/lock.ts` 的单实例锁与 Fastify 自带 logger，
都在 `main.ts` 创建且只被 boot 触碰。

容器通过 `fastify.decorate('container', container)` 挂一次，
route handler 从 `request.server.container.services.xxx` 取。
**禁止 route 从容器里取 repo / db / proc / adapters。**

凡是与外部世界交互的东西（clock、ids、fs、spawn、fetch）**都必须在容器里有可替换实现**。
集成测试通过替换 `proc.spawnManaged` 为假进程来跑，**禁止在测试里 mock 模块路径**。

**容器装配是接线的终点，不是可选项**（06 节接线注册表，接线审计 2026-09-19）：`createContainer()` 返回的
`proc` / `adapters` / `workspace` 必须是真实实现而不是空对象；`services.review`、`services.gates` 必须注册并被
`run.ts` 的进程退出回调与 route 共用（M7-T9）；`dispatch.createRun()` 落库事务返回后必须经
`workspace.prepareWorktree()` → `adapters[agent].buildLaunchSpec()` → `proc.spawnManaged()` → `runService.attachProcess()`
真正拉起进程（M8-T10）。`test/integration/container-wiring.test.ts` 用真实容器 + 假子进程断言这条链路，
只 INSERT 一行 `starting` 而不 spawn 的派发一律不算接通。

## 后台工作

`src/jobs/` 下一个工作一个文件，统一形状 `createXxxJob(deps) => {name, start(), stop()}`。
全部由 boot 在 `listen()` **之后**启动、在优雅退出时**先于** HTTP 关闭。
**五个都必须出现在 `boot/container.ts` 的 `jobs` 数组里**——不在数组里的 job 永远不会被 `start()`（M7-T9 接线，`test/arch/container-jobs.test.ts` 逐字断言名字集合）。

**只有五个：**

| job | 触发 | 做什么 |
|---|---|---|
| `reconcile-runs` | 启动期一次 | E-123：按 `runs.pid` 对账，进程不存在标「异常终止」、存在则标「失联」并给杀掉入口。**绝不推定成功** |
| `log-index-repair` | 启动期一次 | 补齐索引尾部 |
| `stall-detector` | 30s tick | 按 `runs.last_event_at` 与启动/思考两套阈值，**只发 `run.stalled_suspected` 弱事件，不改运行状态、不杀进程**（E-120） |
| `scheduler-tick` | 事件触发 + 5s 兜底 | 一个 tick 固定四步、每步各自最多一个事务：① **进 HEAD 刷新**——查 `landed` 且 `is_in_head=0` 的实施/收口运行（每运行 ≥30s 一次、每 tick ≤20 条，按 `ended_at` 升序），**顺序** await `workspace.isBranchInHead()`，顺手记 `branch_tip_sha`，一次事务批量写回；② **批次推导**——对 `running` / `awaiting_landing` 的批次算「全部 landed？全部进 HEAD？」，未全进 → `awaiting_landing`；全进且无在途收口且轮次未超 → **收口模式为自动时**选 batch_no 最小的一个调 `wrapupService.triggerWrapup({trigger:'auto'})`，**触发成功即 return，本 tick 不再派发**（收口运行要占名额，E-283）；**收口模式为手动时**只把 `canWrapup` 算成 true、不触发，等 `POST /batches/:id/wrapup`（E-312）；③ **补位派发**——这一步就是既有派发，只是窗口维度换成槽位：`domain/lane-slots.ts` 的 `countLaneSlots({tasks, runs})` 按 `tasks.lane_no` 非空计已占槽位（持槽的收口运行也算 1），空槽数 = `lane_count − 已占`；先给持槽任务下 `queued` 的审查／查 bug 行与 `lane_no` 为空的收口运行按 agent 名额启动，再对每个空槽从可放行集合取任务——**打回后等泳道的返工排在全部新任务之前**（按打回时间先后，E-327），其余按 M8-T2 的可放行集合以层号、taskKey 字典序取——经 `assertSessionNotShared()` 后派实施运行并写 `tasks.lane_no`、`runs.lane_no`，发 `lane.assigned`；一个 tick 最多补到空槽用完；**agent 并发上限仍按运行计**（M8-T1 的 `calculateConcurrencyLimit` 与 `countsTowardAgentConcurrency` 原样复用，审查、查 bug、收口与修复运行各占该 agent 1 名额但不占槽位，E-311）；空槽而无可放行任务时该槽在 `lanes[]` 里是空闲泳道；④ 没有第五步。**全局一把内存互斥量，禁止并发 tick、禁止重入**——否则会把同一任务派两次；禁止一个 tick 触发两次收口；禁止对未全部 landed 的批次跑 git；禁止在任何读接口里现跑 git 判进 HEAD。`PATCH /documents/:id/settings` 改 `laneCount` 后 nudge 一次 tick：调大立即补位（E-310），调小只让 `countLaneSlots` 的空槽为负、不杀任何运行（E-309） |
| `disk-watch` | 5min | 超阈值发 `system.disk_warning` 并置「停止新派发」标志（E-103 / E-104） |

**收口触发不是第六个 job**——它是 `scheduler-tick` 的第二步（决策 62）。
**泳道补位与会话归档也不是 job**——补位是 tick 的第三步，归档由任务终态迁移的 service 方法在事务后触发（决策 87、88）。
**收流不是 job**——子进程输出由 proc 的流水线**事件驱动**。
只有「没人触发也必须发生」的事才配做 job；**任何人想为收流加轮询 tick 一律打回**。

隔离规则：job 禁止 import `http/`、禁止持有 request/reply、只调 service，
且**必须与 route 复用同一批 service 方法**（jobs 里出现第二套业务逻辑一律打回）；
写库时 `actorDeviceId` 恒为 `null` 表示系统发起（E-128）。

每个 tick 自己保证不重入（上一次未完成则跳过本次并计数），
内部必须 try/catch 把异常转成事件，**禁止让异常冒泡到 `unhandledRejection`**。
`stop()` 必须 clearInterval 并等待当前 tick 结束。

## 子进程管理（本项目特有）

`proc/` 是全仓唯一允许 `import child_process` 的目录，唯一入口：

```ts
spawnManaged(spec: LaunchSpec): ManagedProcess
LaunchSpec = { file, args: string[], cwd, envOverrides, timeouts, label, runId }
```

调用方恒传绝对 `file` 与原始 `args[]`，`proc` 恒以 `shell: false` 启动（E-42）。
Windows 设置 `windowsHide: true`；直接启动原生程序时使用 `windowsVerbatimArguments: false`。
**业务层禁止组装命令串或预转义参数。仅 Windows 适配器可为已解析的 `.cmd` / `.bat`
生成 ComSpec 所需的命令串，并在这个分支返回 `windowsVerbatimArguments: true`。**
adapters 的 agent 调用、workspace 的 git 调用、审查的机械检查命令与平台终止动作，
**全部走这一个函数**。

**可执行文件**：`file` 必须是 `platform.resolveExecutable()` 按当前宿主解析出的
**绝对路径**（E-130）。Windows 保留盘符、UNC 与长路径语义；以 `.cmd` / `.bat`
结尾的目标不直接 spawn，改为 spawn `platform.comSpec()`。`resolveExecutable()`
负责返回已校验的脚本路径与 ComSpec 路径；**拿到全部原始 `args[]` 后**，Windows
适配器才用 `quoteForCmd()` 完成脚本路径和各参数的转义及整条命令的外层引号，返回冻结的
`{file: ComSpec, args: ['/d', '/s', '/c', commandLine], spawnOptions}`。
`proc` 原样消费该对象，不能在已闭合的 `/c` 命令后追加参数。原生程序与 POSIX
程序仍传独立 argv；`DaemonLaunchSpec` 不接纳命令串或 `spawnOptions`。
Windows 实机测试须通过 `.cmd` 和 `.bat` 启动回显程序，断言最终 argv 的值与个数：
覆盖空参数、普通参数、空格、Unicode、引号、分号（U+003B）、`&`、`^`、`%`、`!`，
同时覆盖含空格与元字符的脚本路径；不得只比较转义函数的输出字符串。
不允许插入额外命令或展开环境变量。ComSpec 参数含 NUL、CR 或 LF 时，在启动前返回
`E_VALIDATION` 并以 `details.argumentIndex` 标出参数，不能静默截断或谎称已无损传递。
macOS/Linux 对 POSIX 绝对路径做 `realpath`，要求最终目标存在、是普通文件且通过 `X_OK`，
然后直接 spawn；符号链接无效走类型化错误，不回退到同名 PATH 候选（E-262、E-263）。
读到另一平台的路径格式时保留原值但标无效，绝不转换盘符、根目录或挂载点（E-264）。

图形界面和自启进程不得依赖 `.zshrc` / `.bashrc` 补出的 PATH：解析顺序恒为
“注册表绝对路径 → 平台级固定候选目录 → 要求用户选择文件”，并在失败详情里列出全部已检查位置；
**禁止 source 或执行用户 shell 启动文件**（E-270）。

**进程树终止**：spawn 成功即把 pid 写进 `runs.pid`，并登记到内存中以 `runId` 为键的
`ProcessRegistry`。终止一律走 `platform.killTree(pid, processOps)`：Windows 先执行
`taskkill ['/PID',pid,'/T']`，等 3 秒仍存活再加 `/F`；macOS/Linux 启动托管进程时建立独立
进程组，先对进程组发 `SIGTERM`，等 3 秒仍存活再发 `SIGKILL`。两次尝试都写事件。
`process.kill` 只允许封装在注入的 `processOps.signalGroup()` 内执行平台适配器给出的动作，
业务层与调用方禁止直接杀父进程，否则会留下占文件锁的孤儿 node/git/npm（E-119）。
不引入 Job Object 附加模块（Node 无原生 API，需 N-API 编译，
与「零原生依赖除 better-sqlite3」冲突）；孤儿的兜底是平台 `killTree` + 启动时对账。

**流读取**：
**禁止 `child.stdout.setEncoding()`**（多字节 UTF-8 会被 chunk 边界切碎），
**禁止 `readline`**（E-203：`U+2028` / `U+2029` 在 JSON 字符串里合法但会被断行——
文件顶部必须写死这条注释，并配一条含 `U+2028` 的回归用例）。
统一由 `proc/line-reader.ts` **在 Buffer 上只按 `0x0A` 切、剥尾部 `\r`、再 UTF-8 解码**；
单行上限 1 MiB，超限截断并附 `{truncated: true, rawByteLen}` 后继续找下一个 `\n`（E-141）。

**子进程环境**由 `proc/env.ts` 单点构造：
强制 `LANG` / `LC_ALL=en_US.UTF-8`、`NO_COLOR=1`、`FORCE_COLOR=0`（E-131）；
按 `envDenylist` 清掉 `ANTHROPIC_MODEL` / `ANTHROPIC_DEFAULT_*_MODEL` 等模型覆盖变量（E-37）；
写死 git 凭据禁用：`GIT_TERMINAL_PROMPT=0`、`GIT_ASKPASS=`、`GCM_INTERACTIVE=never`、
`GIT_CONFIG_NOSYSTEM=1`、`GIT_CONFIG_GLOBAL=〈空文件〉`（E-138）。
**不做 `chcp`**——管道输出与控制台代码页无关，解码统一在 line-reader 做。

**超时分三个独立计时器**，全在 `proc/timers.ts`（E-190）：

| 计时器 | 默认 | 到点做什么 |
|---|---|---|
| `startupTimeoutMs` | native 60s / generic-acp·npx 180s | 从 spawn 到第一条可解析事件。超时 → 杀树 + `E_AGENT_STARTUP_TIMEOUT` + 标派发失败 |
| `idleTimeoutMs` | 900s | 从最后一条事件起算。**只喂给 stall-detector 打弱标记，proc 层绝不因它杀进程** |
| `hardWallClockMs` | 0（关闭） | 仅用户显式设置才生效 |

**唯一允许「到点必杀」的超时**是机械检查命令的 `checkTimeoutMs`（默认 10 分钟，E-66），杀后不重试。

**背压**：每 run 一个 `logstore.AppendQueue`，待写字节超 8 MiB 时 `child.stdout.pause()`、
回落到 4 MiB 再 `resume()`。
**禁止把 stdout 读进内存字符串、禁止 `for await` 累加全量。**
向 stdin 注入回话必须检查 `write()` 返回值并在 `drain` 后续写——返回 false 仍连写一律打回。

**僵尸回收**：`exit` / `error` / `close` 三个事件都走同一个**幂等** `finalize(runId)`，
负责清三个定时器、flush 并关闭写队列、从 Map 移除、写终态事件。
**daemon 优雅退出时不杀 agent 子进程**（E-01 / E-51 要求任务继续跑），
但必须承认并写死一条事实：**除 codex app-server / grok leader socket 这类外部常驻通道外，
子进程管道无法跨 daemon 重启重挂**——重启后只能对账不能重挂，
**禁止任何「重新 attach stdout」的假实现**。

## 内部事件模型（本项目特有）

信封形状写死，定义放 **`packages/shared/src/api/events.ts`** 供两端共用（路径以 06 节修订 3 为准）：

```ts
{
  id: number,              // daemon 全局单调号，用于 SSE Last-Event-ID
  ts: string,              // 带毫秒 ISO8601，来自注入的 clock
  runId: string | null,
  taskId: string | null,
  scope: 'run' | 'task' | 'batch' | 'agent' | 'system' | 'lane' | 'settings' | 'document',
  kind: EventKind,
  seq: number,             // 该 run 内从 0 起的连续序号，用于文件定位
  actorDeviceId: string | null,
  payload: unknown
}
```

`EventKind` 是具名联合，**分两组、靠命名形状区分**：

- **ACP 组**严格沿用 `session/update` 原文小写下划线：`agent_message_chunk`、`agent_thought_chunk`、
  `tool_call`、`tool_call_update`、`plan`、`available_commands_update`。
  **禁止为了「统一风格」改成 camelCase。**
- **本产品组**一律 `〈scope〉.〈过去式动词〉`。其中 **`run.state_changed`（payload 带 `from` / `to` / `reason`）
  是状态机每一次成功迁移都必须发的那一条**——十三个状态若只靠 `run.started` / `run.exited` / `run.aborted`
  三条，UI 看不到其余十个（见 09 节）。完整清单：`run.state_changed` / `run.started` / `run.exited` / `run.aborted` /
  `run.stalled_suspected` / `run.stderr_line` / `run.permission_blocked`（E-133）/
  `run.remote_push_detected`（E-75）/ `run.message_delivered` / `run.message_undelivered`（E-113）/
  `task.gate_waiting` / `task.gate_passed` / `task.review_verdict` / `task.landed`（payload 带 `by: 'auto'|'human'` 与 `gateId`）/
  `batch.advanced`（**每一次** `batches.state` 迁移都发，payload `{batchId, batchNo, from, to, reason}`，前端靠它展开批次树）/
  `batch.wrapup_started`（payload `{batchId, batchNo, round, runId, trigger, promptSource, branchName}`）/
  `batch.wrapup_finished`（payload `{batchId, batchNo, round, runId, wrapupId, verdict: 'clean'|'fixed'|'open'|'unparsed', declaredVerdict, fixRunIds, unassignedCount, batchState}`）/
  `run.rework_dispatched`（`runId` 是**接收返工的那条实施运行**，payload `{mode: 'inject'|'resume'|'new_run', source: 'review'|'human'|'wrapup', sourceRunId, reviewRunId, wrapupRunId, reworkCount, itemIds}`）/
  `settings.gates_changed`（scope `settings`，payload `{gates}`）/
  `settings.pipeline_changed`（scope `settings`，payload `{pipeline: {bughunt, wrapupMode}}`，E-318）/
  `document.settings_changed`（scope `document`，payload `{docId, laneCount}`，`PATCH /documents/:id/settings` 写成功后发，让两端的泳道缓存失效，E-309、E-310）/
  `lane.assigned`（scope `lane`，payload `{docId, laneNo, taskId, runId, reason: 'refill' | 'manual' | 'rework'}`，补位、手动派发或人打回后重新入道写下 `tasks.lane_no` 的事务后发；收口运行占槽时 `taskId` 为 null）/
  `lane.released`（scope `lane`，payload `{docId, laneNo, taskId, runId, reason: 'landed' | 'awaiting_human' | 'failed' | 'aborted' | 'interrupted' | 'wrapup_finished'}`，`tasks.lane_no` 置 NULL 或收口运行到终态的事务后发；收口释放时 `taskId` 为 null）/
  `task.sessions_archived`（payload `{taskId, runIds, killedPids, residualPids}`，归档事务返回、`killTree` 两阶段做完后发；`residualPids` 非空即 E-322）/
  `agent.availability_changed`（payload 加 `login: LoginState | null`；**每次登录探测结束**——成功、超时、unparsable、exec_missing——都发一条 `reason:'login_changed'`，`available` 与上次相同、payload 含完整 `LoginState`（含 `checkedAt`、pi 的 `providers`），前端据此失效 `agents` 缓存重拉 `GET /agents`；`changed` 谓词不把 `login` 算进去，`login_changed` 的 publish 不触发登录缓存自清，任何「收到该事件就重探」的订阅方必须排除此 reason，决策 130，E-335）/
  `system.disk_warning` / `system.docs_changed`。
  `run.exited` 的 payload 固定带 `stderrTail: string[]`（进程 `close` 时从 proc 通道的「最后 20 行 stderr」环形缓冲取，每行 ≤1 KiB、总量 ≤8 KiB，落盘前过 `redactSecrets()`；成功运行也写、可能为空数组），审批卡按 E-348 从该 run 最后一条 `run.exited` 读它（决策 122）

  **本产品组 kind 的前缀就是信封 `scope`**（决策 106，E-334）：`scope` 八值 `run` / `task` / `batch` / `agent` / `system` / `lane` / `settings` / `document`，
  `EVENT_DEFINITIONS` 的 scope 由前缀派生并用类型断言机检（`kind` 的前缀字面量类型必须等于 `scope`）。
  `GET /events?docId` 对 `run` / `task` / `batch` / `lane` 按 docId 过滤（`lane` 按 `payload.docId`），`settings` / `document` / `agent` / `system` 全量下发不过滤。
  窗口数调整只发 `document.settings_changed`；空泳道出现或消失不发 `lane.*`；超出窗口数只在 `lanes[]` 标 `overLimit`、不发 release。
  事件 payload **禁止带收口报告正文、返工块正文或查 bug 报告正文**——只带 id 与计数，正文走 REST。

厂商私有字段一律塞 `payload.vendor` 原样保留，
**禁止为某一家新增顶层 kind**（E-186 / 决策 34）。

**id 单调递增**的实现写死为 `events/id-allocator.ts` 的**水位预分配**：
SQLite `event_seq(name TEXT PRIMARY KEY, watermark INTEGER)`，
内存计数器每用满 1000 个就把新水位写库，启动时从水位继续。
**允许跳号、禁止回退**（客户端按 id 去重，E-10）。
**禁止任何其他地方自造事件 id、禁止用纯内存计数器**——daemon 重启会回退，
直接破坏 E-153 的重放语义。

**环形缓冲与落盘的边界**写死为三条：

1. `events/ring-buffer.ts` 全局一个、容量恒 5000 条（它就是 E-153 说的重放窗口）
2. 存完整信封，但单条 payload 超 32 KiB 时在入缓冲前替换为
   `{truncated: true, byteLen, ref: {fileSeq, byteOffset, byteLen}}`（E-142）
3. **SSE 推送与断线重放只读环形缓冲**；任何按游标回读历史**只走 logstore 的字节偏移分段读**。
   `Last-Event-ID` 小于缓冲最小 id 时返回 `E_REPLAY_WINDOW_EXPIRED`（409），
   让客户端改走 REST 全量快照（E-153）。
   **禁止为了回读去查 `events` 表拿 payload**——表里根本没有正文。

**落盘规则**：每条归一化事件写一行 `events.ndjson`（**全量原文，永不截断**），
每条原始输出行写一行 `raw.log`；
而 `events` 索引表**只收里程碑事件**（`run.*` / `task.*` / `batch.*` / `lane.*` / `system.*` /
`tool_call` / `tool_call_update` / `plan`），
**高频的 `*_chunk` 不进表**——否则一次运行会灌出几十万行索引。

## 登录态探测、实时清单与指派取值链（本项目特有）

三件事都是补充需求 2026-09-12（二）加进来的，放在一起说是因为它们共用同一条边界：**产品只问 agent，不猜、不读凭据、不当闸门**（决策 108、109）。

**探测器扩展**：`adapters/login-probe.ts` 的 `probeLogin()` 与 `adapters/models-live.ts` 的 `readModelsLive()` 都复用 M4-T3 `adapters/probe.ts` 的
`executeProbeProcess()`（已是 `spawnManaged` + 超时 `kill()`）与 `buildProbeLaunch()`（`.cmd`／`.bat` 的 ComSpec 分流），可执行路径由调用方传入 M4-T3 已解析的 `resolvedPath`，
不自己解析；`resolvedPath` 为空直接 `unknown/exec_missing`。解析器按注册表 `loginProbe.parser` / `modelsLive.parser` 具名枚举选（`codex_login_status` / `claude_auth_json` / `grok_models_exit` / `pi_auth_check` / `none`；
`grok_models_text` / `pi_list_models_table` / `codex_model_list_jsonrpc` / `none`），注册表只装命令参数、正则源串与超时值，不装解析逻辑（决策 15）。
codex 的 `model/list` 走 `adapters/codex/model-list-rpc.ts`：stdin 逐行写 `initialize` → `initialized` → `model/list`，`onJson` 忽略无 id 的通知与非本请求 id 的响应，`hidden:true` 的项过滤，`nextCursor` 最多追两页，收齐即 `kill()`。
**缓存**：登录态缓存 `loginCache`（键 `login:〈agentId〉`）与 `liveCache` 都在 `service/agents.ts`，**不复用** M4-T3 的指纹缓存（生命周期与可执行文件 mtime 无关）；失效点只有四个——`POST /agents/:id/probe`、`GET /agents/:id/models?refresh=1`、可用性翻转、该 agent 的运行零产出退出；
同一 agent 的在途探测用 `inflight` Map 去重；**没有定时器、没有 TTL**（决策 115）。`parser='none'` 的 agent 不起进程、不写缓存、DTO 的 `login` 为 null。
**脱敏**：stdout／stderr 进 logger、`rawStdout`、`warnings` 或事件 payload 前必过 `adapters/probe.ts` 的 `redactSecrets()`；解析器读原文（E-354）。

**取值链所在层**：`domain/assignment.ts` 的 `resolveAssignment()` 是零依赖纯函数（只 import `./effort-tier.ts` 与 shared 类型），六个 `stage` 穷举：
`implement`（body → agent 默认）、`review`（`reviewOverride` → 任务指派，跨家时模型不带、思考强度 `remapEffortAcrossAgents()`）、`rework` / `bughunt` / `wrapup-fix`（逐字任务指派，零回落）、
`wrapup`（手动 body → `wrapupAssignment` 固定项 → 跟随来源）。它不读 settings、db、clock；缺 agent 不在函数里判，由 service 调用后 `assertCanDispatch()`。
读快照只经 `service/assignment-reader.ts` 的 `readTaskAssignment(implRunId)`（旧行 `assignment_json` 为 NULL 时用该快照首条 `runs` 行合成，不回填），`assignment_json` 字面量只许出现在 `repo/dispatch-snapshots.ts` 与该文件（arch 测试）。
`domain/effort-value.ts` 的 `toEffortColumns()` / `fromEffortColumns()` 是 `EffortValue` 与 `runs.effort_tier` / `effort_vendor` 两列的唯一转换点，两列同时非空抛 `E_INTERNAL`；
`domain/effort-tier.ts` 的映射函数改为接收注册表 `effortVendorMap` 作参数，参数名（`-c model_reasoning_effort`、`MAX_THINKING_TOKENS`、`--reasoning-effort`、`--thinking`）仍留代码层 `KNOWN_EFFORT_TRANSPORTS`，禁止搬进注册表。
history 来源由 `repo/runs.ts` 的 `listSucceededModelNames({agentId, limit})` 一条 SQL 派生（成功终态集合来自 `domain/run-state-machine.ts` 的 `SUCCEEDED_RUN_STATES`，变量标记按数组长度生成），pi 的 `:〈thinking〉` 后缀只在 `adapters/pi` 剥（决策 114，E-340）。

**禁令**：`service/agents.ts` 禁止出现 `jsonrpc` / `model/list` / `--list-models` / `logged in` / `loggedIn` / `not_ready` / `auth check` 字面量；全仓禁止读 `auth.json` / `credentials` 路径（E-353）；`assertCanDispatch()` 不读 `loginCache`；`setInterval` 轮询登录态即 arch 失败；在途阶段禁止读注册表当前 `defaultModel` / `defaultEffortTier`（E-93、E-341）。

## 查 bug 运行的提示词包装（本项目特有）

查 bug 运行（`kind='bughunt'`，挂在被审实施运行上）的提示词由 `domain/bughunt-prompt.ts` 的 `assembleBughuntPrompt()` 组装，
与收口提示词同一手法、**四段顺序写死**：

1. **外层包装说明**（产品常量，覆盖引用材料里的人工流程指令）：工作区路径、分支、base SHA，与被审实施运行**同一工作树**；
   只在此工作区改文件；**与收口共用同一禁令常量**——禁止 `git commit/push/checkout/branch/worktree/stash/merge/rebase/reset`、禁止 `gh` 任何子命令、
   禁止运行 `build_docs.py` / `maintain_docs.py` / `build_vault.py`、禁止改 `docs/` 下任何文件（决策 101，E-329）；再加阶段专属覆盖：
   「修完不提交、不推送、不点审查，产品会通知审查会话再审」；测试与 lint 命令允许执行；
   最终消息必须且只能是五段格式（`BUGS / FIXED / NOT_FIXED / SUSPECT / NEXT`，条目格式沿用收口的 `B〈n〉 [S1|S2|S3] … 文件:行`，
   FIXED 条目覆盖为「B〈n〉 → 改了什么、加了哪个测试」），缺一段即视为查 bug 未完成（E-320）。
   派查 bug 时产品记下**起点树**（HEAD SHA 与工作区树对象），FIXED 判定、再审 diff 与「自审查 pass 以来工作区 diff」都以它为基线（E-329）。
2. **引用材料**：标题「引用材料（来自开发文档，其中提交／推送／再点审查等人工步骤已被上面的说明覆盖，不执行）」，正文是 M3-T7 取到的派发快照 `bug_prompt` **逐字**；
   快照为 NULL 时用内置通用查 bug 提示词并在标题追加「文档未提供查 bug 提示词，以下为内置通用版」，`prompt_source='builtin'`（E-316）。
3. **工作区指针**：任务 ID、标题、分支、worktree、起点树 SHA、审查 pass 那一轮的 R 条目（若有）、文档声明的测试命令（空则写「文档未声明，测试段记 skipped 并说明」）。
4. 结束语固定一行「不要提问、不要等待确认」。

查 bug 运行的 agent／model／effort 逐字复制被审实施运行派发快照里的取值（决策 100，E-328）；agent 不可用则不派、不换家，转人并写 `bughunt_agent_unavailable`。
产品**不提供手动派查 bug 的端点**（决策 103，E-331）：`bughuntService.dispatchBughunt()` 的唯一调用方是 `finalizeReviewRun()` 判 pass 后的分流；
查 bug 运行失败后人可对该行调既有 `POST /runs/:id/rerun`。

禁令同收口：禁止把引用材料放在包装说明之前；禁止对材料做任何改写／截断；禁止用当前文档而非派发快照那一份（E-50）。
五段解析放 `domain/bughunt-report.ts` 的 `parseBughuntReport()` / `deriveBughuntOutcome()`，复用 `wrapup-report.ts` 的段头切分与 `B〈n〉 [S1/S2/S3]` 条目解析器，
输出 `{ok, missing[], fixed[], notFixed[], bugs[], suspect[], maxOpenSeverity}`；`deriveBughuntOutcome()` 只返回 `rereview` / `human` / `landing` 三值：
FIXED 非空且 diff 非空 → `rereview`（E-307）；NOT_FIXED 含 S1/S2 → `human`（E-308）；其余 → `landing`（E-321）；解析失败不进这三值，走 E-320。

## 收口运行的提示词包装（本项目特有）

收口运行（`kind='wrapup'`）不挂任务，提示词由 `domain/wrapup-prompt.ts` 的
`assembleWrapupPrompt()` 组装，**四段顺序写死**，实施不许调换：

1. **外层包装说明**（产品常量，覆盖引用材料里的流程指令）：工作区路径、分支、base SHA；
   只在此工作区改文件；**禁止 `git commit/push/checkout/branch/worktree/stash/merge/rebase`、
   禁止 `gh` 任何子命令、禁止建新分支或新目录、禁止运行 `build_docs.py` / `maintain_docs.py` / `build_vault.py`、
   禁止改 `docs/` 下任何文件**；测试与 lint 命令允许执行；改动留在工作区不提交，产品出落地清单；
   最终消息必须且只能是八段格式（`BATCH_SUMMARY / TESTS / BUGS / FIXED / NOT_FIXED / SUSPECT / RECORD / NEXT`，
   `RECORD` 段写 `verdict: clean|fixed|open` 而不是文件路径），缺一段即视为收口未完成（E-274）。
